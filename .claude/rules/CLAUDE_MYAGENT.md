## Architecture (MyAgent.py)

**Mixin-based modular design** — The `App` class in `MyAgent.py` inherits from 22 mixin classes in the `myagent/` package, each grouping related methods by concern (UI, streaming, tools, persistence, etc.). Constants and tool schemas live in `myagent/constants.py`; helper classes in `myagent/helpers.py`. Only `__init__` and the entry point remain in `MyAgent.py`. All mixins share state through `self.*` — no inter-mixin imports.

**Multi-provider support** — A Provider combobox switches between Anthropic, OpenAI, Google, xAI, and Moonshot (plus Ollama for local inference). Provider labels are company names; the Google provider serves the Gemini models and the Moonshot provider the Kimi models — legacy saved provider values ("Gemini", "Kimi") normalize to the company labels in `_restore_model_params`. The internal message format stays Anthropic-style; translation happens only at the API boundary: OpenAI uses `_messages_to_responses()`/`_tools_to_responses()`/`_stream_responses()`, Gemini uses `_messages_to_gemini()`/`_tools_to_gemini()`/`_stream_gemini_call()`, xAI reuses the Responses translators with its own `_stream_xai_call()`, and Moonshot (Kimi models) — Chat-Completions-only, so the Responses translators do NOT apply — has its own `_messages_to_kimi()`/`_tools_to_kimi()`/`_stream_kimi_call()` (see below). The `_ToolBlock` wrapper gives OpenAI/Google/xAI/Moonshot/Ollama dict-based tool responses the same `.name`/`.id`/`.input` interface as Anthropic's Pydantic objects, so `_execute_tool()` works identically for all providers. Gemini tool call IDs are synthesized as `gemini_{name}_{index}` (the API doesn't use IDs). Provider is saved per-instruction and in `agent_state.json`. The Instruction button is disabled while running. Google (Gemini) requires `GEMINI_API_KEY` or `GOOGLE_API_KEY`; xAI requires `XAI_API_KEY`; Moonshot requires `MOONSHOT_API_KEY` (or `KIMI_API_KEY`).

**OpenAI model filtering** — `_fetch_openai_models()` filters to Responses-API-compatible families via `OPENAI_RESPONSES_PREFIXES` (`gpt-4.1`, `gpt-5` — pruned in the 2026-07 audit: gpt-4.5 left the API 2025-07, gpt-4o retired 2026-02-16, and the whole o-series is scheduled out to gpt-5.6, o1/o1-pro/o3-mini/o4-mini on 2026-10-23 and o3/o3-pro on 2026-12-11); non-chat types (embedding, audio, search, realtime, preview, transcribe, tts) and legacy models (gpt-3.5-turbo, base gpt-4, gpt-4-turbo) are excluded. Scheduled-retirement ids that still pass the family prefixes are dropped too, via `OPENAI_DEPRECATED_MODEL_PREFIXES` (gpt-5-mini/-nano/-chat/-codex, gpt-5-2025 dated, gpt-5.1-chat) plus exact-match `OPENAI_DEPRECATED_MODEL_IDS` (bare `gpt-5`, bare `gpt-5.1-codex` — exact so the surviving gpt-5.6* and -codex-max/-mini ids aren't killed); policy is retiring-models-removed-ahead-of-shutdown, and their pricing entries are removed as well (gpt-5-pro and gpt-4.1 have no announced retirement and stay). GPT-5.6 (2026-07-09) ships as three tiers — sol (flagship $5/$30), terra (balanced $2.50/$15, the fallback default), luna (fast $1/$6) — priced in `OPENAI_PRICING`; gpt-5-chat-latest / gpt-5.1-chat-latest / gpt-5-codex / bare gpt-5.1-codex retired 2026-07-23. `OPENAI_REASONING_PREFIXES` (`o1`, `o3`, `o4`, `gpt-5`) get `reasoning` params instead of `temperature`. `gpt-5.x-chat-*` "Instant" variants (`_is_gpt5_chat_model()`) are non-reasoning, reject temperature, but support `text.verbosity`. The client uses `httpx.Timeout(600.0, connect=10.0, read=120.0)` to avoid indefinite hangs.

**Gemini model filtering** — `_fetch_gemini_models()` calls `gemini_client.models.list()`, strips the `"models/"` prefix, then applies a two-stage agentic filter: require the `generateContent` action (drops bidi-only live/audio models, embeddings, imagen, veo), then drop `GEMINI_NON_AGENTIC_SUBSTRINGS` name matches — specialized output modalities (TTS, the `-image`/Nano Banana lines, lyria music, omni AV), Interactions-API managed agents (deep-research, antigravity), the computer-use preview (needs its own tool protocol), gemma (no function calling), robotics — plus shut-down generations (`gemini-2.0-*`, `gemini-1.*`, which the API still lists) and the sunsetting `gemini-2.5*` family (retirement announced for no earlier than 2026-10-16 — picker-hidden and unpriced ahead of it per the 2026-07 audit policy, though the `thinking_budget` param wiring stays so a pinned 2.5 instruction keeps working until Google pulls it), falling back to `GEMINI_FALLBACK_MODELS`. What remains: the pro/flash/flash-lite text tiers, dated previews/variants (incl. `-customtools`, which is tuned to prefer registered custom tools — exactly MyAgent's pattern), and the floating `-latest` aliases. EVERY current text tier supports thinking — including Flash-Lite (verified live 2026-07) — so `GEMINI_THINKING_PREFIXES` has no "lite" carve-out. The config style is version-split by `_gemini_uses_thinking_level()`: Gemini 3+ (and the non-versioned `-latest` aliases, which float to 3.x+) send `thinking_level` (low/medium/high mapping 1:1 from the strength combo; a stale saved max coerces to high, and `gemini-3-pro-preview` coerces medium→high since it accepts only low|high), while 2.5 still requires the legacy `thinking_budget` (low=1024, medium=8192, high=24576 — sending `thinking_level` to a 2.5 model is HTTP 400). Both styles set `include_thoughts=True` so thought summaries stream to the Show Thinking pane (without it Gemini returns no thought parts at all). A reactive fallback in `_stream_gemini_call` retries once with the other style on a thinking-related 400, covering models/aliases whose style the version rules mispredict. SDK is `google-genai`, initialized with `GEMINI_API_KEY` or `GOOGLE_API_KEY`.

**xAI (Grok) integration** — `myagent/xai_mixin.py` rides on the already-installed `openai` SDK with `base_url="https://api.x.ai/v1"` (`XAI_DEFAULT_BASE_URL`) and `XAI_API_KEY` — no new dependency. xAI's primary surface is an OpenAI-style **Responses API** (same `input` items, flat `type:"function"` tool declarations, `function_call_output` results), so the existing `_messages_to_responses()`/`_tools_to_responses()` translators are reused verbatim; only the streaming caller is xAI's own. Architecture invariants:
1. **Raw event iteration, not the SDK stream wrapper** — `_stream_xai_events` consumes `client.responses.create(stream=True)` events directly instead of `responses.stream()`, whose client-side snapshot state machine is tuned to OpenAI's exact event sequences. Usage comes from the `response.completed` event (not `get_final_response()`); reasoning deltas are accepted as BOTH `response.reasoning_text.delta` and `response.reasoning_summary_text.delta` (models differ) and feed the Show Thinking pane.
2. **Server-side tools ON, mixing verified** — live probes (2026-07-05) proved xAI's built-ins mix cleanly with client-side function tools in one request (correct routing whichever the task needs), so xAI follows the OpenAI pattern: `_get_tools()` strips the local DuckDuckGo `web_search`/`fetch_webpage` and `_stream_xai_call` appends `{"type": "web_search"}` + `{"type": "x_search"}`, plus `{"type": "code_interpreter"}` gated off while desktop tools are on (same double-scaled-clicks rationale as OpenAI). Each invocation bills a flat $0.005, folded into the authoritative cost (below). Server activity streams as `web_search_call`/`code_interpreter_call`/`custom_tool_call` (x_search) output items → surfaced as activity notices; a 400 naming a built-in strips just that tool and retries.
3. **Reasoning knob per family** — `XAI_REASONING_EFFORT` (constants) maps prefixes to accepted `reasoning.effort` values, longest prefix wins: `grok-4.3` none/low/medium/high (low = API default; "none" disables reasoning), `grok-4.5` low..xhigh (always-reasoning — "none" is HTTP 400, verified live 2026-07-17), `grok-4.20-multi-agent` low..xhigh (the knob is agent collaboration count, not depth). Families absent from the table — the pinned `grok-4.20-*-reasoning`/`-non-reasoning` variants and the aliases (bare `grok-4.20` → the pinned reasoning variant, `grok-latest` → grok-4.3 at its server default) — get NO reasoning param; behaviour is baked into the model id. `_model_supports_thinking()` returns "extended" for knob families → the OpenAI-style Reasoning combobox; a stale saved effort coerces to the family default ("low") instead of erroring. Reasoning summaries verified streaming live (grok-4.3 emits them even at effort=low).
4. **Temperature alongside reasoning** (Gemini-style) — always shown in the UI and always sent; `_stream_xai_call`'s BadRequest downgrade ladder (drop temperature → drop reasoning summary → drop reasoning, each via `continue` so successive 400s converge) degrades gracefully if a model refuses. `openai.AuthenticationError` is surfaced as a clear "check XAI_API_KEY" error instead of ten retries.
5. **Model fetch + filtering** — `_fetch_xai_models()` lists `/v1/models`, keeps `grok*` ids, drops `XAI_NON_AGENTIC_SUBSTRINGS` (the grok-imagine image/video models), falls back to `XAI_FALLBACK_MODELS` (grok-4.3 default) — which matches the live catalog 1:1 (verified 2026-07-17): the API serves exactly grok-4.3, grok-4.5 (the agentic-coding flagship, 500K context, vision, added 2026-07), the three grok-4.20 variants, and grok-build-0.1; ALL legacy families (grok-4/-fast, grok-3, grok-2) are retired, with grok-code-fast-1 surviving only as an alias of grok-build-0.1. Aliases are alias *fields*, not list entries, so the picker shows canonical ids only. `XAI_NON_VISION_PREFIXES` (grok-build-0, grok-code) drives the weak-desktop-combo warning — text-only per docs; the prefix is `grok-build-0`, not `grok-build`, because `grok-build-latest` re-aliased to grok-4.5 (vision) in the 2026-07 catalog.
6. **Exact cost tracking via `cost_in_usd_ticks`** — xAI is the only provider that returns the authoritative billed cost in the response (`usage.cost_in_usd_ticks`, 1 tick = $1e-10, verified to the digit against hand-computed pricing). `_stream_xai_events` converts it to `usage_dict["cost_usd"]` and `stream_worker` prefers it over the table estimate, so the cost line is exact — including the cached-input discount ($0.20/M vs $1.25/M full rate; xAI caches aggressively) and the $0.005/server-tool fees, neither visible to a 2-tuple estimate. `XAI_PRICING` (verified live against /v1/models' price fields, unit $1/10000 per MTok: grok-4.3 + all grok-4.20 variants $1.25/$2.50, grok-4.5 $2/$6 — incl. the re-aliased grok-build-latest, whose longer entry outranks the grok-build prefix — grok-build and its grok-code-fast alias $1/$2, grok-latest alias) remains as the fallback when the field is absent; >200K-input long-context doubling keeps the ≤200K tier (gemini-3.1-pro convention). Documented in `MyAgent_Pricing.txt`.
7. **Live-verified end-to-end 2026-07-05** — a real grok-4.3 `stream_worker` run (tool round trip via local `web_search`, effort=low) confirmed: streaming text + reasoning-summary deltas arrive, xAI's UUID-style `call-…` tool ids round-trip through `function_call_output`, usage lands in `response.completed`, and the cost tracker matched hand-computed pricing to the digit ($0.002954 for 1771 in / 296 out).

**Moonshot (Kimi) integration** — provider label **"Moonshot"** (the company, matching the Anthropic/OpenAI/xAI convention; the models are branded kimi-*, so the mixin/constants keep `kimi_*`/`KIMI_*` names, and legacy saved provider values normalize in `_restore_model_params` — "Kimi"→"Moonshot", and likewise "Gemini"→"Google" from the same-day Google rename). `myagent/kimi_mixin.py` rides on the `openai` SDK with `base_url="https://api.moonshot.ai/v1"` (`KIMI_DEFAULT_BASE_URL`) and `MOONSHOT_API_KEY` / `KIMI_API_KEY` — no new dependency. Unlike xAI, Kimi's surface is **Chat Completions ONLY** (no Responses endpoint), so the mixin has its own translators: `_messages_to_kimi()` (system message first; tool results as `role:"tool"` messages keyed by `tool_call_id`; assistant tool calls on the `tool_calls` array; images as `image_url` data-URL parts, with tool-result images deferred to a follow-up user message like the Responses translator) and `_tools_to_kimi()` (nested `function` format, not the flat Responses shape). Catalog/params/contract verified against platform.kimi.ai docs 2026-07-25. Architecture invariants:
1. **reasoning_content round-trip is per-model policy, and it's load-bearing** — Kimi thinking models return reasoning in a non-standard `reasoning_content` field (streamed as `delta.reasoning_content`, always before `content`) and are TRAINED to reason across interleaved tool calls: the accumulated reasoning must be re-sent unmodified on assistant messages during a tool loop or quality silently degrades (the classic bug in OpenAI-compatible harnesses pointed at Kimi). `_stream_kimi_events` accumulates it into a `{"type": "thinking", "thinking": ...}` block stored FIRST in content_blocks (internal history stays Anthropic-style; chat_mixin already serializes that shape, so Save Thinking works), and `_messages_to_kimi` re-emits it as `reasoning_content`. Policy: REQUIRED for `kimi-k3` / `kimi-k2.7-code*` (Preserved Thinking always on) and `kimi-k2.6`; FORBIDDEN for `kimi-k2.5` (`KIMI_NO_REASONING_ROUNDTRIP_PREFIXES` — no Preserved Thinking support at all). Unknown future models default to round-tripping, backstopped by a 400-ladder rung that learns per-model (`_kimi_reasoning_rejected`), rebuilds the wire messages without reasoning, and retries. On `end_turn` the plain-string append drops the final turn's reasoning — explicitly allowed by Moonshot once a turn completes.
2. **Thinking knob per family** — `kimi-k3`: always-reasoning, top-level `reasoning_effort` on a SPARSE low/high/max ladder (no medium; API default max) → the extended Reasoning combobox; stale efforts coerce via `_KIMI_EFFORT_COERCE` (medium→high, xhigh→max, minimal/none→low, else max). `kimi-k2.6`/`k2.5`: `thinking {"type": "enabled"|"disabled"}` → the plain Thinking checkbox (strength hidden, Ollama-style); k2.6 additionally gets `keep: "all"` (Preserved Thinking) whenever enabled — matching the keep-everything translator — while k2.5 never gets `keep`. `kimi-k2.7-code` (+`-highspeed`): always thinks, rejects the thinking param entirely → no knob (support None), reasoning still streams to the Show Thinking pane. All Kimi-specific params ship via `extra_body` (the SDK has no typed `thinking`/`reasoning_effort` for chat.completions); `max_completion_tokens` is typed (32768 when thinking — docs demand ≥16000 for tool loops — else 8192), with a ladder rung swapping to legacy `max_tokens` on rejection.
3. **NEVER temperature** — every current Kimi model fixes sampling server-side (non-modifiable per the parameter reference; the thinking guide says "do not set it"). The UI hides the temp widgets for ALL Kimi models and `_kimi_model_params()` never emits it. `_get_model_param_summary` shows `reasoning=X` (k3), `thinking=on/off` (k2.6/k2.5), or `thinking=always-on` (k2.7-code).
4. **No server-side tools** — Kimi keeps the local DuckDuckGo `web_search`/`fetch_webpage` (the Gemini pattern); `_get_tools()` does not strip them. Tokens are the only cost.
5. **Exact cost via cache-hit folding** — usage arrives on the final stream chunk (`stream_options {"include_usage": true}`); `_kimi_usage_dict` probes cached-input tokens under the three names in the wild (`prompt_tokens_details.cached_tokens`, flat `cached_tokens`, DeepSeek-style `prompt_cache_hit_tokens`) and computes `cost_usd = (input−cached)·miss + cached·hit + output·out` from `KIMI_PRICING` + `KIMI_CACHE_HIT_PRICING` (hit input is ~1/6 the miss rate — which is what keeps the mandatory reasoning re-send cheap). stream_worker prefers `cost_usd` over the all-miss 2-tuple estimate. Documented in `MyAgent_Pricing.txt`.
6. **Model fetch + filtering** — `_fetch_kimi_models()` lists `/v1/models`, keeps ids starting `kimi-k`, and drops the discontinued DASH family `kimi-k2-*` (kimi-k2-thinking etc., EOL 2026-05-25 — the current K2 generation uses DOTS: kimi-k2.5/k2.6/k2.7-code); `moonshot-v1*` (EOL 2026-08-31), `kimi-latest`, and `kimi-thinking-preview` fall out of the prefix rule. Fallback `KIMI_FALLBACK_MODELS` matches the live catalog 1:1 (verified 2026-07-25 with a real key: kimi-k2.6 / k3 / k2.7-code / k2.7-code-highspeed — **kimi-k2.5 is documented+priced but NOT served**, at least to new accounts; its pricing/no-round-trip entries are retained in case it returns). Default kimi-k2.6 — the 256K vision agentic tier at $0.95/$4. `KIMI_NON_VISION_PREFIXES` (`kimi-k2.7-code`, text-only) drives the weak-desktop-combo warning.
7. **Retry ladder + streaming hygiene** — same skeleton as xAI: raw chunk iteration, first-content timeout (180s) with a waiting ticker, `AuthenticationError` → clear "check MOONSHOT_API_KEY" message, RateLimit/5xx backoff via `retry_util`, STOP checked per chunk, `finish_reason=length` surfaces a truncation warning. The BadRequest ladder rungs (each `continue`s): drop `reasoning_effort` → strip reasoning round-trip (learn-once) → drop `thinking.keep` then the whole `thinking` param → swap `max_completion_tokens`→`max_tokens`. Detection helpers + translators + params are characterization-tested in `tests/test_kimi_detect.py`; pricing in `tests/test_pricing.py`.
8. **Live-verified end-to-end 2026-07-25** — a real kimi-k2.6 streaming run (thinking enabled+keep=all, tool declared) confirmed the wire shapes `_stream_kimi_events` relies on: `delta.reasoning_content` streams before content, tool calls accumulate via `delta.tool_calls` (ids look like `get_time_0` — name-based, not `call_*`), `finish_reason` lands `tool_calls`/`stop`, and usage arrives in the final chunk (`prompt_tokens`/`completion_tokens` + `completion_tokens_details.reasoning_tokens`; `prompt_tokens_details` was null on small calls, so the cache probe's fallbacks matter). A second call with `reasoning_content` round-tripped on the assistant message + a `role:"tool"` result was ACCEPTED and answered correctly — the Preserved-Thinking contract works as wired.

**Temperature/thinking UI visibility** — Model parameter controls are dynamically shown/hidden (not just disabled) based on the selected model's capabilities. `_forget_all_model_widgets()` resets all widgets at the start of `_on_model_selected()` to guarantee correct pack order when switching model types. Rules:
- Models without thinking support hide the thinking checkbox + strength combo, showing only temperature (or just verbosity for `gpt-5.x-chat-*` Instant models, which reject temperature).
- OpenAI reasoning models hide temperature entirely.
- Anthropic adaptive models replace checkbox+strength with a **Thinking mode combobox** whose values are built per-model by `_anthropic_mode_values()`: Off/Adaptive/Low/Medium/High, plus Xhigh (Opus 4.7+, Sonnet 5+, Fable/Mythos 5) and Max (Opus 4.6+, Sonnet 4.6+, Fable/Mythos 5); temperature is hidden when thinking is active. The per-family gates were verified live 2026-07 against the Models API capability tree (`m.capabilities["effort"]`); minor-less Claude 5 ids parse as `(major, 0)` in `_parse_claude_major_minor`, so `claude-sonnet-5` hits the `claude-sonnet- >= (5, 0)` rules without a hardcoded list.
- **Claude Opus 5 (`claude-opus-5`) and Claude Sonnet 5 (`claude-sonnet-5`)** are adaptive-only (`budget_tokens` is HTTP 400), reject non-default temperature (`_anthropic_rejects_temperature` covers opus >= 4.7 and sonnet >= 5.0), support effort up to Xhigh/Max, and — unlike the 4.x generation — **run ADAPTIVE thinking when the `thinking` param is omitted**. `_anthropic_thinking_on_by_default()` detects both families (opus/sonnet >= 5.0), and `_stream_anthropic_call`'s off-branch sends an explicit `thinking={"type": "disabled"}` for them so "Off" really is off (otherwise the model silently thinks against the non-thinking 8K max_tokens cap with the Show Thinking pane dark; Opus 5 accepts the explicit disable only at effort ≤ high — satisfied, since "Off" sends no effort). Opus 5 is the picker default (`FALLBACK_MODELS[0]`), priced like Opus 4.8 ($5/$25). The Anthropic picker also filters `ANTHROPIC_DEPRECATED_MODEL_PREFIXES` (Opus 4.1 — retires 2026-08-05 — the 4.0 ids, Claude 3.x/2.x) out of the live `models.list()`, the same filter SelfBot has carried; pinned instructions can still run a hidden id until Anthropic shuts it down. Pricing is in `ANTHROPIC_PRICING` at the launch intro rate ($2/$10 per MTok through 2026-08-31 — flip to $3/$15 from September).
- **Claude 5 Mythos-class models (`claude-fable-5`/`claude-mythos-5`, matched by `ALWAYS_ON_THINKING_PREFIXES`) have always-on thinking** — an explicit disable or `budget_tokens` is HTTP 400. The combo drops "Off" (a stale saved "Off" coerces to Adaptive; headless runs, which skip the UI coercion, get the same override inside `_stream_anthropic_call`), temperature is never sent (`_anthropic_rejects_temperature` covers them alongside Opus 4.7+), and pricing ($10/$50 per MTok) is in `ANTHROPIC_PRICING`. Adaptive thinking is sent as `{"type": "adaptive", "display": "summarized"}` so the Show Thinking pane gets readable text on Fable 5 / Opus 4.7+, whose API default became "omitted" (empty thinking deltas); 4.6 already summarizes, so the field is a no-op there. Fable 5 safety classifiers can end a call with `stop_reason="refusal"` (HTTP 200, possibly empty content) — `_stream_anthropic_call` surfaces it as a ⚠ warning with the `stop_details` category/explanation instead of letting the run end silently.
- Google (Gemini) shows temperature alongside thinking controls (the API accepts both).
- GPT-5.1+ use a **Reasoning combobox** (None/Low/Medium/High; Xhigh for gpt-5.2+/codex-max, but mini/nano cap at High). GPT-5.4+ show temperature when reasoning is "None"; older gpt-5 keep it hidden. GPT-5.0 base adds "minimal".
- Moonshot hides temperature for EVERY Kimi model (fixed server-side). kimi-k3 gets the Reasoning combobox (Low/High/Max, stale values coerce to Max); kimi-k2.6/k2.5 get the plain Thinking checkbox with the strength combo hidden (Ollama-style boolean toggle); kimi-k2.7-code shows no thinking controls at all (always-on server-side, reasoning still streams to the pane).
- All gpt-5 (incl. `-chat`) show a **Verbosity combobox** (Low/Medium/High → `text.verbosity`).

The Thinking/Reasoning label and its dropdown are always packed adjacently; `_on_thinking_toggled()` delegates to `_on_model_selected()` to maintain pack order. Detection helpers: `_parse_gpt5_minor()`, `_is_gpt5_family()`, `_is_gpt5_chat_model()`, `_has_reasoning_none()`, `_has_reasoning_xhigh()`, `_has_openai_verbosity()`, `_gpt5_supports_temp_at_none()`.

**Agentic loop** — `stream_worker()` runs a `while True:` loop: dispatches to `_stream_anthropic_call()`/`_stream_responses_call()`/`_stream_gemini_call()` by provider, streams the response, executes tool calls, appends results, loops. Exits on `end_turn` or when `stop_requested` is set via STOP. No fixed iteration limit.

**Tool system** — Five static lists (`TOOLS`, `FILE_TOOLS`, `DESKTOP_TOOLS`, `BROWSER_TOOLS`, `META_TOOLS`) plus dynamic `MCP_TOOLS` in `constants.py`, assembled by `_get_tools()` in `streaming_mixin.py`. `TOOLS` and `FILE_TOOLS` are always included; the rest are gated by their checkboxes. Dispatch is in `_execute_tool()`. `find_element` is provider-gated — `_get_tools()` strips it for every provider but Google (it uses Gemini's native pointing API). Adding a static tool requires: (1) schema dict in the right list in `constants.py`, (2) `elif` branch in `_execute_tool()`, (3) `do_<name>()` in the appropriate mixin, and optionally (4) adding the name to `PARALLEL_SAFE_TOOLS` if thread-safe and stateless. MCP tools are added at runtime — see below.

**MCP integration** — `myagent/mcp_mixin.py` connects to Model Context Protocol servers (filesystem, GitHub, Slack, etc.) at startup, enumerates each server's tools via the `mcp` Python SDK, and exposes them through the same `_get_tools()`/`_execute_tool()` pipeline as native tools. Architecture invariants:
1. **Async-only SDK** — `MCPMixin` runs a dedicated asyncio loop in a background thread (`self._mcp_thread`); the sync streaming worker calls in via `asyncio.run_coroutine_threadsafe`.
2. **One `AsyncExitStack`, one long-lived runner** — all server connections live in a single stack owned by `_mcp_runner`, which connects, lists tools, then parks on `self._mcp_shutdown_event` for the whole session. Required because anyio binds task-group cancel scopes to the originating task: splitting the lifecycle across multiple `run_coroutine_threadsafe` calls would kill the stdio pumps and surface as `Connection closed` on the next `list_tools`. Shutdown signals the runner; the stack unwinds sessions/stdio_clients LIFO and subprocesses exit. A post-unwind `gc.collect()` + two `await asyncio.sleep(0)` cycles drain pending pipe-close callbacks to avoid harmless `Event loop is closed` finalizer tracebacks.
3. **Namespaced tool names `<server>__<tool>`** (double underscore — valid for all four providers' regexes); `_execute_tool` looks up `block.name` in `self._mcp_tools_by_name` and routes to `do_mcp_call` before the static dispatch chain.
4. **Per-user config** in `mcp_servers.json` (root), same shape as Claude Desktop / Cursor, so community servers drop in unchanged. `${NAME}` placeholders in `env` values are substituted at spawn time by `_substitute_placeholders`: `${RANDOM_PORT}` is reserved (each occurrence → an independent OS-assigned free port; does not consult `os.environ`), any other `${NAME}` → `os.environ[NAME]` (or empty + a one-shot warning). Substitution is scoped to user-typed `spec["env"]` keys only — not the ambient env, not `command`/`args` (so secrets don't leak via process listings). This keeps `mcp_servers.json` secret-free and safe to track.
5. **Graceful degradation** — without `mcp` installed, `_HAS_MCP` is False, the checkbox is disabled, and every method is a no-op.
6. **Deferred connect** via `root.after(100, self._connect_mcp_servers)` so a slow handshake never blocks launch; per-server failures are logged, not fatal.

9. **Reconnect-on-close** — if `list_tools` raises `ClosedResourceError`/`Connection closed`, `_list_tools_for_server` opens a fresh session via `_open_server_session`, swaps it into `_mcp_sessions[name]`, and retries. Belt-and-braces; (8) is the real fix and this rarely fires.

**Proton Mail integration** — `myagent/protonmail_mixin.py` adds native multi-account Proton tools via Proton Bridge over stdlib IMAP+SMTP — NOT MCP and NOT a REST API (Proton publishes none; E2E encryption means decryption is client-side, so Bridge is the official integration path). A foundational footgun of flat-namespace mixins — defensively prefix non-shared helpers.

   - (a) **SUBJECT search** is reliable for single-word substrings but fragile for multi-word substrings against non-ASCII subjects (curly quotes, em-dashes, accented letters); the `proton_search` description steers toward single words, and `_uid_search` switches to `CHARSET UTF-8` byte-literals for non-ASCII queries.

   - (c) **Label removal can leave a transient new UID** in the source (Bridge↔Proton eventual consistency); `do_proton_modify_labels` snapshots source UIDs, detects strays after the MOVE, and re-MOVEs them up to 2×, reporting `label_removal_retries: N` (0 = clean).

The description steers toward the explicit-key form (`SUBJECT`/`BODY`/`TEXT`/`FROM`/`TO "..."`), which works on both.

**Native file tools** — `myagent/file_mixin.py` (mixin #21) adds five always-available tools (`read_file`/`edit_file`/`write_file`/`glob_files`/`grep_files`) via `FILE_TOOLS`, modeled on Claude Code's tool contracts — the reliable-editing surface for coding tasks, replacing PowerShell round-trips (PS 5.1 `Set-Content` defaults to the ANSI codepage, here-strings mangle `$`/backticks, CRLF is invisible in tool output). Architecture invariants:
1. **Fail-loud editing** — `edit_file` requires an exact `old_string` match that is UNIQUE in the file: zero matches, or several without `replace_all=true`, returns a retryable error naming the problem — never a guess applied to the wrong place. 2. **Read-before-edit tracking** — `self._file_read_paths` (lazy init in `_file_reads()`, process-lifetime — matching the fire-and-forget one-run-per-process pattern) gates `edit_file` and `write_file`-over-existing: the model must have `read_file`'d the file first, so edits are grounded in actual content, not a stale imagination of it.
3. **Byte-exact round-trips** — all IO uses `encoding="utf-8", newline=""` so `\r\n` stays literal in the string; `_file_apply_edit` retries an LF-normalized `old_string` expanded to CRLF (only when the file is CRLF and `old_string` carries no `\r` of its own); a leading BOM decodes to U+FEFF and re-encodes unchanged. **Click accuracy pipeline** — Desktop click invariants, refined for cross-provider accuracy:
- All providers receive **pixel coordinates** (no [0, 1000] normalization) — what the model reads in the image is what it passes to `mouse_click`. The old Gemini [0, 1000] convention caused ~1-pixel drift and broke entirely under multi-monitor mixed-DPI.
- `do_mouse_click`/`_scroll`/`_drag`/`_read_screen_text` use `round(float(x))` (not `int(x)`) to avoid truncation bias.
- A pre-screenshot guard refuses click/scroll/drag/OCR with "Take a screenshot first" when `_screenshot_dims == (0, 0)`.
- Tiered out-of-bounds policy: ≤2px overflow clamps silently; >2% of the dimension refuses with a "re-take a screenshot" message; in between clamps with a `⚠ clamped` warning.
- A 50ms `time.sleep` after `pyautogui.click` lets the UI settle before the next screenshot.
- The `_capture_single_display` region branch snapshots `entry_scale`/`entry_offset` at entry so chained region screenshots don't drift through stacked offsets.

**Per-display state tracking** — Multi-display coordinate state lives in two parallel dict pairs:
- `_display_states[N]`/`_display_images[N]` — the **most recent capture** (full or region) for display N. Used by `mouse_click`, `find_element`, and any `display=N` tool.
- `_display_full_states[N]`/`_display_full_images[N]` — the **most recent FULL capture** for display N, never overwritten by region captures. Region screenshots (`screenshot(display=1, x, y, width, height)`) interpret their coordinates in this full-image space, not relative to the last capture — without this two-slot split, chained region screenshots drift through stacked offsets.

`_resolve_coord_state(display)` is the shared lookup: returns `_display_states[display]` if a `display` param is given, else the current `_screenshot_scale/offset/dims`. `mouse_click`, `mouse_scroll`, `mouse_drag`, `read_screen_text`, and `find_element` all accept an optional `display` so the model can disambiguate screens without re-screenshotting.

**Image resolution caps per provider** — `_capture_single_display` resizes to each API's actual limit:
- **Anthropic**: `1568` long edge / `1.15 MP` — the API silently downscales to this anyway.
- **OpenAI**: `2048` long edge / `5 MP` — verified the API silently downscales above 2048 (gpt-5.2 reported `PIL.Image.size == (2048, 1152)`), so 2048 keeps `_screenshot_scale` matching what the model sees.
- **Gemini**: `2048` long edge / `4 MP` — higher than Anthropic's because Gemini's 768×768 tile system gives small UI elements more pixel density.

**find_element tool (Gemini-only)** — Uses Gemini's native spatial pointing API to locate UI elements by description. `gemini_mixin.py:do_gemini_find_element` uses Google's *exact* documented prompt (`"Point to the X. The answer should follow the json format: [{\"point\": <point>, \"label\": <label1>}, ...]. The points are in [y, x] format normalized to 0-1000."`) — the trained pointing capability only fires on this phrasing. Parses both the array shape and a single-object fallback. Takes an optional `display` so the cached-image lookup hits the right screen (`_display_images[display]`). Returns pixel coordinates (converted from [0, 1000]) and names the exact `mouse_click` to make. Stripped from `_get_tools()` for every provider but Google.

**Grid overlay** — `do_screenshot` accepts optional `grid=true`; `_capture_single_display` then calls `_draw_coord_grid(img)` after the API-limit resize (so labels match what the model sees), drawing 100px magenta gridlines with `(x,y)` labels at intersections (skipping (0,0)). Opt-in / default-off so it doesn't obscure small text; the tool description nudges its use for small/dense UI.

**Diag checkbox** — `Diag` (next to `Save Thinking`) gates `[DIAG capture]`/`[DIAG click]` activity lines showing the full coordinate-mapping trail (display rects, physical/logical/sent-to-model dims, scale, offset, raw input, computed screen pixels). Persisted as `diag_enabled`. Independent of `Debug` (which controls API JSON payload display). Defaults on.

**Code interpreter gating (OpenAI)** — `_stream_responses_call` and `_payload_for_display` skip `code_interpreter` when desktop tools are on (`self.desktop_enabled.get() and _HAS_DESKTOP`). With CI access, gpt-5.2 loads screenshot bytes via PIL, sees the API-resized dimensions, and pre-scales coordinates itself — colliding with our scaling and producing double-scaled clicks. Stripping CI forces direct visual perception. CI stays available for non-desktop OpenAI tasks (data analysis, file processing, etc.).

**OpenAI tool rejection cache** — Newer models can reject server-side tools with HTTP 400 (e.g. `gpt-5.2-pro` rejects `code_interpreter`). `_stream_responses_call`'s `BadRequestError` handler regex-extracts the tool name from the message, adds it to `self._openai_unsupported_tools[model_id]`, strips it, and retries once — caching so later calls in the session skip it upfront. Same pattern as the temperature retry.

**Weak desktop combo warning** — `_weak_desktop_combo_warning()` (streaming_mixin) returns a warning string for weak-click-precision provider/models: gpt-5 at reasoning none/minimal, gpt-5 `-chat` Instant variants, any `gemini-2.x`. `stream_worker` posts it as `⚠ ...` at agent start. Informational only — doesn't change behaviour or override the model. Anthropic, gpt-4, gpt-5 ≥ low, and gemini-3.x pass clean.

**Parallel tool execution** — When the model requests multiple tools in one turn, blocks are partitioned into parallel-safe (`web_search`, `fetch_webpage`, `csv_search`, `get_skill`, `read_document`, `read_file`, `glob_files`, `grep_files`, `run_instruction`) and sequential (everything else). Parallel-safe run concurrently via `concurrent.futures.ThreadPoolExecutor`; sequential run one at a time in order. Results go into a pre-allocated list indexed by original position, preserving API-expected ordering. `run_instruction`'s membership (2026-07-22) is what enables **parallel waited children**: each spawn is an independent child process and a waited call blocks only its own executor thread, so several `run_instruction` calls in ONE assistant turn become concurrently-running waited subagents — total wait is the slowest child, not the sum (safety plumbing in the Meta-agent tools block below).

**Conversational mode** — Per-instruction `conversational` toggle (Convo checkbox) enforcing a chatbot loop: when the model ends a turn without calling `user_prompt` and the toggle is on, `stream_worker` invokes `do_user_prompt` directly, appends the reply as a regular user message, and continues. Empty/`quit`/`exit`/`stop` ends cleanly. Unlike the 2+-calls "established pattern" nudge (which coaxes the model back to self-driven `user_prompt`), this bypasses model compliance entirely — for smaller open-weights models (Qwen3, Llama, gpt-oss) that don't follow the meta-rule. Default off so one-shot tasks exit normally.

**Shared-store sync (`myagent/datapaths.py`)** — the authored-content stores (`agent_instructions.json`, `skills.json`, and SelfBot's `system_prompts.json`) resolve to **`<OneDrive>/MyAppShare/`** when a OneDrive client is present (`MYAGENT_DATA_DIR` env override; repo-root fallback on solo machines) — OneDrive, not git, syncs them across machines, mirroring TodoList's todos.json move. (Named `MyAgent` until 2026-07-19: `_shared_dir` adopts a legacy dir via in-place `os.rename` — synced as a cheap rename, no re-upload — and if the rename fails it keeps serving the legacy dir for the session rather than an empty new-name store, retrying next launch.) `constants.py` resolves `INSTRUCTIONS_FILE`/`SKILLS_FILE` through `resolve_store()` at import (path decision + mkdir only); `load_store()` runs the **one-shot migration** lazily (a leftover repo-root copy is seeded or key-level-unioned into the shared file — shared entries win their names, a differing local entry survives as `name__<hostname>` — then renamed `*.migrated.bak` so deletions can't resurrect); `save_store()` is atomic via unique `mkstemp`+`os.replace` (SelfBot and MyAgent can save skills.json concurrently) and re-`makedirs` the parent (OneDrive GCs a still-empty shared dir). `_load_skills`/`_load_saved_instructions` also call `absorb_conflict_forks()` — OneDrive's `<stem>-<Computer>.json` concurrent-write forks are unioned back in and deleted, so a sync race costs nothing (conflicting entries surface as `name__label` for reconciling in the UI). Structurally unit-tested in `tests/test_datapaths.py`.

**Agent Instructions** — Stored in `agent_instructions.json` as `{name: {text, images: [{data, media_type, filename}], desktop, browser, meta, mcp, conversational, provider, model, temperature, thinking_enabled, thinking_effort, thinking_budget, thinking_mode, text_verbosity, skill_modes: {name: mode}, disabled_confirm_patterns: [str], blocked_tools: [str]}}`. The button label shows a count when patterns are bypassed (e.g. `PS Safety (3 bypassed)`).

**run_command timeout + process-tree kill** — `run_command` accepts an optional `timeout` (clamped 5–600 s in `_execute_tool`, default 30) passed through to `run_powershell(command, timeout)`. Execution is Popen-based (not `subprocess.run`): on expiry `_kill_process_tree` kills the ENTIRE tree — `taskkill /T /F` on Windows, `killpg` on POSIX (the child is started with `start_new_session=True` so the group is its own) — then a second `communicate(timeout=10)` salvages partial output and the tool returns a "timed out after N seconds … re-run with a larger 'timeout'" error instead of hanging. Root cause (2026-07-23, first cold MSVC build via the `Coding_Agent_CodingAgent_WIN_Laptop` instruction): `subprocess.run(timeout=30)` kills only the direct child, and CPython's post-kill `communicate()` blocks until every holder of the inherited stdout/stderr pipes exits — a nested `powershell -File` → `cmd` → `cl.exe` chain survived the kill and wedged the agent thread indefinitely. Characterization-tested in `tests/test_run_command_timeout.py` (simple timeout, grandchild-holding-pipes returns promptly, fast command unaffected). SelfBot carries the same fix in-file (see CLAUDE_SELFBOT.md).

**Per-instruction hard tool blocklist (`blocked_tools`)** — the deterministic guarantee for unattended runs, added 2026-07-22 after assessing (and rejecting) a general hooks system: a per-instruction `blocked_tools: [str]` list enforced at TWO layers. Layer 1: `_get_tools()` strips blocked names from the fully assembled list (`_filter_blocked_tools`, applied after MCP/mail assembly so namespaced tools are coverable) — the model never sees the tool. Layer 2: a first-position gate in `_execute_tool` (ahead of ALL routing — MCP, mail prefixes, static chain) refuses any blocked call with a firm "HARD-BLOCKED … do not attempt it again" result plus an always-shown ⚠ warning — the backstop for hallucinated or stale tool_use. Rationale vs the alternatives: prompt directives are probabilistic (the 2026-06-08 over-trash incident) and confirm dialogs are unanswerable in unattended runs, so bypassed there; `blocked_tools` holds regardless of model compliance. Live-verified 2026-07-22: an instruction with `blocked_tools=["run_command"]` explicitly told to run a command produced ZERO tool_use blocks and honestly reported `BLOCKED:` — first attempt also demonstrated the test-oracle trap: with no honest "I couldn't" exit, sonnet-5 *fabricated* `TOOL_SAID: hello` (transcript proved nothing executed; verify blocklist tests from transcripts, not model self-report). Scope caveat: Anthropic/OpenAI/xAI **server-side** tools (web_search, code_execution — appended after `_get_tools()`, executed in the provider's sandbox, not on this machine) are NOT covered; the live run confirmed the model still saw `bash_code_execution`. Persisted per-instruction (all `disabled_confirm_patterns` sites mirrored: editor save/load/clear, `_apply_instruction_entry`, agent_state `applied_instruction` snapshot, `manage_instructions` read/create/update — update replaces the whole list). No dedicated UI dialog (edit via `manage_instructions` or the store). **Scoping lesson (2026-07-22 near-miss):** the blocklist was first applied to `Email_AllUnreadSummary_*` with the three mail `*_trash` tools — then REVERTED on reading the instruction text: those instructions *legitimately* trash the 8 SPECIFYING-LIST bill/receipt types during the SPECIFYING step, and a name-level block cannot distinguish that scoped use from the runaway over-trash it was meant to prevent (it would have silently broken bill-trashing on every scheduled run). `blocked_tools` is for tools an instruction NEVER needs — their over-trash guard remains the load-bearing `*** SAFETY (READ-ONLY)` prompt directive ([[email-summary-overtrash-guard]] semantics, holding since 2026-06-08). Unit-tested in `tests/test_blocked_tools.py` (strip semantics, gate-before-all-routing on a bare host).

**Command-line launch** — `python MyAgent.py -l "Name"` auto-loads a saved instruction and starts the agent (`argparse` `-l`/`--load`). `_auto_launch()` is scheduled via `root.after(100)` (UI ready), then `_start_agent` via `root.after(200)` (one event-loop cycle between state setup and start). Unknown names show an error dialog listing the available ones. `-l` also auto-fills "Save Chat as" with `"{Name}_{timestamp}"` so output is captured.

**Headless mode** — `--headless` runs without a main window (`root.withdraw()`); dialogs skip `transient()`/`grab_set()` so they float standalone. The process auto-closes after the loop completes — as does a GUI run launched with `--result-file` (a `headless=false` waited child is still a subagent: it auto-closes at loop end so the waiting parent gets the report immediately, instead of only when the user closes the child window or the wait times out; interactively-launched GUI sessions, which have no result file, stay open as always). For orchestrator patterns where a parent spawns child instances via `run_command` or `run_instruction`. `--result-file PATH` makes `stream_worker` write a JSON outcome summary (`{instruction, status: completed|stopped|error, error, final_text}`) when the loop ends — the return channel behind `run_instruction(wait=true)`, also usable directly by external scripts that need a MyAgent run's answer. `--extra-file PATH` appends the file's UTF-8 text to the `-l` instruction as an ADDITIONAL TASK CONTEXT block for that run only — the input half of the same channel (`run_instruction`'s `extra_text`), equally usable by scripts to parameterize a scheduled instruction per run.

**Meta-agent tools** — Three tools in `META_TOOLS` (gated by the Meta checkbox). Two CRUD tools (`manage_instructions`, `manage_skills`) use one `action` param (`list`/`read`/`create`/`update`/`delete`) to keep the tool count low. `manage_instructions` create inherits the current provider/model/thinking settings; `read` returns all model params; `update` accepts them as optional fields alongside text/desktop/browser/meta/skill_modes. `manage_skills` updates the in-memory dict and refreshes the UI thread-safely via `_post_skill_ui_refresh()`. `run_instruction` launches a saved instruction as a separate process (`subprocess.Popen` + `sys.executable`), headless by default (`headless=false` to show the GUI) — fire-and-forget by default, or **`wait=true` for true subagents**: the parent's streaming thread blocks (polling 1 s so STOP stays responsive, `timeout_seconds` default 600 → terminate + error), the child is launched with `--result-file <mkstemp path>`, and on child exit the parent reads the JSON `{instruction, status, error, final_text}` the child's `stream_worker` wrote at loop end (`_write_result_file`, both success and exception paths, before the headless close — process exit is the synchronization point) and returns `final_text` (capped 20 000 chars) as the tool result. `_final_assistant_text` extracts the last assistant text from str/dict/SDK-object content. **`extra_text`** parameterizes a spawn: the parent writes it to a `myagent_extra_*.txt` mkstemp file and passes `--extra-file` (file transport, NOT argv — Windows newline/length hazards — and NOT env — an inherited var would leak this parent's addendum into any grandchild); the child reads it once in `__init__` and `_auto_launch` appends it to the instruction text via `_merge_extra_text` under an "ADDITIONAL TASK CONTEXT (for this run only…)" separator — the saved instruction on disk is untouched. Waited runs delete both temp files in the `finally`; a fire-and-forget child's extra file stays in `%TEMP%` (the child must still read it after the parent's tool returns). Live-verified 2026-07-22 (both features): a parent passed `extra_text` to a generic child, the child's transcript carried the injected block verbatim, and the parent relayed the child's parameterized report back. `manage_instructions`/`manage_skills` stay sequential (they mutate shared state), but **`run_instruction` is PARALLEL_SAFE** (2026-07-22 — the parallel-waited-children capability): several calls in one assistant turn run concurrently on stream_worker's executor, waited children overlap, and each wait loop independently honors STOP and its own `timeout_seconds`. Two pieces make it safe: (a) **`_SPAWN_LOCK`** (module lock in skills_mixin) serializes only the prologue — the store existence-check (`_load_saved_instructions` absorbs OneDrive conflict forks, a disk mutation) through the `Popen` — while the waited poll loop runs unlocked so children genuinely overlap; (b) **`_claim_instance_number` claims slots atomically** (`O_CREAT|O_EXCL`, PID written on the raw fd immediately), so simultaneously-launching children get distinct instance numbers / `agent_state_N.json` files. The claim protocol also covers the reclaim races: an *unreadable* lock younger than 5 s is treated as a mid-claim sibling (not stale); a judged-stale lock is removed by `_reclaim_stale_lock` under a per-slot **mutex directory** (`<lock>.reclaim` — os.mkdir is atomic on both OSes) with the content re-validated INSIDE the mutex, so only the exact file generation that was judged stale can ever be removed. A bare check-then-remove was itself a TOCTOU (os.remove is path-based and cannot tell inode generations apart: a reclaimer descheduled between its re-read and its remove deleted a sibling's FRESH replacement lock and both returned the same slot; the earlier "conditional remove + verify-after-write" only protected a claimant whose lock was clobbered *before* its verify — the storm test failed 4-in-5 on macOS until the mutex fix, 2026-07-23). A crashed reclaimer's leftover mutex is cleared once older than 10 s; after winning the O_EXCL create the claimant still re-reads to verify ownership (belt-and-braces). Unit-tested in `tests/test_parallel_children.py`: PARALLEL_SAFE membership (manage_* excluded), two mocked-Popen waited children overlapping with per-spawn result isolation, an 8-thread barrier race for slots, and a stale-reclaim storm. The tool description teaches the fan-out pattern (issue all spawns in one turn, each with its own extra_text/timeout). Meta toggle saved per-instruction.

**State persistence** — `agent_state.json` stores provider, last instruction, model, temperature, thinking settings (incl. `thinking_mode`), `text_verbosity`, display checkbox states (debug, tool calls, activity, show/save thinking), and a `geometries` dict keyed by monitor configuration. Each monitor-config key (from `_get_monitor_config_key()` — Win32 `EnumDisplayMonitors` / macOS CoreGraphics `CGGetActiveDisplayList`) maps to a set of window/dialog geometries (main, editor, prompt, confirm, PS Safety, Skills Manager), so docked/undocked or different arrangements restore correctly. Periodic auto-save every 5s captures live geometry from open dialogs; geometries also flush immediately on dialog close. On restore, `_sanitize_geometry()` validates against the full virtual-desktop bounds (`_get_virtual_screen_bounds()`) and resets windows that are too small (<200×150) or fully off-screen. Old flat-geometry state files are migrated to the per-config format on first load. (Disabled confirm patterns live per-instruction in `agent_instructions.json`, not here. Skill modes are likewise NOT stored here: `skills.json` is their single sticky source of truth, loaded by `_load_skills()`; the `applied_instruction` snapshot deliberately omits `skill_modes` so a relaunch cannot overwrite the user's global modes.)

**Dialog geometry pattern** — All dialogs use a withdraw/deiconify sequence so `transient(parent)` can't override saved positions: `withdraw()` → build content → `update_idletasks()` → set geometry → `deiconify()`. PS Safety re-applies geometry via `after(100ms)` because its checkbutton widgets request a large natural size that can override saved dims on map. On macOS, `transient(parent)` is skipped entirely (its WM confines transients to the parent's screen, blocking secondary-monitor placement); on Windows it works cross-screen and is kept. Dialog refs (`_ps_safety_dialog`/`_confirm_dialog`/`_prompt_dialog`) live on `self` so the auto-save can read live geometry; closing the editor captures the PS Safety geometry before the destroy cascade.

**LaTeX to Unicode conversion** — Assistant text is converted to Unicode after each streaming segment via `_post_process_latex()`, which walks `tag_ranges("assistant")` and applies `_latex_to_unicode()` only to assistant-tagged text (so tool_info filenames/paths aren't mangled). The static converter handles all delimiters (`\( \)`, `$ $`, `\[ \]`, `$$ $$`), *braced* super/subscripts only (`^{...}`/`_{...}` — bare `^x`/`_x` left alone to avoid filename false positives), Greek letters, operators, `\frac{a}{b}`→`a/b`, functions, arrows, set notation, with unrecognised `\command` patterns falling back to backslash-strip. A `post_process_latex` queue message fires after each provider call returns text, and during `complete`.

**Server-side tools** — OpenAI and Anthropic use server-side web search and code execution instead of the local DuckDuckGo `web_search`/`fetch_webpage` tools. OpenAI appends `web_search_preview` + `code_interpreter` (`container: auto`, `include: ["code_interpreter_call.outputs"]`) — but CI is gated off when desktop is on (above). Anthropic appends `web_search_20250305` + `code_execution_20250825` via `client.beta.messages.stream()` with the matching betas + `files-api-2025-04-14`; code-execution file outputs are extracted from `final_message.content` post-stream (file IDs aren't available mid-stream) and downloaded via `client.beta.files.download()`. Gemini can't combine built-in tools (`google_search`, `code_execution`) with custom function declarations (API restriction), so it keeps local DuckDuckGo search. xAI CAN mix (verified live 2026-07-05) and appends server-side `web_search` + `x_search` (+ `code_interpreter`, desktop-gated) at $0.005 per invocation — see the xAI integration block. Moonshot (Kimi) uses no server-side tools and keeps local DuckDuckGo search (the Gemini pattern). Code-execution file outputs from both are sniffed with PIL: images are shown inline (max 600px) and saved to `saved_chats/` as PNG; non-image files (exported reports, CSVs, ...) are saved to `saved_chats/` as `ci_output_{ts}_{filename}` with a `[File saved: …]` notice instead of a PIL "cannot identify image file" error — the original filename comes from the provider's file metadata (Anthropic `beta.files.retrieve_metadata`, OpenAI `files.retrieve`), falling back to a utf-8 sniff (`output.txt`/`output.bin`).

**Multi-display desktop tools** — On macOS `pyautogui.screenshot()` only grabs the primary display, so `_macos_display_screenshot()` uses Quartz `CGWindowListCreateImage` with a per-display `CGRect`; on Windows, `ImageGrab.grab(bbox=..., all_screens=True)` via `_get_windows_display_rects()` (EnumDisplayMonitors). Both index the primary (origin 0,0) as display 0. The `screenshot` tool's `display` param: omit it to capture ALL displays as separate images (the recommended first step, stated explicitly in the schema), or pass a number for one. For OpenAI/Google/Moonshot, screenshot images are delivered as separate user messages (not embedded in tool outputs) with coordinate-system hints. Region screenshots interpret (x, y, width, height) relative to display N's FULL image (`_display_full_states[N]`), capture, then store the result in `_display_states[N]` for subsequent clicks. The result text tells the model to "use pixel coordinates AS YOU READ THEM... Do NOT scale or convert" to stop it pre-converting after inspecting dimensions via code_interpreter (see CI gating).

**Chat saving is opt-in** — Chats save (on close or via the periodic auto-save) only if a name is typed in "Save Chat as"; blank → no file is created.

**Multi-instance support** — Multiple instances run at once; each claims the lowest free number via lock files (`agent_lock_N.lock` holding the PID). Instance 1 uses `agent_state.json`, 2+ use `agent_state_N.json` for independent persistence. Stale locks (crashed PIDs) are detected via `OpenProcess` + executable-name verification (`GetModuleBaseNameW` confirms `python.exe`/`pythonw.exe`, guarding against recycled PIDs) and reclaimed. The title bar shows `My Agent (N)` for 2+. Locks are cleaned up on graceful close.

**API retry logic** — Same as SelfBot: up to 10 retries, exponential backoff capped at 60s (429) / 90s (529). OpenAI also catches `APITimeoutError` (retry without backoff). A 180s first-content timeout cancels a stream that produces no visible output (thinking/text/tool calls); a background ticker posts elapsed time every 15s while waiting. OpenAI models that reject `temperature` retry without it; those that reject server-side tools are handled by the rejection cache (above). All providers break out of the loop immediately on success.

**Context-overflow compaction (Anthropic)** — a long agentic run can exceed the context window mid-task; the API returns 400 `prompt is too long: <T> tokens > <M> maximum`, which is not retryable as-is. `_stream_anthropic_call`'s BadRequestError handler now recovers instead of surrendering: `parse_overflow_counts` + `trim_history_for_context` (pure functions in `myagent/helpers.py`, ported 1:1 from SelfBot's sliding-window recovery) drop the oldest conversation rounds **in place** — cutting only at genuine user-turn boundaries so a `tool_use`/`tool_result` pair is never orphaned, sizing the cut to 0.75·M from the reported counts (oldest-half fallback), always keeping the last two rounds — then post a red ⚠ warning and `continue` the retry loop (`api_kwargs["messages"]` is the same list object, so the retry sends the shorter prompt and the trim persists into `stream_worker`'s ongoing loop). When even the last two rounds overflow (`removed == 0`), the pre-existing graceful exit fires: an actionable error naming 1M-context models, `end_turn` instead of a crash. Structurally unit-tested in `tests/test_context_trim.py`. Other providers keep their existing behavior (their overflow errors differ per API; the Anthropic path was the documented gap).

**STOP during streaming** — STOP sets `stop_requested`, checked inside each provider's stream event loop (not just between API calls), enabling mid-stream cancellation.

**API cost tracking** — `stream_worker()` tracks real-time cost across all three providers. Each streaming method returns a usage dict (6th tuple element): Anthropic from `final_message.usage` (incl. `cache_creation_input_tokens`/`cache_read_input_tokens`), OpenAI from `stream.get_final_response().usage`, Gemini from the last chunk's `usage_metadata`. Static `_get_pricing(provider, model)` does a longest-prefix match against the hardcoded tables in `constants.py` (`ANTHROPIC_PRICING`/`OPENAI_PRICING`/`GEMINI_PRICING`). Costs accumulate per run and emit as `cost_update` messages (blue monospace `cost_info` tag, gated by Activity); unmatched prefixes skip silently. `MyAgent_Pricing.txt` documents the entries. STOP/incomplete streams return `None` usage and skip cost for that call. When the agentic loop ends (GUI **and** headless, on success **and** on the exception path — which also schedules `_on_close` in headless so a failed unattended run exits instead of lingering as a zombie process), `_log_api_cost(total_cost)` appends one `{timestamp};{provider};{model};{cost}` line to `APICOST_LOG_FILE` (repo root via `_BASE_DIR`, gitignored) — semicolon-delimited so a comma in a model name can't split a field, plain 4-decimal cost for spreadsheet summing. It skips when `total_cost == 0` (no priced usage — Ollama, unmatched prefix, or STOP before the first result), mirroring the live display; best-effort, so a write failure warns via the queue but never interrupts the run. Before each append it runs the shared one-slot rotation `rotate_log_if_needed(APICOST_LOG_FILE, APICOST_LOG_MAX_BYTES)` (`myagent/helpers.py`; 100 KB cap in `constants.py`): over the cap the log is atomically renamed to `APICostLog.txt.old` (replacing the previous archive) and restarts with a timestamped marker line — semicolon-free, so the Cost Log viewers' field-count parsers (`NF>=4` / `$f.Count -lt 4`) skip it in their summaries. `Heartbeat.py` (`heartbeat.log`) and `UnreadSummary.py` (`unread_summary.log`) delegate their rotation to the same helper.

**State restore fallback** — `_restore_model_params()` checks the saved model exists in the saved provider's model list; on mismatch (e.g. an auto-save race pairing an Anthropic model with the OpenAI provider, or the saved provider's API key missing from the launching environment), it falls back to the provider's curated default via `_default_model_for_provider()` — NEVER `available_models[0]`: fetched lists are sorted, and lexicographic-first can be a terrible pick (xAI's sorts to the pinned `grok-4.20-0309-non-reasoning`, which is what a Heartbeat-launched FNE run silently ran on 2026-07-25 when its plist lacked `MOONSHOT_API_KEY`). Both drift warnings (provider unavailable / model fallback) are queued immediately AND stashed in `self._model_drift_warnings`, which `stream_worker` re-posts at run start — required because `_start_agent` clears the whole output window right after an `-l` auto-launch restore, erasing anything queued during it (that clear is why the FNE incident left zero visible trace in the window or the saved transcript). Corollary for ops: every NEW provider's API key must be added to every launchd plist / scheduled task that embeds keys, or instructions saved for that provider silently drift.
