## Architecture (MyAgent.py)

**Mixin-based modular design** — The `App` class in `MyAgent.py` inherits from 25 mixin classes in the `myagent/` package, each grouping related methods by concern (UI, streaming, tools, persistence, etc.). Constants and tool schemas live in `myagent/constants.py`; helper classes in `myagent/helpers.py`. Only `__init__` and the entry point remain in `MyAgent.py`. All mixins share state through `self.*` — no inter-mixin imports.

**Multi-provider support** — A Provider combobox switches between Anthropic, OpenAI, Google, xAI, and Moonshot (plus Ollama for local inference). Provider labels are company names; the Google provider serves the Gemini models and the Moonshot provider the Kimi models — legacy saved provider values ("Gemini", "Kimi") normalize to the company labels in `_restore_model_params`. The internal message format stays Anthropic-style; translation happens only at the API boundary: OpenAI uses `_messages_to_responses()`/`_tools_to_responses()`/`_stream_responses()`, Gemini uses `_messages_to_gemini()`/`_tools_to_gemini()`/`_stream_gemini_call()`, xAI reuses the Responses translators with its own `_stream_xai_call()`, and Moonshot (Kimi models) — Chat-Completions-only, so the Responses translators do NOT apply — has its own `_messages_to_kimi()`/`_tools_to_kimi()`/`_stream_kimi_call()` (see below). The `_ToolBlock` wrapper gives OpenAI/Google/xAI/Moonshot/Ollama dict-based tool responses the same `.name`/`.id`/`.input` interface as Anthropic's Pydantic objects, so `_execute_tool()` works identically for all providers. Gemini tool call IDs are synthesized as `gemini_{name}_{index}` (the API doesn't use IDs). Provider is saved per-instruction and in `agent_state.json`. The Instruction button is disabled while running. Google (Gemini) requires `GEMINI_API_KEY` or `GOOGLE_API_KEY`; xAI requires `XAI_API_KEY`; Moonshot requires `MOONSHOT_API_KEY` (or `KIMI_API_KEY`).

**OpenAI model filtering** — `_fetch_openai_models()` filters to Responses-API-compatible families via `OPENAI_RESPONSES_PREFIXES` (`gpt-4.1`, `gpt-5`, and `gpt-6` since 2026-09-06 — pruned in the 2026-07 audit: gpt-4.5 left the API 2025-07, gpt-4o retired 2026-02-16, and the whole o-series is scheduled out to gpt-5.6, o1/o1-pro/o3-mini/o4-mini on 2026-10-23 and o3/o3-pro on 2026-12-11); non-chat types (embedding, audio, search, realtime, preview, transcribe, tts) and legacy models (gpt-3.5-turbo, base gpt-4, gpt-4-turbo) are excluded. Scheduled-retirement ids that still pass the family prefixes are dropped too, via `OPENAI_DEPRECATED_MODEL_PREFIXES` (gpt-5-mini/-nano/-chat/-codex, gpt-5-2025 dated, gpt-5.1-chat) plus exact-match `OPENAI_DEPRECATED_MODEL_IDS` (bare `gpt-5`, bare `gpt-5.1-codex` — exact so the surviving gpt-5.6* and -codex-max/-mini ids aren't killed); policy is retiring-models-removed-ahead-of-shutdown, and their pricing entries are removed as well (gpt-5-pro and gpt-4.1 have no announced retirement and stay). GPT-5.6 (2026-07-09) ships as three tiers — sol (flagship $4/$20), terra (balanced $2/$12, the fallback default), luna (fast $0.20/$1.20) — priced in `OPENAI_PRICING` (re-trued 2026-08-25: sol had been carrying gpt-5.5's $5/$30; there is no bare `gpt-5.6` family row any more, so an unknown future 5.6 id is unpriced rather than mispriced); all three accept `reasoning.effort: "max"` (`_has_reasoning_max`, minor ≥ 6 — 5.5/5.4 reject it, probed live); gpt-5-chat-latest / gpt-5.1-chat-latest / gpt-5-codex / bare gpt-5.1-codex retired 2026-07-23. `OPENAI_REASONING_PREFIXES` (`o1`, `o3`, `o4`, `gpt-5`, `gpt-6`) get `reasoning` params instead of `temperature`. **GPT-6 Astra** (`gpt-6-astra`, 2026-09-03 — the new flagship, listed second in `OPENAI_FALLBACK_MODELS` so terra keeps the default) is always-reasoning with billed cache writes; its own paragraph is below. `gpt-5.x-chat-*` "Instant" variants (`_is_gpt5_chat_model()`) are non-reasoning, reject temperature, but support `text.verbosity`. The client uses `httpx.Timeout(600.0, connect=10.0, read=120.0)` to avoid indefinite hangs.

**Gemini model filtering** — `_fetch_gemini_models()` calls `gemini_client.models.list()`, strips the `"models/"` prefix, then applies a two-stage agentic filter: require the `generateContent` action (drops bidi-only live/audio models, embeddings, imagen, veo), then drop `GEMINI_NON_AGENTIC_SUBSTRINGS` name matches — specialized output modalities (TTS, the `-image`/Nano Banana lines, lyria music, omni AV), speech-to-text (`transcribe`, added 2026-09-19: `gemini-3.5-transcribe` answers on `generateContent`, so the action test passes it, but only with an `audioTranscription` part — it belongs to the Voice Setup picker, see **Voice input**), Interactions-API managed agents (deep-research, antigravity), the computer-use preview (needs its own tool protocol), gemma (no function calling), robotics — plus shut-down generations (`gemini-2.0-*`, `gemini-1.*`, which the API still lists) and the sunsetting `gemini-2.5*` family (retirement announced for no earlier than 2026-10-16 — picker-hidden and unpriced ahead of it per the 2026-07 audit policy, though the `thinking_budget` param wiring stays so a pinned 2.5 instruction keeps working until Google pulls it), falling back to `GEMINI_FALLBACK_MODELS`. What remains: the pro/flash/flash-lite text tiers, dated previews/variants (incl. `-customtools`, which is tuned to prefer registered custom tools — exactly MyAgent's pattern), and the floating `-latest` aliases. EVERY current text tier supports thinking — including Flash-Lite (verified live 2026-07) — so `GEMINI_THINKING_PREFIXES` has no "lite" carve-out. The config style is version-split by `_gemini_uses_thinking_level()`: Gemini 3+ (and the non-versioned `-latest` aliases, which float to 3.x+) send `thinking_level` (low/medium/high mapping 1:1 from the strength combo; a stale saved max coerces to high, and `gemini-3-pro-preview` coerces medium→high since it accepts only low|high), while 2.5 still requires the legacy `thinking_budget` (low=1024, medium=8192, high=24576 — sending `thinking_level` to a 2.5 model is HTTP 400). Both styles set `include_thoughts=True` so thought summaries stream to the Show Thinking pane (without it Gemini returns no thought parts at all). A reactive fallback in `_stream_gemini_call` retries once with the other style on a thinking-related 400, covering models/aliases whose style the version rules mispredict. SDK is `google-genai`, initialized with `GEMINI_API_KEY` or `GOOGLE_API_KEY`.

**xAI (Grok) integration** — `myagent/xai_mixin.py` rides on the already-installed `openai` SDK with `base_url="https://api.x.ai/v1"` (`XAI_DEFAULT_BASE_URL`) and `XAI_API_KEY` — no new dependency. xAI's primary surface is an OpenAI-style **Responses API** (same `input` items, flat `type:"function"` tool declarations, `function_call_output` results), so the existing `_messages_to_responses()`/`_tools_to_responses()` translators are reused verbatim; only the streaming caller is xAI's own. Architecture invariants:
1. **Raw event iteration, not the SDK stream wrapper** — `_stream_xai_events` consumes `client.responses.create(stream=True)` events directly instead of `responses.stream()`, whose client-side snapshot state machine is tuned to OpenAI's exact event sequences. Usage comes from the `response.completed` event (not `get_final_response()`); reasoning deltas are accepted as BOTH `response.reasoning_text.delta` and `response.reasoning_summary_text.delta` (models differ) and feed the Show Thinking pane.
2. **Server-side tools ON, mixing verified** — live probes (2026-07-05) proved xAI's built-ins mix cleanly with client-side function tools in one request (correct routing whichever the task needs), so xAI follows the OpenAI pattern: `_get_tools()` strips the local DuckDuckGo `web_search`/`fetch_webpage` and `_stream_xai_call` appends `{"type": "web_search"}` + `{"type": "x_search"}`, plus `{"type": "code_interpreter"}` gated off while desktop tools are on (same double-scaled-clicks rationale as OpenAI). Each invocation bills a flat $0.005, folded into the authoritative cost (below). Server activity streams as `web_search_call`/`code_interpreter_call`/`custom_tool_call` (x_search) output items → surfaced as activity notices; a 400 naming a built-in strips just that tool and retries.
3. **Reasoning knob per family** — `XAI_REASONING_EFFORT` (constants) maps prefixes to accepted `reasoning.effort` values, longest prefix wins: `grok-4.3` none/low/medium/high (low = API default; "none" disables reasoning), `grok-4.5` low..xhigh (always-reasoning — "none" is HTTP 400, verified live 2026-07-17), `grok-4.6` the same low..xhigh always-reasoning ladder ("none" is HTTP 400 "This model does not support `reasoning_effort` value `none`", verified live 2026-08-18), `grok-4.20-multi-agent` low..xhigh (the knob is agent collaboration count, not depth). Families absent from the table — the pinned `grok-4.20-*-reasoning`/`-non-reasoning` variants and the aliases (bare `grok-4.20` → the pinned reasoning variant, `grok-latest` → whatever xAI currently serves as latest — grok-4.3 until 2026-08, grok-4.6 since — at its server default; a floating alias deliberately never gets a knob, so a server-side re-point can't strand a saved effort value) — get NO reasoning param; behaviour is baked into the model id. `_model_supports_thinking()` returns "extended" for knob families → the OpenAI-style Reasoning combobox; a stale saved effort coerces to the family default ("low") instead of erroring. Reasoning summaries verified streaming live (grok-4.3 emits them even at effort=low).
4. **Temperature alongside reasoning** (Gemini-style) — always shown in the UI and always sent; `_stream_xai_call`'s BadRequest downgrade ladder (drop temperature → drop reasoning summary → drop reasoning, each via `continue` so successive 400s converge) degrades gracefully if a model refuses. `openai.AuthenticationError` is surfaced as a clear "check XAI_API_KEY" error instead of ten retries.
5. **Model fetch + filtering** — `_fetch_xai_models()` lists `/v1/models`, keeps `grok*` ids, drops `XAI_NON_AGENTIC_SUBSTRINGS` (the grok-imagine image/video models), falls back to `XAI_FALLBACK_MODELS` (grok-4.3 default) — which matches the live catalog 1:1 (verified 2026-07-17, re-verified 2026-08-18): the API serves exactly grok-4.3, grok-4.5 (500K context, vision, added 2026-07), grok-4.6 (the 2026-08-12 flagship — same $2/$6, 500K context, vision, NO aliases of its own; the announced `-fast` variant returns 404 "does not exist or your team does not have access", so it is not wired), the three grok-4.20 variants, and grok-build-0.1; ALL legacy families (grok-4/-fast, grok-3, grok-2) are retired, with grok-code-fast-1 surviving only as an alias of grok-build-0.1. Aliases are alias *fields*, not list entries, so the picker shows canonical ids only. `XAI_NON_VISION_PREFIXES` (grok-build-0, grok-code) drives the weak-desktop-combo warning — text-only per docs; the prefix is `grok-build-0`, not `grok-build`, because `grok-build-latest` re-aliased to grok-4.5 (vision) in the 2026-07 catalog.
6. **Exact cost tracking via `cost_in_usd_ticks`** — xAI is the only provider that returns the authoritative billed cost in the response (`usage.cost_in_usd_ticks`, 1 tick = $1e-10, verified to the digit against hand-computed pricing). `_xai_usage_dict` (split out of `_stream_xai_events` 2026-09-15, when it also began subtracting the subset-style `cached_tokens` from `input_tokens` — see the disjoint-buckets paragraph in the 2026-07-31 caching section) converts it to `usage_dict["cost_usd"]` and `stream_worker` prefers it over the table estimate, so the cost line is exact — including the cached-input discount ($0.20/M vs $1.25/M full rate; xAI caches aggressively) and the $0.005/server-tool fees, neither visible to a 2-tuple estimate. `XAI_PRICING` (verified live against /v1/models' price fields, unit $1/10000 per MTok: grok-4.3 + all grok-4.20 variants $1.25/$2.50, grok-4.5 and grok-4.6 $2/$6 — incl. the re-aliased grok-build-latest (still → grok-4.5), whose longer entry outranks the grok-build prefix — grok-build and its grok-code-fast alias $1/$2, and the floating grok-latest alias priced at its CURRENT target — $2/$6 since it re-pointed to grok-4.6 in 2026-08; cached input is $0.20/M on most families, $0.30/M grok-4.5, $0.50/M grok-4.6) remains as the fallback when the field is absent; >200K-input long-context doubling keeps the ≤200K tier (gemini-3.1-pro convention). Documented in `MyAgent_Pricing.txt`.
7. **Live-verified end-to-end 2026-07-05** — a real grok-4.3 `stream_worker` run (tool round trip via local `web_search`, effort=low) confirmed: streaming text + reasoning-summary deltas arrive, xAI's UUID-style `call-…` tool ids round-trip through `function_call_output`, usage lands in `response.completed`, and the cost tracker matched hand-computed pricing to the digit ($0.002954 for 1771 in / 296 out).

**Moonshot (Kimi) integration** — provider label **"Moonshot"** (the company, matching the Anthropic/OpenAI/xAI convention; the models are branded kimi-*, so the mixin/constants keep `kimi_*`/`KIMI_*` names, and legacy saved provider values normalize in `_restore_model_params` — "Kimi"→"Moonshot", and likewise "Gemini"→"Google" from the same-day Google rename). `myagent/kimi_mixin.py` rides on the `openai` SDK with `base_url="https://api.moonshot.ai/v1"` (`KIMI_DEFAULT_BASE_URL`) and `MOONSHOT_API_KEY` / `KIMI_API_KEY` — no new dependency. Unlike xAI, Kimi's surface is **Chat Completions ONLY** (no Responses endpoint), so the mixin has its own translators: `_messages_to_kimi()` (system message first; tool results as `role:"tool"` messages keyed by `tool_call_id`; assistant tool calls on the `tool_calls` array; images as `image_url` data-URL parts, with tool-result images deferred to a follow-up user message like the Responses translator) and `_tools_to_kimi()` (nested `function` format, not the flat Responses shape). Catalog/params/contract verified against platform.kimi.ai docs 2026-07-25. Architecture invariants:
1. **reasoning_content round-trip is per-model policy, and it's load-bearing** — Kimi thinking models return reasoning in a non-standard `reasoning_content` field (streamed as `delta.reasoning_content`, always before `content`) and are TRAINED to reason across interleaved tool calls: the accumulated reasoning must be re-sent unmodified on assistant messages during a tool loop or quality silently degrades (the classic bug in OpenAI-compatible harnesses pointed at Kimi). `_stream_kimi_events` accumulates it into a `{"type": "thinking", "thinking": ...}` block stored FIRST in content_blocks (internal history stays Anthropic-style; chat_mixin already serializes that shape, so Save Thinking works), and `_messages_to_kimi` re-emits it as `reasoning_content`. Policy: REQUIRED for `kimi-k3` / `kimi-k2.7-code*` (Preserved Thinking always on) and `kimi-k2.6`; FORBIDDEN for `kimi-k2.5` (`KIMI_NO_REASONING_ROUNDTRIP_PREFIXES` — no Preserved Thinking support at all). Unknown future models default to round-tripping, backstopped by a 400-ladder rung that learns per-model (`_kimi_reasoning_rejected`), rebuilds the wire messages without reasoning, and retries. On `end_turn` the plain-string append drops the final turn's reasoning — explicitly allowed by Moonshot once a turn completes.
2. **Thinking knob per family** — `kimi-k3`: always-reasoning, top-level `reasoning_effort` on a SPARSE low/high/max ladder (no medium; API default max) → the extended Reasoning combobox; stale efforts coerce via `_KIMI_EFFORT_COERCE` (medium→high, xhigh→max, minimal/none→low, else max). `kimi-k2.6`/`k2.5`: `thinking {"type": "enabled"|"disabled"}` → the plain Thinking checkbox (strength hidden, Ollama-style); k2.6 additionally gets `keep: "all"` (Preserved Thinking) whenever enabled — matching the keep-everything translator — while k2.5 never gets `keep`. `kimi-k2.7-code` (+`-highspeed`): always thinks, rejects the thinking param entirely → no knob (support None), reasoning still streams to the Show Thinking pane. All Kimi-specific params ship via `extra_body` (the SDK has no typed `thinking`/`reasoning_effort` for chat.completions); `max_completion_tokens` is typed (32768 when thinking — docs demand ≥16000 for tool loops — else 8192), with a ladder rung swapping to legacy `max_tokens` on rejection.
3. **NEVER temperature** — every current Kimi model fixes sampling server-side (non-modifiable per the parameter reference; the thinking guide says "do not set it"). The UI hides the temp widgets for ALL Kimi models and `_kimi_model_params()` never emits it. `_get_model_param_summary` shows `reasoning=X` (k3), `thinking=on/off` (k2.6/k2.5), or `thinking=always-on` (k2.7-code).
4. **No server-side tools** — Kimi keeps the local DuckDuckGo `web_search`/`fetch_webpage` (the Gemini pattern); `_get_tools()` does not strip them. Tokens are the only cost.
5. **Exact cost via cache-hit folding** — usage arrives on the final stream chunk (`stream_options {"include_usage": true}`); `_kimi_usage_dict` probes cached-input tokens under the three names in the wild (`prompt_tokens_details.cached_tokens`, flat `cached_tokens`, DeepSeek-style `prompt_cache_hit_tokens`) and computes `cost_usd = (input−cached)·miss + cached·hit + output·out` from `KIMI_PRICING` + `KIMI_CACHE_HIT_PRICING` (hit input is ~1/6 the miss rate — which is what keeps the mandatory reasoning re-send cheap). stream_worker prefers `cost_usd` over the all-miss 2-tuple estimate. Since 2026-09-15 the emitted `input_tokens` is the MISS count (gross `prompt_tokens` minus the cache hit), so the buckets are disjoint like every other provider's — the formula always subtracted, but the reported bucket passed the gross figure through and double-counted the hit in the cost log's TOK-IN field. Documented in `MyAgent_Pricing.txt`.
6. **Model fetch + filtering** — `_fetch_kimi_models()` lists `/v1/models`, keeps ids starting `kimi-k`, and drops the discontinued DASH family `kimi-k2-*` (kimi-k2-thinking etc., EOL 2026-05-25 — the current K2 generation uses DOTS: kimi-k2.5/k2.6/k2.7-code); `moonshot-v1*` (EOL 2026-08-31), `kimi-latest`, and `kimi-thinking-preview` fall out of the prefix rule. Fallback `KIMI_FALLBACK_MODELS` matches the live catalog 1:1 (verified 2026-07-25 with a real key: kimi-k2.6 / k3 / k2.7-code / k2.7-code-highspeed — **kimi-k2.5 is documented+priced but NOT served**, at least to new accounts; its pricing/no-round-trip entries are retained in case it returns). Default kimi-k2.6 — the 256K vision agentic tier at $0.95/$4. `KIMI_NON_VISION_PREFIXES` (`kimi-k2.7-code`, text-only) drives the weak-desktop-combo warning.
7. **Retry ladder + streaming hygiene** — same skeleton as xAI: raw chunk iteration, first-content timeout (180s) with a waiting ticker, `AuthenticationError` → clear "check MOONSHOT_API_KEY" message, RateLimit/5xx backoff via `retry_util`, STOP checked per chunk, `finish_reason=length` surfaces a truncation warning. The BadRequest ladder rungs (each `continue`s): drop `reasoning_effort` → strip reasoning round-trip (learn-once) → drop `thinking.keep` then the whole `thinking` param → swap `max_completion_tokens`→`max_tokens`. Detection helpers + translators + params are characterization-tested in `tests/test_kimi_detect.py`; pricing in `tests/test_pricing.py`.
8. **Live-verified end-to-end 2026-07-25** — a real kimi-k2.6 streaming run (thinking enabled+keep=all, tool declared) confirmed the wire shapes `_stream_kimi_events` relies on: `delta.reasoning_content` streams before content, tool calls accumulate via `delta.tool_calls` (ids look like `get_time_0` — name-based, not `call_*`), `finish_reason` lands `tool_calls`/`stop`, and usage arrives in the final chunk (`prompt_tokens`/`completion_tokens` + `completion_tokens_details.reasoning_tokens`; `prompt_tokens_details` was null on small calls, so the cache probe's fallbacks matter). A second call with `reasoning_content` round-tripped on the assistant message + a `role:"tool"` result was ACCEPTED and answered correctly — the Preserved-Thinking contract works as wired.

**MCP integration** — `myagent/mcp_mixin.py` connects to Model Context Protocol servers (filesystem, GitHub, Slack, etc.) at startup, enumerates each server's tools via the `mcp` Python SDK, and exposes them through the same `_get_tools()`/`_execute_tool()` pipeline as native tools. Architecture invariants:
1. **Async-only SDK** — `MCPMixin` runs a dedicated asyncio loop in a background thread (`self._mcp_thread`); the sync streaming worker calls in via `asyncio.run_coroutine_threadsafe`.
2. **One `AsyncExitStack`, one long-lived runner** — all server connections live in a single stack owned by `_mcp_runner`, which connects, lists tools, then parks on `self._mcp_shutdown_event` for the whole session. Required because anyio binds task-group cancel scopes to the originating task: splitting the lifecycle across multiple `run_coroutine_threadsafe` calls would kill the stdio pumps and surface as `Connection closed` on the next `list_tools`. Shutdown signals the runner; the stack unwinds sessions/stdio_clients LIFO and subprocesses exit. A post-unwind `gc.collect()` + two `await asyncio.sleep(0)` cycles drain pending pipe-close callbacks to avoid harmless `Event loop is closed` finalizer tracebacks.
3. **Namespaced tool names `<server>__<tool>`** (double underscore — valid for all four providers' regexes); `_execute_tool` looks up `block.name` in `self._mcp_tools_by_name` and routes to `do_mcp_call` before the static dispatch chain.
4. **Per-user config** in `mcp_servers.json` (root), same shape as Claude Desktop / Cursor, so community servers drop in unchanged. `${NAME}` placeholders in `env` values are substituted at spawn time by `_substitute_placeholders`: `${RANDOM_PORT}` is reserved (each occurrence → an independent OS-assigned free port; does not consult `os.environ`), any other `${NAME}` → `os.environ[NAME]` (or empty + a one-shot warning). Substitution is scoped to user-typed `spec["env"]` keys only — not the ambient env, not `command`/`args` (so secrets don't leak via process listings). This keeps `mcp_servers.json` secret-free and safe to track.
5. **Graceful degradation** — without `mcp` installed, `_HAS_MCP` is False, the checkbox is disabled, and every method is a no-op.
6. **Deferred connect** via `root.after(100, self._connect_mcp_servers)` so a slow handshake never blocks launch; per-server failures are logged, not fatal.
7. **Dual-sink `_mcp_log`** — status lines go to both the GUI queue and `sys.stderr`; launch with `python.exe` or `pythonw.exe MyAgent.py 2> mcp.log` to capture the MCP stream off-process. `mcp_enabled` persisted per-instruction. To enable: `pip install mcp`, drop in `mcp_servers.json`, restart, tick the MCP checkbox.
8. **Windows ProactorEventLoop hardening** — three settings prevent `ClosedResourceError` / spurious EOF on the first RPC after `initialize()`, all rooted in IOCP fragility: (a) pass `errlog=os.devnull` (opened once in `_connect_mcp_servers`) to every `stdio_client` — under `pythonw.exe` `sys.stderr` is None, which corrupts IOCP routing; (b) create the loop with `asyncio.new_event_loop()` *inside* `_loop_runner`, since IOCP ownership binds to the constructing thread; (c) pass an explicit `list_roots_callback` returning `ListRootsResult(roots=[])` — the SDK default returns an error and skips advertising the roots capability, which some servers (e.g. `server-filesystem`) handle badly.
9. **Reconnect-on-close** — if `list_tools` raises `ClosedResourceError`/`Connection closed`, `_list_tools_for_server` opens a fresh session via `_open_server_session`, swaps it into `_mcp_sessions[name]`, and retries. Belt-and-braces; (8) is the real fix and this rarely fires.

**Proton Mail integration** — `myagent/protonmail_mixin.py` adds native multi-account Proton tools via Proton Bridge over stdlib IMAP+SMTP — NOT MCP and NOT a REST API (Proton publishes none; E2E encryption means decryption is client-side, so Bridge is the official integration path). Its sixteen tools mirror the Gmail surface 1:1 (same names with `proton_` prefix), with the same In-Reply-To/References handling and optional `attachments` (20 MB cap, MIME auto-detected). Architecture invariants:
1. **Per-account Bridge credentials, no OAuth** — config at `~/.config/myagent-protonmail/accounts.json`: `email`, `username`, `app_password` (Bridge-generated, NOT the Proton login), per-account `imap_host`/`imap_port`/`smtp_host`/`smtp_port`, and optional `ca_cert_path` (Bridge's exported `cert.pem`) for verified TLS. Absent/missing cert → `CERT_NONE` (acceptable for localhost-only Bridge traffic, where a MITM already needs code execution on the machine). IMAP connections are cached per-account; SMTP opens fresh per send.
2. **Account enum patched at runtime** — same `_get_tools()` pattern as Gmail.
3. **No "scope" concept** — Bridge gates the surface server-side (no permanent delete, no settings); Trash is recoverable from Proton's UI.
4. **Destructive ops gated by `_confirm_proton_action`** — `proton_send`/`reply`/`send_draft`/`trash`/`delete_label`; same dialog + per-tool bypass as Gmail (stored in `disabled_confirm_patterns`). Dispatch via `block.name.startswith("proton_")`.
5. **`_HAS_PROTONMAIL`** is always True on CPython (stdlib `imaplib`+`smtplib`+`email` transport); kept for parity. Bridge availability is detected at first-call time, not startup, so Bridge restarts reconnect transparently. `proton_enabled` persisted per-instruction.
6. **IMAP UIDs are per-folder** — per-message tools take a (`folder`, `uid`) pair; bulk ops take `folder` + `uids: [int]`. UIDs are never reused (RFC 3501), so a MOVE → MOVE-back round-trip yields three distinct UIDs for the same logical message.
7. **Four helpers renamed `_proton_*`** (`_format_proton_summary`, `_extract_proton_bodies`, `_extract_proton_attachments`, `_attach_proton_files`) to avoid MRO shadowing: the App's mixin order (`...GmailMixin, ProtonMailMixin...`) means Gmail's identically-named statics would otherwise win the left-to-right MRO and silently break Proton (empty bodies, arity crashes). A foundational footgun of flat-namespace mixins — defensively prefix non-shared helpers.
8. **Four empirical Bridge/dovecot quirks, mitigated**:
   - (a) **SUBJECT search** is reliable for single-word substrings but fragile for multi-word substrings against non-ASCII subjects (curly quotes, em-dashes, accented letters); the `proton_search` description steers toward single words, and `_uid_search` switches to `CHARSET UTF-8` byte-literals for non-ASCII queries.
   - (b) **`Labels/X` MOVE is additive, not exclusive** — INBOX→`Labels/Foo` just adds the label; moving back removes it. System folders (INBOX/Sent/Drafts/Trash/Archive/Spam) are true exclusive destinations. Documented in `proton_modify_labels`.
   - (c) **Label removal can leave a transient new UID** in the source (Bridge↔Proton eventual consistency); `do_proton_modify_labels` snapshots source UIDs, detects strays after the MOVE, and re-MOVEs them up to 2×, reporting `label_removal_retries: N` (0 = clean).
   - (d) **Bare-token SEARCH works on Bridge, dovecot rejects it** — `q="invoice"` is a loose full-text match on Bridge but errors `BAD Unknown argument` on dovecot/cPanel (WebCentral). The description steers toward the explicit-key form (`SUBJECT`/`BODY`/`TEXT`/`FROM`/`TO "..."`), which works on both.
9. **Native, not MCP** — same rationale as Gmail, plus credential hygiene via Bridge's per-install app-password (never the real Proton login or mailbox password).

Its sixteen tools mirror the Gmail surface 1:1 (same names with `outlook_` prefix), with proper conversation threading and optional `attachments` (~3 MB cap, MIME auto-detected). Architecture invariants:
1. **OAuth via MSAL, single process** — token caches at `~/.config/myagent-msmail/{account}_token.json` (chmod 600), Azure app client_id at `msal_app.json` (or `OUTLOOK_CLIENT_ID`/`MS_CLIENT_ID` env), account list at `accounts.json`. `_outlook_token(account)` tries `acquire_token_silent` first, falls back to `acquire_token_interactive(prompt="select_account")` (transient localhost redirect server), then refreshes silently. A `PublicClientApplication` is cached per account in `self._outlook_apps`. A 401 forces one token re-acquire + retry inside `_outlook_graph`.
2. **Account enum patched at runtime in `_get_tools()`** — each tool's `account` field gets `enum=[...accounts.json names...]`; empty `accounts.json` → empty enum (clearer error than dropping the tools). Same pattern as Gmail/Proton.
3. **Scope `Mail.ReadWrite` + `Mail.Send` only** — read/send/draft/move/categories/mark-read but NOT permanent delete (a deliberate safety boundary mirroring Gmail's; Deleted Items is recoverable from Outlook's UI).
4. **Destructive ops gated by `_confirm_outlook_action`** — `outlook_send`/`reply`/`send_draft`/`trash`/`delete_label` pop a Tk `askyesno`; denial returns `"user denied: ..."`. `outlook_reply` deletes its server-side `createReply` draft on denial so nothing is left behind. Dispatch routes via `block.name.startswith("outlook_")`. Confirm bypass via the Safety dialog's "Outlook destructive tools" section (shared `_disabled_confirm_patterns`).
5. **`_HAS_OUTLOOK` flag** mirrors `_HAS_GOOGLE`/`_HAS_PROTONMAIL`: missing `msal` → checkbox disabled, methods no-op. `outlook_enabled` persisted per-instruction and in `agent_state.json`.
6. **Gmail "labels" → Outlook "categories"** — `outlook_list/create/delete_label` wrap `/me/outlook/masterCategories`; `outlook_modify_labels` operates on category **display names** (not ids) because Graph stores `message.categories` as a name array, reading current categories and applying the add/remove diff. `outlook_trash` is a Graph `move` to the well-known `deleteditems` folder (each move yields a NEW message id, returned as `moved_ids` — same per-move-id-churn gotcha as Proton's per-folder UIDs).
7. **Single body, not multipart** — Graph messages have one body (`contentType: html|text`); when `body_html` is supplied it is sent as the body and the plain `body` is dropped (`_outlook_body_field`). A draft IS a message, so `outlook_send_draft` takes the draft's message id.
8. **All non-shared helpers prefixed `_outlook_`** — `OutlookMixin` is last of the three mail mixins in the App's MRO (`...GmailMixin, ProtonMailMixin, OutlookMixin...`), so prefixing avoids the flat-namespace shadowing footgun (Gmail's `_header`/`_extract_bodies`/etc. would otherwise win the MRO).
9. **Native, not MCP** — same rationale as Gmail: a tight 16-tool catalog, multi-account by one parameter, real confirmation dialogs, and reusable MSAL/token plumbing for future Microsoft Graph services (Calendar, OneDrive).

**Local document reader** — `myagent/document_mixin.py` adds one tool, `read_document(path, max_chars?, pages?)`, extracting text from PDF (`pypdf`), DOCX (`python-docx`), HTML (via `extract_text_from_html` in `helpers.py`), and most plain-text/source formats. Architecture invariants:
1. **Provider-agnostic** — operates on local file paths, so it pairs with `gmail_get_attachment`/`proton_get_attachment`/`fetch_webpage` with no source-specific wiring. The local filesystem is the boundary between provider-specific download and format-specific extraction.
2. **Always-available** — in static `TOOLS` (no checkbox) and in `PARALLEL_SAFE_TOOLS` (read-only, stateless).
3. **Graceful degradation** via `_HAS_PYPDF`/`_HAS_DOCX` — a missing lib makes only that format return a `pip install` hint; others keep working. Plain text and HTML have no dependency.
4. **Per-format extras** — PDFs return `page_count`/`pages_extracted`/`metadata`; DOCX returns `paragraph_count`/`table_count`/core properties, with tables rendered as `|`-separated rows to preserve column structure.
5. **PDF page ranges** — optional `pages` accepts `"1-5"`/`"3"`/`"1,3,5-7"` (1-indexed); out-of-range values are dropped for a partial result rather than an error.
6. **Encrypted-PDF detection** — tries empty-password decryption (common for owner-password-only PDFs); on failure returns a clear message and suggests `qpdf --decrypt` via `run_command`.
7. **Per-page error isolation** — a malformed page gets a `[page N: extraction error]` placeholder and extraction continues.
8. **Unknown extensions** — tries UTF-8 decode (catches mislabelled text), else a 256-byte hex preview; suggests `file`/`unzip`/`pandoc`/`ffprobe` for the deliberately-unsupported long tail (XLSX, ZIP, RTF, EPUB, A/V).
9. **Paired with the on-demand skill "email-attachment-processing"** (`skills/` store) documenting the `_read → _get_attachment → read_document → reason` pattern; on-demand so it costs zero base-prompt tokens.

**Native file tools** — `myagent/file_mixin.py` (mixin #21) adds five always-available tools (`read_file`/`edit_file`/`write_file`/`glob_files`/`grep_files`) via `FILE_TOOLS`, modeled on Claude Code's tool contracts — the reliable-editing surface for coding tasks, replacing PowerShell round-trips (PS 5.1 `Set-Content` defaults to the ANSI codepage, here-strings mangle `$`/backticks, CRLF is invisible in tool output). Architecture invariants:
1. **Fail-loud editing** — `edit_file` requires an exact `old_string` match that is UNIQUE in the file: zero matches, or several without `replace_all=true`, returns a retryable error naming the problem — never a guess applied to the wrong place. The pure core `_file_apply_edit` (no IO) is what makes shell-free editing trustworthy.
2. **Read-before-edit tracking** — `self._file_read_paths` (lazy init in `_file_reads()`, process-lifetime — matching the fire-and-forget one-run-per-process pattern) gates `edit_file` and `write_file`-over-existing: the model must have `read_file`'d the file first, so edits are grounded in actual content, not a stale imagination of it.
3. **Byte-exact round-trips** — all IO uses `encoding="utf-8", newline=""` so `\r\n` stays literal in the string; `_file_apply_edit` retries an LF-normalized `old_string` expanded to CRLF (only when the file is CRLF and `old_string` carries no `\r` of its own); a leading BOM decodes to U+FEFF and re-encodes unchanged. Structurally unit-tested in `tests/test_file_mixin.py` (uniqueness, CRLF fallback, BOM round-trip, refusal paths, glob/grep pruning).
4. **`read_file` is the gate and the viewer** — cat -n numbering, `offset`/`limit` paging (default 1000 lines), 500-char line truncation, binary sniff (NUL in the first 8K) that steers to `read_document`/`run_command`.
5. **glob/grep prune heavy dirs** (`FILE_SKIP_DIRS`: `.git`/`.venv`/`node_modules`/`__pycache__`/`.claude` — the last because `.claude/worktrees/` holds full repo copies that would double every hit) and skip binary / over-2 MB files. `grep_files` is pure-Python regex (no ripgrep dependency) with `files_with_matches`/`content`/`count` modes and a filename `glob` filter.
6. **Always available + parallel-safe reads** — `FILE_TOOLS` extends unconditionally in `_get_tools()` (like `read_document`, no checkbox); `read_file`/`glob_files`/`grep_files` are in `PARALLEL_SAFE_TOOLS`, while `write_file`/`edit_file` stay sequential. Dispatch is one grouped dynamic `getattr(self, f"do_{block.name}")` branch in `_execute_tool` (mail-mixin pattern). All helpers are `_file_*`-prefixed against MRO shadowing.
7. **Paired with the `Coding_Agent` instruction** (shared store) encoding the Claude-Code discipline: user_prompt for the task → glob/grep/read to explore → surgical `edit_file` (never shell edits, never whole-file rewrites) → verify by running tests via `run_command` → summary. Model claude-sonnet-5, adaptive thinking.

**Excel live-workbook integration** — `myagent/excel_mixin.py` (mixin #23) adds nine `excel_*` tools (`EXCEL_TOOLS`, Excel checkbox) driving the REAL Excel application via **xlwings** — COM on Windows, AppleScript on macOS — deliberately NOT file-level xlsx editing: formulas recalculate live, VBA macros run, the user watches changes land in the open workbook, and one mixin serves both machines. Tools: `excel_open` (attach-or-launch + state summary; optional `password` for open-protected files — a wrong one errors immediately with no dialog, and the attach-to-already-open route needs no password at all, keeping it out of the model pipeline), `excel_read` (TSV labeled with real row numbers / column letters), `excel_write` (cells typed EXACTLY as a user would — '42' number, '2026-08-01' date, '=SUM(B2:B9)' live formula; the all-string cell schema dodges provider JSON-schema union quirks), `excel_format`, `excel_sheet` (list/add/rename/delete/activate/clear), `excel_find`, `excel_run_macro`, `excel_save`, `excel_close`. Architecture invariants:
1. **Stateless per call — no COM handles cached on self.** Tool calls run on a fresh stream_worker thread each run and COM apartments don't cross threads, so every call re-attaches via the Running Object Table. `_excel_app` is the single chokepoint (all nine tools reach it, directly or via `_excel_book`/`_excel_target`): the per-thread `CoInitialize` (Windows) and the xlwings-missing guard (a `pip install xlwings` RuntimeError that every tool's try/except surfaces as its friendly error string) live once there, not repeated per tool — since the 2026-08-03 simplify pass; before it the guard covered only `excel_open`. A `.books.count` liveness probe guards against a just-quit instance lingering in the ROT with a dead window handle (otherwise: cryptic `FindWindowEx` 1400 errors).
2. **Attaches to the USER'S running Excel by design** — so `excel_close(quit_app=true)` quits ONLY when no other workbooks remain open. Found live 2026-08-01: the first smoke test's quit saved-and-closed the user's own open personal workbook. NEVER involve user workbooks in tests (see memory `deathbook-protected-workbook`); smoke-test with scratchpad workbooks only.
3. **Currency formats change the wire type** — COM returns `$#,##0.00` cells as VT_CY → `decimal.Decimal`, not float. Display (`_excel_cell_str`) normalizes Decimal; `excel_find`'s numeric match uses `numbers.Number` (minus bool), never `isinstance(v, (int, float))`.
4. **`_HAS_EXCEL`** = xlwings importable (constants.py); Excel-not-installed surfaces at first call via `_excel_app`'s guard, like Proton Bridge. All helpers are `_excel_`-prefixed (the MRO-shadowing rule). All nine tools stay sequential — never PARALLEL_SAFE (one shared COM apartment).
5. **Windows live-verified 2026-08-01** (attach to running instance, create/write/recalc, read formulas, format incl. the currency-Decimal regression, sheets, find, save, quit-refusal with bystander workbooks). **macOS live-verified 2026-08-01 on the M4 Mac Mini** (Excel 16.111.2, xlwings 0.36.12 + appscript — `xlwings` added to `requirements.txt`, which the original merge omitted): all nine tools pass the same surface, formulas survive a save→reopen round-trip as formulas, and `_excel_cell_str`'s Decimal normalization is visible (`59.849999999999994` → `59.85` once currency-formatted). Two macOS prerequisites bit that test: **Excel must be ACTIVATED** (unactivated, `save_workbook_as` fails `OSERROR -50` at every path — not a path or `password` problem), and Excel's sandbox **"Grant File Access" modal can stall a tool call ~433 s with no timeout** on the first save into an unvisited folder — neither is clickable in a `--headless`/launchd run. Pure helpers are unit-tested in `tests/test_excel_mixin.py`.
6. **The wedged-Excel silent-write hazard** (found live on macOS 2026-08-01, on two separate long-running instances). A long-lived Excel process can enter a state where reads, formatting and sheet ops all keep working while **every cell-value write is silently discarded** — no error, and `saved:true` proves Excel never even marks the document dirty. Confirmed NOT an xlwings bug: raw AppleScript `value` / `value2` / `formula` / `formula r1c1` / via `selection` / frontmost all fail identically. Not caused by launch method or save order (both tested and cleared). **Restarting Excel fixes it.** The danger is that `_excel_app`'s `.books.count` liveness probe does NOT detect it — it reports healthy — so `excel_write` announced *"Wrote 5x5 cells"* over a no-op. Mitigation: `_excel_write_dropped` (pure, unit-tested) now checks every write. Small writes (≤200 cells) compare against the existing read-back echo; larger writes get a bounded first-row probe, closing the gap where big writes had **no** verification at all. It is deliberately conservative — it fires only when every expected cell was non-empty and every cell read back empty, so a formula returning `""` can't trip it. Diagnostic tell for a wedged instance: `osascript` `count of workbooks` times out while `count of windows` answers instantly.
7. **Unattended opens of protected workbooks: the dialogs, and the read-only trap** (worked through live 2026-08-01 against `DeathBook.xlsm`, a `CDFV2 Encrypted` OLE container in OneDrive). Three separate blockers, only one of which is an open parameter.
   - **The workbook gallery / DocStage HANGS the agent** (hit live 2026-08-01: MyAgent locked on its very first `excel_open`). `_excel_app(launch=True)` launches with `add_book=False`, so Excel comes up with NO document and shows its start screen — the template gallery with Cancel/Create. That window blocks Excel's Apple Event queue **completely**: `books.open` never returns, and even `tell application "Microsoft Excel" to activate` times out. Accessibility does not expose it either (`count of windows` returns 0), so it cannot be clicked away programmatically — the only recovery is killing Excel, which makes the pending call fail and releases the agent. Prevent it with `defaults write com.microsoft.office ShowDocStageOnLaunch -bool FALSE` (also set on `com.microsoft.Excel`; GUI equivalent is Excel → Preferences → General → "Open Excel Workbook Gallery when application opens"). Verified: launch-with-no-workbook went from hanging indefinitely to returning in 0.5 s. This is the single most important macOS setting for unattended Excel runs — a modal that blocks the event queue is unrecoverable from inside the agent, unlike every other dialog here.
   - **Macro prompt** on `.xlsm` — NOT an open parameter but an Office-wide preference: `defaults write com.microsoft.office VisualBasicMacroExecutionState -string EnabledWithoutWarnings` (documented values `DisabledWithWarnings` *(default)* / `DisabledWithoutWarnings` / `EnabledWithoutWarnings`; read at launch, so Excel must restart). It spans Word and PowerPoint and makes any macro-bearing file run silently — a security trade the user opts into, never a default to set. Windows needs no equivalent: its Trust Center already trusts the location.
   - **Password dialogs** — `password` and `write_res_password` are DIFFERENT passwords and one workbook can carry both: the first decrypts the file, the second claims write access on a write-reserved workbook. `_excel_open_kwargs` (pure, unit-tested) assembles the `books.open()` kwargs, omitting anything blank so an ordinary open stays byte-identical to a bare `open(path)`; `ignore_read_only_recommended` is plumbed for the softer read-only *recommendation* prompt. **DeathBook turned out NOT to be write-reserved** (`write_reserved=False`, `read_only_recommended=False`) — it needs only the one open password — so these params are general capability, not that file's fix.
   - **Silent read-only is the real trap, and its cause is UNRESOLVED.** DeathBook opened read-only for an agent run and, minutes later, fully editable on three consecutive fresh-Excel runs with successful write probes — same single password, file untouched. Neither a sidecar `~$` lock file (a zero-filled one does not reproduce it) nor Excel session state reproduced it on demand, so **do not repeat the plausible-sounding "Excel caches a path's read-only state for the session" explanation — it was tested and did not hold.** What ships is detection, not a diagnosis: `_excel_is_read_only` (`api.ReadOnly` on Windows, `api.read_only.get()` on macOS, chained so the wrong-platform probe's `AttributeError` falls through) and `_excel_read_only_note`, which lists what to check (sidecar lock, genuine write-reservation, disk writability, open-elsewhere/OneDrive) and gives the remedy that actually worked: quit Excel completely and retry. This matters because read-only is silent and only bites at the first save — the same silent-failure class as the dropped-write hazard in 6.
8. **Two macOS-only defects fixed 2026-08-01.** (a) `do_excel_run_macro` reported SUCCESS for a non-existent macro — macOS `run VB macro` returns `None` for a MISSING macro exactly as for one that ran and returned nothing, and Excel's AppleScript dictionary exposes **no** way to enumerate VBA project members, so existence genuinely cannot be checked. It now branches on `sys.platform`: Windows keeps the confident "ran" message (COM raises for an unknown macro), macOS says "was dispatched" plus an explicit note to confirm the effect. (b) `_excel_get_sheet`'s friendly *"Sheet 'X' not found. Sheets: …"* never fired on macOS, because `book.sheets[name]` returns a LAZY reference that only blows up later at use (leaking a raw `OSERROR -1728` from whatever call happened to touch it). It now validates against the real sheet names via `_excel_resolve_sheet_name`, which also gives macOS the case-insensitive lookup Windows COM had natively. Relatedly, `do_excel_sheet` validates its `action` against `SHEET_ACTIONS` **before** resolving the sheet, so a bad action is named as such instead of surfacing as "sheet not found" for whatever placeholder name rode along with it. `SHEET_ACTIONS` is `EXCEL_SHEET_ACTIONS` from constants.py — the same tuple feeds the tool schema's `enum`, so the guard and the schema cannot drift apart.

**Physical tools (2026-09-21)** — `myagent/physical_mixin.py` (mixin #25) adds the **Physical** tool set (`PHYSICAL_TOOLS`, Physical checkbox, persisted per instruction as `"physical"`): tools that sense the room the computer sits in rather than the computer itself. One tool today, `camera_capture` — a still photo from a webcam via **OpenCV**, returned as the same `[text, image]` block pair `do_screenshot` returns, so the Anthropic tool_result path and every hoisting translator carry it unchanged. Optional `camera` (index, default 0), `save_path` and `delay_seconds` (a self-timer — invariant 13). Architecture invariants:
1. **Its own set, never a Desktop tool** — asked and answered at design time (the user's question was "Desktop, or a new Physical category?"). *Consent*: a camera sees the room and whoever is in it; the many Desktop-enabled instructions, unattended Heartbeat runs included, must not gain it by ticking a box that means "drive the mouse". *Coordinates*: see (2). *Dependency*: OpenCV, not pyautogui. `tests/test_surface.py` pins `DESKTOP_TOOLS` to an exact name list besides. "Physical" rather than "Camera" so that whatever else senses or acts on the world outside the computer has a home; `blocked_tools` is the per-tool control inside the set.
2. **A photo is not a click surface.** `do_camera_capture` reads and writes NONE of the screenshot pipeline's state — `_screenshot_scale` / `_offset` / `_dims`, `_display_states`, `_display_full_states`, the cached images — so a photo taken between a screenshot and a `mouse_click` leaves the click where it would have landed (pinned: the test sets all eight attributes and compares them after a capture). The click pipeline stays frozen; the camera has its own `_camera_fit` and its own copy of the per-provider limits (`CAMERA_IMAGE_CAPS`: 2048 / 4 MP Google, 2048 / 5 MP OpenAI, 1568 / 1.15 MP everyone else — the same numbers, for the same reason: past them the API downscales anyway).
3. **The hoisted-image hint knows about photos** (`helpers.is_camera_result` / `camera_aware_hint`). The Responses (OpenAI + xAI), Gemini, Kimi and Ollama translators defer tool-result images to a follow-up user message introduced by a hardcoded *"Below is the screenshot image … use the pixel coordinates … for mouse_click"* — over a webcam photo, an invitation to click at the furniture. Each translator records one bool per deferred image (`is_camera_result(tc_content)`: the result's first text block opens with `CAMERA_RESULT_MARKER`, the one constant the mixin writes and the helper reads) and passes its hint through `camera_aware_hint`: no photo → the SAME string object back (byte-identical for screenshots — pinned against the literal pre-camera text for all four translators); photos only → a photo hint; a mixed turn → the screenshot hint plus "of the N images below, image K is a camera photo". The photo's own result text deliberately never contains a parenthesised `(WxH pixels)` — that is the shape the translators' dimension regex looks for, and in a mixed turn it must find the *screenshot's* size (dimensions are written `1430x804 pixels` unparenthesised, the saved size `1920 by 1080`; both pinned). The markers live in `helpers.py`, not `constants.py`, because `Heartbeat.py` / `UnreadSummary.py` import helpers and it must stay stdlib-only. Known, deliberately untouched: `user_prompt` reply images and `browser_screenshot` images still get the screenshot wording.
4. **Auto-exposure needs an ADAPTIVE settle, not a frame count.** Measured 2026-09-21 on the development laptop (integrated 1080p camera): the first 20 DirectShow frames ran mean brightness 79 → 138 → 64 and were still falling; from a cold start DirectShow levelled at ~1.9 s and Media Foundation at ~2.65 s, the latter after a dip whose turning point (~0.95 s) looks flat for several frames. `_camera_settled(samples, window, span)` therefore requires the samples to reach back a FULL `CAMERA_SETTLE_WINDOW` (0.75 s) with every frame in it within `CAMERA_SETTLE_SPAN` (1.0 of 255); a 0.25 s window is fooled by the turning point (pinned, with both measured ramps as fixtures). `CAMERA_SETTLE_CAP` (4 s) takes the latest frame regardless — a TV or trees in the wind never settle — and the result then says brightness may be off. The exposure signal is the mean of every 8th pixel each way (1/64 the cost). A photo takes 3–4 s.
5. **Stateless per call: open → settle → one frame → release**, `cap.release()` in a `finally` on every path (pinned across success, no-open, no-frames, STOP). No handle outlives a call, so the indicator light is on only during a photo and another app gets the camera straight back. Never PARALLEL_SAFE — one device.
6. **The grab runs on its own daemon thread** (`_camera_grab_guarded`), bounded by `CAMERA_TIMEOUT` (25 s): a blocking driver call cannot be interrupted by STOP, so a wedged driver must cost a timeout rather than the run (the Excel gallery hang is the precedent for "unrecoverable from inside the agent"); a fresh thread also carries no COM apartment for Media Foundation to collide with (the Excel tools `CoInitialize` the worker). The waiting side polls every 0.1 s, so STOP sets the `cancel` event and the grab exits within a frame; a STOP is reported as such (`_CameraStopped`), WITHOUT the "check your camera" hint every real failure gets.
7. **Backends are named, in order** (`_camera_backends`): Windows tries Media Foundation (opened in 0.45 s, 26 fps at 1080p) then DirectShow (0.4 s + 0.55 s to change mode, 16 fps) so one failing falls through to the other; macOS `CAP_AVFOUNDATION`; else `CAP_ANY`. 1920×1080 is requested and the driver answers with its nearest mode. On this laptop the Windows Hello **IR camera** is a second PnP device, but neither backend exposes it as an index — index 0 is the colour camera on both. OpenCV's log level is lowered to ERROR at first use: an index that will not open is a tool result here, not console noise.
8. **`save_path`** goes through `normalize_save_path` (the mail tools' guard against a Windows path invented on the Mac), gains `.jpg` when it has no extension, accepts only `.jpg` / `.jpeg` / `.png`, and REFUSES an existing file or a folder — all before the camera is opened (pinned: `opened_with == []`). The file is the FULL-resolution frame at JPEG quality 92 (the model's copy is 85, after the resize), written with Python's `open`, never `cv2.imwrite`: that goes through the ANSI code page on Windows and returns False — silently — for a path with characters outside it (live-verified with `saved photo é.jpg`). A failed save is a `⚠ NOT saved` note on a result that still carries the photo.
9. **JPEG, not PNG** — the one place tool-result images are not PNG; every translator already reads `source.media_type` rather than assuming. A 1080p photo is ~2 MB as PNG and 100–170 KB as JPEG. A nearly black frame (mean < 6) comes back WITH the image plus a privacy-shutter / lens-cover / dark-room warning.
10. **`_HAS_CAMERA`** (constants.py) is `importlib.util.find_spec("cv2")` — presence, no import; `_camera_cv2()` imports at the first capture and is the single missing-OpenCV guard. (With opencv installed pyscreeze imports `cv2` at startup anyway, ~80 ms, for `find_image_on_screen`'s confidence matching — the README's existing reason for the optional `opencv-python` extra.) `_blind_camera_warning` posts a ⚠ at run start when Physical is on and the model takes no image input (the xAI / Moonshot / Ollama text-only families), unless Desktop is on and `_weak_desktop_combo_warning` has already said it.
11. **Wiring** follows Excel's: `physical_enabled` BooleanVar (MyAgent.py), the editor checkbox between Excel and Meta (disabled without OpenCV), `"physical"` in the saved entry / applied snapshot / `manage_instructions` list-read-create-update and its schema; an entry saved before the toggle existed loads with it off. A static scan pins that `instructions_mixin.py` and `state_mixin.py` mention `"physical"` / `physical_enabled` / `_editor_physical` exactly as often as their Excel twins. The ten toggles need 904 px at 150 % display scaling, so the editor's fresh-state default width went 900 → 960.
12. **Verified 2026-09-21 on Windows**: in-process against the real camera (settle, per-provider sizing, save / refuse / no-extension, a non-ASCII path, `camera=5`, STOP at 0.8 s → back in 1.2 s), then real headless runs — `claude-haiku-4-5` (image inside the tool_result) described the room correctly, `gpt-5.6-luna` (the hoisted path) received the 1920×1080 photo and classed it as a physical scene. **macOS verified 2026-09-22** (M4 Mac Mini + Logitech BRIO 500, in-process against the real camera over AVFoundation at 1920×1080) — after a fix, because `OPENCV_AVFOUNDATION_SKIP_AUTH=1` had made the Mac path impossible: OpenCV's AVFoundation backend checks the TCC permission BEFORE touching the device and, while it is undetermined, sends the request and fails the open — from ANY thread (the prompt is tccd's, and the main-thread run-loop spin OpenCV wants only matters to a script about to exit); skipping the request meant no prompt ever, and macOS lists an app under Privacy & Security > Camera only after its first request, so it could not even be granted by hand. Now `_camera_cv2` sets the flag to `0`, and `_camera_mac_authorize` (darwin only, called BEFORE the self-timer wait so the prompt comes while someone is there) reads the permission through the ObjC runtime via ctypes (`_camera_mac_auth_status`: 0 undetermined / 1 restricted / 2 denied / 3 authorized, None elsewhere — no PyObjC), sends the request with a throwaway open when undetermined (OpenCV fails it at once, no camera light) and polls until it is answered — `CAMERA_AUTH_WAIT` 60 s, STOP-interruptible — so the first photo lands in the same call; `_camera_failure_hint` (an instance method now) words a denial (System Settings) and an unanswered prompt apart. Asked once per launching app per machine (`My Agent.app`, Terminal, or the python binary for a launchd job). Pinned in `MacAuthorizationTests`. SelfBot is untouched.
13. **`delay_seconds` — the self-timer, and how a monitoring loop is paced** (added the same day, after the user's first "photo every 10 s" run stopped by itself). **Click accuracy pipeline** — Desktop click invariants, refined for cross-provider accuracy:
- All providers receive **pixel coordinates** (no [0, 1000] normalization) — what the model reads in the image is what it passes to `mouse_click`. The old Gemini [0, 1000] convention caused ~1-pixel drift and broke entirely under multi-monitor mixed-DPI.
- `do_mouse_click`/`_scroll`/`_drag`/`_read_screen_text` use `round(float(x))` (not `int(x)`) to avoid truncation bias.
- A pre-screenshot guard refuses click/scroll/drag/OCR with "Take a screenshot first" when `_screenshot_dims == (0, 0)`.
- Tiered out-of-bounds policy: ≤2px overflow clamps silently; >2% of the dimension refuses with a "re-take a screenshot" message; in between clamps with a `⚠ clamped` warning.
- A 50ms `time.sleep` after `pyautogui.click` lets the UI settle before the next screenshot.
- The `_capture_single_display` region branch snapshots `entry_scale`/`entry_offset` at entry so chained region screenshots don't drift through stacked offsets.

**Per-display state tracking** — Multi-display coordinate state lives in two parallel dict pairs:
- `_display_states[N]`/`_display_images[N]` — the **most recent capture** (full or region) for display N. Used by `mouse_click`, `find_element`, and any `display=N` tool.
- `_display_full_states[N]`/`_display_full_images[N]` — the **most recent FULL capture** for display N, never overwritten by region captures. Region screenshots (`screenshot(display=1, x, y, width, height)`) interpret their coordinates in this full-image space, not relative to the last capture — without this two-slot split, chained region screenshots drift through stacked offsets.

`_resolve_coord_state(display)` is the shared lookup: returns `_display_states[display]` if a `display` param is given, else the current `_screenshot_scale/offset/dims`. `mouse_click`, `mouse_scroll`, `mouse_drag`, `read_screen_text`, and `find_element` all accept an optional `display` so the model can disambiguate screens without re-screenshotting.

**Image resolution caps per provider** — `_capture_single_display` resizes to each API's actual limit:
- **Anthropic**: `1568` long edge / `1.15 MP` — the API silently downscales to this anyway.
- **OpenAI**: `2048` long edge / `5 MP` — verified the API silently downscales above 2048 (gpt-5.2 reported `PIL.Image.size == (2048, 1152)`), so 2048 keeps `_screenshot_scale` matching what the model sees.
- **Gemini**: `2048` long edge / `4 MP` — higher than Anthropic's because Gemini's 768×768 tile system gives small UI elements more pixel density.

**find_element tool (Gemini-only)** — Uses Gemini's native spatial pointing API to locate UI elements by description. `gemini_mixin.py:do_gemini_find_element` uses Google's *exact* documented prompt (`"Point to the X. The answer should follow the json format: [{\"point\": <point>, \"label\": <label1>}, ...]. The points are in [y, x] format normalized to 0-1000."`) — the trained pointing capability only fires on this phrasing. Parses both the array shape and a single-object fallback. Takes an optional `display` so the cached-image lookup hits the right screen (`_display_images[display]`). Returns pixel coordinates (converted from [0, 1000]) and names the exact `mouse_click` to make. Stripped from `_get_tools()` for every provider but Google.

**Grid overlay** — `do_screenshot` accepts optional `grid=true`; `_capture_single_display` then calls `_draw_coord_grid(img)` after the API-limit resize (so labels match what the model sees), drawing 100px magenta gridlines with `(x,y)` labels at intersections (skipping (0,0)). Opt-in / default-off so it doesn't obscure small text; the tool description nudges its use for small/dense UI.

**Diag checkbox** — `Diag` (next to `Save Thinking`) gates `[DIAG capture]`/`[DIAG click]` activity lines showing the full coordinate-mapping trail (display rects, physical/logical/sent-to-model dims, scale, offset, raw input, computed screen pixels). Persisted as `diag_enabled`. Independent of `Debug` (which controls API JSON payload display). Defaults on.

**Debug payload dump rendering (`_debug_render`)** — the "PAYLOAD SENT TO API" dump (Debug checkbox) is JSON-shaped but NOT valid JSON when any string is multi-line: strings containing newlines render as indented triple-quoted blocks with REAL line breaks (2026-08-07 — as a JSON string the system prompt was one endless `\n`-escaped line that hid the very `## Skill:` blocks a user opens the dump to verify), and `ensure_ascii=False` keeps bullets/dashes readable. Stray non-serializable objects fall back to `repr` (display must never crash). A payload with no multi-line strings still round-trips through `json.loads` (unit-tested in `tests/test_debug_render.py`). `_payload_for_display` builds the provider-faithful dict (system/instructions/tools/params per provider) and hands it to `_debug_render`; for OpenAI the reasoning / temperature / verbosity keys come from the same `_openai_model_params` builder the live request uses (2026-09-06 — before that the dump omitted `text.verbosity`); SelfBot carries an in-file copy.

**Code interpreter gating (OpenAI)** — `_stream_responses_call` and `_payload_for_display` skip `code_interpreter` when desktop tools are on (`self.desktop_enabled.get() and _HAS_DESKTOP`). With CI access, gpt-5.2 loads screenshot bytes via PIL, sees the API-resized dimensions, and pre-scales coordinates itself — colliding with our scaling and producing double-scaled clicks. Stripping CI forces direct visual perception. CI stays available for non-desktop OpenAI tasks (data analysis, file processing, etc.).

**OpenAI tool rejection cache** — Newer models can reject server-side tools with HTTP 400 (e.g. `gpt-5.2-pro` rejects `code_interpreter`). `_stream_responses_call`'s `BadRequestError` handler regex-extracts the tool name from the message, adds it to `self._openai_unsupported_tools[model_id]`, strips it, and retries once — caching so later calls in the session skip it upfront. Same pattern as the temperature retry.

**Weak desktop combo warning** — `_weak_desktop_combo_warning()` (streaming_mixin) returns a warning string for weak-click-precision provider/models: gpt-5 at reasoning none/minimal, gpt-5 `-chat` Instant variants, any `gemini-2.x`. `stream_worker` posts it as `⚠ ...` at agent start. Informational only — doesn't change behaviour or override the model. Anthropic, gpt-4, gpt-5 ≥ low, and gemini-3.x pass clean.

**Parallel tool execution** — When the model requests multiple tools in one turn, blocks are partitioned into parallel-safe (`web_search`, `fetch_webpage`, `csv_search`, `get_skill`, `read_document`, `read_file`, `glob_files`, `grep_files`, `run_instruction`) and sequential (everything else). Parallel-safe run concurrently via `concurrent.futures.ThreadPoolExecutor`; sequential run one at a time in order. Results go into a pre-allocated list indexed by original position, preserving API-expected ordering. `run_instruction`'s membership (2026-07-22) is what enables **parallel waited children**: each spawn is an independent child process and a waited call blocks only its own executor thread, so several `run_instruction` calls in ONE assistant turn become concurrently-running waited subagents — total wait is the slowest child, not the sum (safety plumbing in the Meta-agent tools block below).

**Voice input (2026-09-19)** — `myagent/voice_mixin.py` (mixin #24) lets a reply be dictated: the Agent Request dialog's **Mike** button is a toggle (press → red `■ Stop` + timer + level meter → press again → *Transcribing…* → the transcript is inserted into the reply box), and **Voice Setup** edits the settings and tests the chain — a button at the **bottom left of the MAIN window, left of the Debug checkbox** (Alt+V) since 2026-09-20: it began beside Mike, and the user moved it the next day because that dialog exists only while a run is asking something. `do_user_prompt` only embeds the row: `_voice_build_row(dlg, resp_text)` returns `(frame, mike_btn, dictation)`, built BEFORE the image row so Tab order stays visual, and the dialog keeps ownership of three things — the ONE `bind_mnemonics` call per window (a second call would replace the binding, so `m` is merged into the existing `i` / `r` map), the Enter rule in `on_inject` (`recording` → `dictation.toggle()`, i.e. Enter ENDS the recording; `transcribing` → swallowed; both `break`, because sending mid-dictation would lose the speech), and `dictation.shutdown()` in `_capture_and_close` (a `<Destroy>` binding on the toplevel is the backstop for any other destroy path). Architecture invariants:
1. **One state machine, two buttons** — `_VoiceDictation(app, window, button, status, get_config, on_text)` runs idle → recording → transcribing → idle for the Mike button (`get_config` = the saved file, `on_text` = `_voice_insert_into` the reply box) and for Voice Setup's Test button (`get_config` = the dialog's UNSAVED fields, `on_text` = its read-only transcript box), so a provider / model / microphone can be tried before it is saved. The button's resting look is captured from the widget by `cget` and restored verbatim (the toolbar-highlight rule); the recording look is `VOICE_RECORDING_BG` (`#c62828`, constants.py) + white text, with `highlightbackground` painted too for Aqua, whose button face ignores `bg`. **Red means the stream is open**: the look changes only after `recorder.start()` returned, because the first press of a session pays the import below — the status line says *Opening the microphone…* meanwhile.
2. **Two threading rules.** (a) EVERY PortAudio call — the import, the device scan, stream open / close — runs on the Tk thread: PortAudio's Windows backends initialise COM on the initialising thread, and the main thread is the only one that is always there. The block callback runs on PortAudio's own thread and writes nothing but `_VoiceRecorder` fields. (b) Only the API call runs on a worker (`_work`), which touches no widget and hands `(job, text, info, error)` back through a `queue.Queue` that `_poll` drains via `after(80)` — the app-wide rule. A **job counter** makes delivery exact: `shutdown()` bumps it, so a transcript that lands after the window closed is dropped; `shutdown()` itself touches NO widget, because a toplevel's `<Destroy>` arrives after its children have died. The first poll is scheduled, never run inline, so the *Transcribing…* state always gets an event-loop pass (an instant fake API otherwise skipped it — found by the tests).
3. **`sounddevice` is imported at the first press, never at startup** — `_voice_sd()` is the single door (the `_excel_app` pattern: lazy import + the `pip install sounddevice` hint as a RuntimeError the status line shows). Measured 2026-09-19: the first PortAudio initialisation is ~460 ms on Windows (four host APIs), which every launch — the 5-minute headless Heartbeat children included — would pay for a feature only an interactive reply uses; a RE-scan (`_terminate` + `_initialize`) is ~22 ms, so `_voice_sd(rescan=True)` runs at every press and at Voice Setup open, and "system default" follows a headset plugged in mid-session. The rescan is skipped while `_VoiceDictation.live` (the app-wide open-stream count) is non-zero — terminating PortAudio would kill the stream — and it always attempts `_initialize` even if `_terminate` balked. Pinned by a static scan: no module-level `import sounddevice`.
4. **Capture** — `_VoiceRecorder`: `RawInputStream` (no numpy needed), 16 kHz mono int16 (what speech models work at; 1.9 MB/min), falling back to the device's native rate where the host API will not resample (the WAV header carries the rate); in memory only, never on disk; `full` at `VOICE_MAX_PCM_BYTES` = 24 MB (12.5 min, under the 25 MB upload cap) makes `_tick` end the recording by itself. Microphones are listed from ONE host API — the default one (MME on Windows, which resamples by itself; PortAudio otherwise lists every device four times: MME, DirectSound, WASAPI, WDM-KS) — and saved by NAME (`_voice_resolve_device`), since indices shift whenever a device comes or goes; a saved name that is absent today falls back to the default with a note. MME truncates names to 31 chars — cosmetic, and stable.
5. **Never send nothing** — a recording under `VOICE_MIN_SECONDS` (0.4 s, a slip) or whose peak is under `VOICE_SILENCE_PEAK` (50 of 32767) stops at a status message and is not sent. The threshold was measured on this laptop's noise-suppressed array: a quiet room idles at peaks of 2–50, ambient activity reaches 100–300, speech runs to thousands; exact zeros mean muted / denied. The message therefore says *only silence was recorded* (true in every case) rather than claiming a dead microphone — the first wording did, and a live microphone in a quiet room proved it wrong the same day. Silence is where speech models hallucinate a "Thank you."; `gpt-transcribe` returned empty text on ambient noise (status: *No speech recognised*).
6. **OpenAI path** (`/v1/audio/transcriptions`, the existing `openai_client`, 90 s timeout): live-probed matrix 2026-09-19 — `language` (one ISO code) and `prompt` are accepted by all four models (`gpt-transcribe`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe`, `whisper-1`; the docs' claim that gpt-transcribe rejects `language` is wrong); `languages` (several codes) + `keywords` via `extra_body` are gpt-transcribe ONLY — the 4o pair answers `The 'languages' parameter is not supported`, and **whisper-1 answers a bare `Invalid request.` with `param: None`**, so the chat models' "parse the rejected parameter out of the 400" ladder cannot work here. Hence `_voice_openai_params` decides per family up front (`VOICE_OPENAI_KEYWORD_PREFIXES`; the rest get one `language` — omitted when several codes are configured, since pinning a multilingual speaker is worse than auto-detect — and the hint as `prompt`), and the one reactive rung is blunt: any `BadRequestError` with optional params → resend the audio alone, with a note in the status line. `_voice_is_stt_model_id` filters `models.list()` to file-transcription ids (drops `realtime` / `-live-` / `diarize` and dated snapshots); `_voice_order_models` puts the curated ids first.
7. **Google path** (`generateContent` + an audio part, the existing `gemini_client`): `gemini-3.5-transcribe` is the dedicated model and the Google default — it rejects a system instruction (`Developer instruction is not enabled for this model`) and any `thinking_level` (both HTTP 400), and **returns its transcript in a part field, `audioTranscription.text`, that google-genai 1.67.0 does not model** (the part comes out of the SDK empty — `"parts": [{}]` — so `response.text` is None on an HTTP 200 that did carry the transcript; seen by comparing the SDK object with a raw REST call). `_voice_transcribe_gemini` therefore always sets `should_return_http_response=True` and `_voice_gemini_text` reads the transcript from the RAW JSON body — which serves the chat tiers' ordinary `text` parts too (thought parts skipped, first candidate only). Do not "simplify" this back to `response.text`, and do not upgrade the SDK for it. Request shapes step down one per 400: `tuned` (system instruction + temperature 0 + `thinking_level: low` — `minimal` is a 400 on 3.8-flash) → `untuned` (system instruction only) → `plain` (instruction folded into the user text); a dedicated model (`VOICE_GEMINI_DEDICATED_SUBSTRING` in the id) starts on `plain` and sends **the audio and nothing else, whatever is configured**: the 2026-09-20 audit showed it reads NO text part at all — a guard instruction, a language, a vocabulary list, before or after the audio, changed not one byte of its output — so its hints are not sent, its steerability cannot be fixed from our side, and its note in Voice Setup says both. `VOICE_GEMINI_SYSTEM` keeps a chat tier from ANSWERING a question it hears, but the audit's spoken COMMANDS got past it (flash-lite obeyed 2 of 7); `VOICE_GEMINI_GUARD`, a text part placed **BEFORE the audio**, took that to 0 of 7 (after the audio: 1), so chat tiers get `[guard + hints, audio]` in that order — wiring kept for a hand-edited config only, since the audit removed the chat tiers from the picker (rule 11). The picker lists live ids containing `transcribe` that support `generateContent` (the bidi-only `-live` one falls out), minus `VOICE_UNSUITABLE_MODELS`; because `transcribe` also joined `GEMINI_NON_AGENTIC_SUBSTRINGS` the same day, the model no longer appears in the main chat-model picker, where it could never run the agent loop.
8. **Settings are persistent, per-user, and NEVER part of an instruction** (the user asked for exactly this to be confirmed, 2026-09-20) — nothing in `instructions_mixin` / `state_mixin` / `skills_mixin` (`manage_instructions`) / `streaming_mixin` / `datapaths` / `Heartbeat.py` mentions voice (pinned by a static scan, `IndependenceTests`), so loading, applying or saving an instruction cannot touch them and they are absent from the instruction entry and the `applied_instruction` snapshot alike. `get_config` is `_voice_load_config`, i.e. the file is re-read at EVERY Mike press: a Save takes effect at once, in this instance and in any other running one, no restart (live-verified by rewriting the file between two presses). The file: `~/.config/myagent-voice/config.json` (`{provider, models: {OpenAI, Google}, language, hint, device}`; one model remembered PER provider so flipping the provider in the dialog loses nothing), sanitised on every load (`_voice_sanitize_config`: any JSON → a complete dict), saved atomically (mkstemp + `os.replace`). **run_command timeout + process-tree kill** — `run_command` accepts an optional `timeout` (clamped 5–600 s in `_execute_tool`, default 30) passed through to `run_powershell(command, timeout)`. Two pieces make it safe: (a) **`_SPAWN_LOCK`** (module lock in skills_mixin) serializes only the prologue — the store existence-check (`_load_saved_instructions` absorbs OneDrive conflict forks, a disk mutation) through the `Popen` — while the waited poll loop runs unlocked so children genuinely overlap; (b) **`_claim_instance_number` claims slots atomically** (`O_CREAT|O_EXCL`, PID written on the raw fd immediately), so simultaneously-launching children get distinct instance numbers / `agent_state_N.json` files. The claim protocol also covers the reclaim races: an *unreadable* lock younger than 5 s is treated as a mid-claim sibling (not stale); a judged-stale lock is removed by `_reclaim_stale_lock` under a per-slot **mutex directory** (`<lock>.reclaim` — os.mkdir is atomic on both OSes) with the content re-validated INSIDE the mutex, so only the exact file generation that was judged stale can ever be removed. A bare check-then-remove was itself a TOCTOU (os.remove is path-based and cannot tell inode generations apart: a reclaimer descheduled between its re-read and its remove deleted a sibling's FRESH replacement lock and both returned the same slot; the earlier "conditional remove + verify-after-write" only protected a claimant whose lock was clobbered *before* its verify — the storm test failed 4-in-5 on macOS until the mutex fix, 2026-07-23). A crashed reclaimer's leftover mutex is cleared once older than 10 s; after winning the O_EXCL create the claimant still re-reads to verify ownership (belt-and-braces). Unit-tested in `tests/test_parallel_children.py`: PARALLEL_SAFE membership (manage_* excluded), two mocked-Popen waited children overlapping with per-spawn result isolation, an 8-thread barrier race for slots, and a stale-reclaim storm. The tool description teaches the fan-out pattern (issue all spawns in one turn, each with its own extra_text/timeout). Meta toggle saved per-instruction.

**Window geometry persistence (main window + every dialog)** — rebuilt 2026-08-29 after the main window kept coming back on the primary monitor of the dual-2560×1440 desktop. ONE mechanism in `state_mixin.py` serves all six persisted windows (`GEOMETRY_KINDS`: main, editor, ps_safety, prompt, confirm, skills — the on-disk key names inside a layout entry are unchanged, so existing files restore): `_remember_geometry(kind, win)` captures a window's geometry into a per-process cache, `_place_window(win, kind, default_size, parent=, min_size=)` positions a dialog before it is shown, and `_save_last_state` / `_load_last_state` move the cache to and from this instance's state file under the current layout key (`_get_monitor_config_key()` — every monitor's rect from Win32 `EnumDisplayMonitors` / macOS `CGGetActiveDisplayList`, sorted; instance N writes `agent_state_N.json`, so instances persist independently). Three Windows facts, all reproduced live, drive the capture guards in `_remember_geometry`: (1) **a maximized window's `wm geometry` is a chimera** — the ZOOMED size at the NORMAL position (`2560x1417+-723+73`); the old code saved it verbatim every 5 s and the next launch restored it as a 2576×1456 *un-maximized* window straddling both monitors, which Windows counts as living on the primary — THE user-visible bug. Now a zoomed window is never captured; `main_zoomed` is recorded and the last normal geometry kept, tracked as the root moves/resizes by `_bind_geometry_tracking` (root `<Configure>`, filtered to the root's own events since the binding fires for every descendant), and the restore is `geometry(normal)` then `state("zoomed")`, which maximizes on the monitor of the normal position. (2) **A never-mapped root reports `1x1+X+Y`** until Tk's first idle pass, so the save in `__init__` used to write a junk size the next launch rejected as too small — capture requires `winfo_ismapped()`. (3) An iconified window still holds its normal geometry but is left alone so a minimize-from-maximized close restores maximized. `_geometries_for_save` writes this layout's entry only once something real was captured in this process (`_geometry_dirty`) — a `--headless` run whose root never showed passes the file's entries through untouched (possibly under a different key if a monitor came or went mid-run). Restore: `_select_geometry_entry` takes this layout's entry, else the legacy flat fields, else the most recently saved layout (`saved_at`) whose main-window position is still visible here — a monitor that dropped off the bus, or a first launch after rearranging, keeps the window where it was rather than resetting to the primary; `_apply_geometry_entry` also migrates a legacy chimera entry (no `main_zoomed` key, width equal to a monitor's) to a maximized restore at the default size. Visibility (`_geometry_visible`) is checked per monitor — ≥50 px of the window's 30-px title strip on SOME monitor — not against the virtual desktop's bounding box, whose dead corners on an L-shaped layout used to pass. `_sanitize_geometry` returns **None** (never `DEFAULT_GEOMETRY`) when a position is unusable: the old fallback handed dialogs the main window's `1050x930` at (0,0) — the `1050x930+0+0` confirm-dialog entries in `agent_state_2.json` were exactly that. Dialog pattern unchanged: `withdraw()` → build → `update_idletasks()` → `_place_window` → `deiconify()` (saved geometry when visible; else — since 2026-09-16, when SelfBot's dialogs got the same three-branch placement and the two apps were aligned — the saved SIZE, so a resize survives a monitor change and only the position is lost, or with nothing saved / a too-small saved size the dialog's default size; either centred on its parent — the editor for PS Safety/Skills — shrunk and clamped onto that monitor; a withdrawn parent, i.e. `--headless`, centres on the primary); PS Safety re-applies the returned geometry via `after(100ms)` because its embedded checkbuttons request a large natural size on map; macOS skips `transient(parent)` (its WM confines transients to the parent's screen). Dialog refs (`instruction_editor_window` / `skills_editor_window` / `_ps_safety_dialog` / `_confirm_dialog` / `_prompt_dialog`) live on `self` so `_build_geometry_entry` re-captures open dialogs live at every save; closing the editor captures PS Safety before the destroy cascade. The main-window default is `_default_main_geometry()` — `DEFAULT_GEOMETRY` **explicitly centred on the primary monitor** (clamped/shrunk to fit), NOT a bare size string: a no-position `wm geometry` lets the WM choose, which on a multi-monitor box is not reliably the primary — the asymmetry that made dialogs (which always compute a fallback position) behave while the main window landed elsewhere. An opt-in trace (`MYAGENT_GEOMETRY_DEBUG=1` → `geometry_debug.log`, `_geo_log`, off by default, 100 KB one-slot rotation) logs the entry restored at launch and the geometry saved at each close — the fastest way to tell a bad-save from a bad-restore for a "wrong monitor" report. Unit-tested in `tests/test_geometry.py` (display layouts stubbed); live-verified 2026-08-29 on the dual-monitor desktop — an in-process harness round-tripped all five dialogs to the left monitor, real relaunches restored the main window both normal and maximized on the left monitor with a second instance restoring independently from `agent_state_2.json`, and a user session's `geometry_debug.log` confirmed three consecutive launches each restored the exact geometry the previous close saved across both monitors (incl. a mid-session resize). A pre-fix maximized "chimera" entry in an existing `agent_state.json` heals on first load but only lands after one save, so a relaunch caught mid-heal can show one last wrong placement before it stabilizes.

**External window-manager reclaim (FancyZones et al.)** — added 2026-08-29 after the persistent "opens on screen 2 with a brief flash on screen 1" report on the same desktop turned out NOT to be MyAgent moving the window (grep confirms `self.root` geometry is set only in `_apply_geometry_entry`) but **PowerToys FancyZones** repositioning it just after it maps: FancyZones was running, unexcluded, with `openWindowOnActiveMonitor` + `appLastZone_moveWindows` on, so a new window is yanked to the active monitor / its last zone. This is *exactly* why the dialogs behaved and the main window didn't — every dialog already re-asserts its geometry on show (`after(100ms)` / withdraw→deiconify), the main window did not. Fix: `_apply_geometry_entry` records the restored geometry in `self._reassert_geo`; `_start_geometry_reassert` (called from `__init__` after `_load_last_state`) opens a `REASSERT_WINDOW_SECS`=1.5 s arm window and schedules fallback `after()` checks; `_maybe_reclaim_monitor` — driven by the root `<Configure>` (so it fires the instant the mover acts) and those fallbacks — re-applies the restored geometry **only when the window's centre has drifted to a DIFFERENT monitor** (`_monitor_index_of_center`) than it was restored to, and **only inside the arm window**. So an external cross-monitor yank right after launch is undone within a frame, while a same-monitor nudge, or ANY deliberate move after ~1.5 s, is never fought (a maximized restore and a withdrawn/headless root are also skipped). Live-verified: a simulated mover (SetWindowPos to the secondary monitor at launch) was reclaimed to the restored monitor in ~0.1 s, and a later move to the secondary monitor was left alone. Unit-tested in `tests/test_geometry.py::ReclaimMonitor`. Users who WANT FancyZones to manage MyAgent can add `pythonw.exe` to its excluded-apps list instead; the reclaim only defends the first 1.5 s.

**LaTeX to Unicode conversion** — Assistant text is converted to Unicode after each streaming segment via `_post_process_latex()`, which walks `tag_ranges("assistant")` and applies `_latex_to_unicode()` only to assistant-tagged text (so tool_info filenames/paths aren't mangled). **API retry logic** — Same as SelfBot: up to 10 retries, exponential backoff capped at 60s (429) / 90s (529). OpenAI also catches `APITimeoutError` (retry without backoff). A 180s first-content timeout cancels a stream that produces no visible output (thinking/text/tool calls); a background ticker posts elapsed time every 15s while waiting. OpenAI models that reject `temperature` retry without it; those that reject server-side tools are handled by the rejection cache (above). All providers break out of the loop immediately on success.

**Context-overflow compaction (Anthropic)** — a long agentic run can exceed the context window mid-task; the API returns 400 `prompt is too long: <T> tokens > <M> maximum`, which is not retryable as-is. `_stream_anthropic_call`'s BadRequestError handler now recovers instead of surrendering: `parse_overflow_counts` + `trim_history_for_context` (pure functions in `myagent/helpers.py`, ported 1:1 from SelfBot's sliding-window recovery) drop the oldest conversation rounds **in place** — cutting only at genuine user-turn boundaries so a `tool_use`/`tool_result` pair is never orphaned, sizing the cut to 0.75·M from the reported counts (oldest-half fallback), always keeping the last two rounds — then post a red ⚠ warning and `continue` the retry loop (`api_kwargs["messages"]` is the same list object, so the retry sends the shorter prompt and the trim persists into `stream_worker`'s ongoing loop). When even the last two rounds overflow (`removed == 0`), the pre-existing graceful exit fires: an actionable error naming 1M-context models, `end_turn` instead of a crash. Structurally unit-tested in `tests/test_context_trim.py`. Other providers keep their existing behavior (their overflow errors differ per API; the Anthropic path was the documented gap). On Claude Fable 5.1 this trim is a history edit under the preserved-thinking check (keep-tail compaction, mid tool round) — the `drop_block` binding in the next paragraph is what lets the retry succeed there.

**Claude Fable 5.1 harness surface (2026-09-02)** — `claude-fable-5-1` (released 2026-08-28) carries three API breaking changes over Fable 5, two of which touch this harness, plus an opt-in refusal fallback the migration guide says to ship by default. All of it hangs off `_anthropic_fable_features()` (anthropic_mixin), which returns the extra betas / `thinking.block_binding` / `fallbacks` values for the always-on Fable/Mythos class and None for every other model (Fable 5 / Mythos 5 accept both surfaces and simply never act on the binding check); `_payload_for_display` calls the same method so the Debug dump shows what is really sent. (1) **Preserved thinking** — a 5.1 thinking block's `signature` is bound to the conversation prefix that produced it (system, tools, every earlier message); replaying it after that prefix changed is a 400 (`Invalid \`signature\` in \`thinking\` block … bound to a different conversation`) on enforced accounts (created on/after 2026-08-31 — and Anthropic will enforce it for everyone on future models). Every Fable/Mythos request therefore sends `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` under `ANTHROPIC_THINKING_BINDING_BETA` (`thinking-binding-controls-2026-08-01`): the API drops the first mismatched block and every thinking block after it (unbilled — a dropped block lowers `input_tokens`), proceeds, and lists each drop in the response's top-level `input_transformations` (`reason` = `prefix_binding_mismatch` for a history edit, `model_binding_mismatch` for blocks from another model), which `_stream_anthropic_call` prints as an Activity line. Live-verified 2026-09-02 with a real 772-char-signature block replayed after a prefix edit: HTTP 200, `[{'type': 'thinking_dropped', 'path': 'messages.1.content.0', 'reason': 'prefix_binding_mismatch'}]`, `input_tokens` 460 → 446. The no-beta floor is a BadRequest rung that strips every thinking block from history (`helpers.strip_thinking_blocks`, in place — dict and SDK-object blocks alike, never emptying a turn) and retries once (`stripped_thinking` guard); it is checked BEFORE the beta-surface rungs because that error text names `block_binding` as the remedy and must not disable it. What else keeps the check happy: MyAgent already freezes `system` and `tools` for a run, only appends to `messages`, and the rolling `cache_control` markers don't count as edits. (2) **Forced tool choice** (`tool_choice: any` / `tool`) is a 400 on 5.1 — MyAgent never sends `tool_choice` (grep-confirmed), nothing to do. (3) **Model-bound blocks** — only Fable 5.1 / Mythos 5.1 read a 5.1 thinking block; MyAgent never reassigns `self.model` mid-run (`ui_mixin` only), and any other model would drop the blocks silently and unbilled anyway. **Server-side refusal fallbacks** — Fable's classifiers can decline a request with HTTP 200 + `stop_reason="refusal"` (pre-output: empty content, unbilled; mid-stream: partial output billed), which used to end an unattended run with just the ⚠ line. Fable/Mythos requests now send `fallbacks: "default"` under `ANTHROPIC_SERVER_FALLBACK_BETA` (`server-side-fallback-2026-07-01`): on a policy decline the API re-runs the same request on an Opus-tier model inside the same call, routed by refusal category (targets `claude-opus-5` / `claude-opus-4-8`; some categories decline with no fallback — then the ⚠ note says so, quoting `stop_details.recommended_model` when present). **Anthropic prompt caching (`cache_control`)** — added 2026-07-31 after a cost audit found a `Balance Westpac Mastercard account` run costing $2.15 on claude-sonnet-5 versus $0.30 on kimi-k3 — despite Sonnet 5 being the CHEAPER model per token ($2/$10 vs Kimi's $3/$15). The whole gap was caching: Moonshot caches context automatically server-side (`kimi_mixin` prices the hits at $0.30/M vs the $3.00/M miss), while Anthropic's caching is strictly **opt-in** and MyAgent had never set a breakpoint — so every turn of an agentic loop re-sent the entire growing prefix (system prompt + full tool catalog + every prior screenshot and tool result) at the full miss rate, a cost that grows ~quadratically with turn count. `_stream_anthropic_call` now places three breakpoints, under Anthropic's ceiling of four:
1. **One static marker on the system prompt** (`_anthropic_cache_system`). The cache prefix is built in the order tools → system → messages and a breakpoint caches everything *before* it, so this single marker covers the entire tool catalog too — no need to touch the server-side tool dicts. An empty prompt stays a bare string (a text block with `""` is a 400).
2. **Two rolling markers on the newest eligible turns** (`_anthropic_cache_messages`). Turn N writes a cache ending at its last message; turn N+1 matches that prefix and reads it at 0.10x. The second, older marker is the safety net for a write that hasn't landed or a prefix aged past the 5-minute TTL. Default TTL is deliberate: 5-min writes cost 1.25x and match `ANTHROPIC_PRICING`'s cache-write column exactly, so the cost line stays accurate (`ttl: "1h"` would need the `extended-cache-ttl-2025-04-11` beta and 2x writes).

Two invariants make it safe. **History is never mutated** — only the messages receiving a breakpoint are shallow-copied, because `messages` is the live list `stream_worker` appends to and `trim_history_for_context` trims in place; mutating it would accumulate stale breakpoints past the limit of four. **The wire copy is rebuilt inside the retry loop**, not once above it: the overflow handler's in-place trim previously relied on `api_kwargs["messages"] IS messages`, which the copy breaks — rebuilding per attempt restores that and re-places the markers on the post-trim tail. Assistant turns are skipped entirely (`streaming_mixin:1062` appends `final_message.content` verbatim — SDK Pydantic blocks, not dicts), which naturally lands the markers on the user turns carrying `tool_result`s, the real turn boundaries. Structurally unit-tested in `tests/test_anthropic_cache.py`; live-verified 2026-07-31 against claude-sonnet-5 (call 1 `cache_write=2829`, call 2 `cache_read=2829`, `input=2`). Watch it work by ticking **Activity** — the per-call cost line prints `cache_read:N` (`event_loop_mixin.py:176-195`), which read `0` on every Anthropic call before this change. SelfBot has NOT been given the same treatment.

**Cached-input accounting (OpenAI / Gemini)** — added 2026-07-31 as the follow-on to the Anthropic caching work above. Anthropic was the only provider whose caching needed switching ON; OpenAI (automatic above ~1024 tokens) and Gemini (implicit caching, automatic on 2.5+ tiers) were **always** getting the discount on the bill — MyAgent simply never reported it, so every OpenAI/Google line in `APICostLog.txt` was overstated. Three fixes, all live-verified 2026-07-31:
1. **Cached rates in the tables.** `OPENAI_PRICING` / `GEMINI_PRICING` entries are now 3-tuples `(input, output, cached_input)`; `_get_pricing` returns a `cache_read` key for them. Since 2026-09-06 the OpenAI rows that BILL cache writes — the GPT-5.6 tiers and gpt-6-astra, 1.25x input (terra $2.50/M, sol $5.00, luna $0.25, astra $12.50) — are 4-tuples with the write rate, exposed as `cache_write`; the families before 5.6 list no write price and stay 3-tuples. OpenAI's cached rate is 1/10 of input on the GPT-5 families and **1/4 on GPT-4.1**; Gemini's is exactly 1/10 across the Gemini 3 family. A `None` cached slot (the OpenAI `-pro` tiers, which have no cached tier) makes `_get_pricing` **omit** the key rather than emit `0` — a zero would silently price cached tokens *free*, so absence keeps the accumulator's `.get("cache_read", 0)` the explicit choice. The per-million→per-token conversion passes `None` through untouched (dividing it raises).
2. **Disjoint buckets — the load-bearing correctness point.** Anthropic reports cached tokens as a SEPARATE bucket; OpenAI's `input_tokens_details.cached_tokens` and Gemini's `cached_content_token_count` are **SUBSETS** of their input totals. `stream_worker` prices `input × input_rate + cache_read × cache_read_rate`, so feeding it the raw overlapping totals would **double-charge every cached token** — trading one wrong number for another. The new `_openai_usage_dict` / `_gemini_usage_dict` staticmethods (named for the existing `_kimi_usage_dict` convention, and unit-testable unlike the old inline blocks) subtract before emitting, `min(cached, input)`-clamped so a bad report can't go negative. xAI and Kimi report the same subset shape (`input_tokens_details.cached_tokens` / `prompt_tokens_details.cached_tokens`), but both supply an authoritative per-call cost, so their gross pass-through was never priced and went unnoticed until the cost log started writing the buckets themselves (2026-09-14): TOK-IN then counted every cached token twice and the viewers' blended $/MTok came out low by the cache share — $0.54 shown against a real $0.93 on the 2026-09-15 grok-4.6 row (input 246,964 with cached 183,424 inside, output 2,226, authoritative $0.2321), whose cost the table rates reproduce ONLY under the subset reading. Since 2026-09-15 `_xai_usage_dict` (new — the usage block split out of `_stream_xai_events` so it is unit-testable like the others; since the same day's simplify pass it and `_openai_usage_dict` are thin wrappers over ONE `helpers.responses_usage_dict`, so the subset rule for the Responses shape lives in a single place) and `_kimi_usage_dict` subtract too (Kimi's own cost formula always had; only the emitted bucket lagged), and `tests/test_cached_usage.py`'s `DisjointContractCase` pins all four normalizers at once: input + cache_read (+ cache_creation) must equal the provider's gross input.
3. **Gemini thinking tokens were UNDER-reported.** `thoughts_token_count` is its own bucket, NOT part of `candidates_token_count` — the provider's own totals only reconcile when counted separately (live: prompt 15009 + candidates 1 + thoughts 133 = total 15143). They bill at the OUTPUT rate, so `output_tokens` is now `candidates + thoughts`. This error ran *opposite* to the cached over-report and had been partly masking it. (OpenAI needs no equivalent fix — its `output_tokens` already includes reasoning tokens.)

Gemini's implicit-cache floor is **4,096 tokens** on the Gemini 3 tiers, so a zero `cache_read` on short prompts is normal, not a broken probe — a live probe at 2,710 tokens reported `None` and only fired at 15,009. **API cost tracking** — `stream_worker()` tracks real-time cost across all three providers. Each streaming method returns a usage dict (6th tuple element): Anthropic from `final_message.usage` (incl. `cache_creation_input_tokens`/`cache_read_input_tokens`), OpenAI from `stream.get_final_response().usage`, Gemini from the last chunk's `usage_metadata`. Static `_get_pricing(provider, model)` does a longest-prefix match against the hardcoded tables in `constants.py` (`ANTHROPIC_PRICING`/`OPENAI_PRICING`/`GEMINI_PRICING`). Costs accumulate per run and emit as `cost_update` messages (blue monospace `cost_info` tag, gated by Activity); unmatched prefixes skip silently. `MyAgent_Pricing.txt` documents the entries. STOP/incomplete streams return `None` usage and skip cost for that call. When the agentic loop ends (GUI **and** headless, on success **and** on the exception path — which also schedules `_on_close` in headless so a failed unattended run exits instead of lingering as a zombie process), `_log_api_cost(total_cost, had_usage, duration_secs, instruction=, calls=, tokens=)` appends one `{timestamp};{provider};{model};{cost};{params};{secs};{instruction};{calls};{in};{out};{cache_write};{cache_read}` line — `params` (5th field, 2026-08-10) is the comma-joined `_get_model_param_summary()` title-bar string (e.g. `mode=Adaptive`, `reasoning=Medium, temp=1`), recording the thinking/temperature settings the run used; `secs` (6th field, 2026-08-12) is the run's wall-clock duration in whole seconds (`time.monotonic()` from stream_worker entry, hoisted beside `total_cost` so the exception path logs it too) minus `_input_wait_secs` — the seconds the run sat parked on user input (`user_prompt`, command and mail confirmation dialogs), accumulated by `helpers.input_wait_timer` around each blocking wait and zeroed at run start, so TIME(sec) measures the agent working, not the user's response latency (2026-08-13) — rendered as a TIME(sec) column right of COST(USD) in both viewers; `instruction` (7th field, 2026-08-16) is `agent_instruction_name` **snapshotted at run start** (an instruction applied mid-run can't relabel the entry; blank for an ad-hoc run), whitespace-collapsed with any `;` turned into `,` so a user-typed name can never split the line — the viewers' rightmost INSTRUCTION column (after PARAMETERS, per the user), plus a "By instruction" spend rollup in the SUMMARY (rows with a name only; since 2026-09-02 all four rollups — machine / provider / model / instruction — are repeated over the current month only under a THIS MONTH heading, one shared rollup function per viewer; since 2026-09-22 the SUMMARY's `today` row is followed by one row per day for the last seven days — every calendar day back from yesterday, `$0.0000` for a day without a run, weekday in `today`'s slot, the amounts of those rows and `this month` in one decimal-aligned column ending at column 34 — the two viewers byte-identical, each reading every date from ONE clock reading and the sums from one per-day map built in a single pass; details in `desktop_launchers/README.md`); `calls` (8th field, 2026-08-16) is the final `call_num` — the "Call #N" counter, one per API round-trip of the agentic loop, so every call after the first is a tool-use round-trip — hoisted above the `try` beside `total_cost` for the same reason (a run that dies on Call #3 logs `3`), the viewers' CALLS column right of TIME(sec) — where the macOS viewer substitutes `-` for an empty secs / calls / params because BSD `column -t` collapses consecutive delimiters, which would shift every column after a mid-row empty field; `tokens` (9th-12th fields, 2026-09-14) is the run's cumulative `(input, output, cache_write, cache_read)` token counts — the same four buckets `_get_pricing` rates, summed over every call; they were ALREADY accumulated for the output window's running totals and merely discarded at log time, which left the log unable to answer *what is my blended $/MTok for this model* (cost alone cannot separate a 5x per-token rate from a 40x cache-read discount — e.g. Fable 5.1 reads cache at $0.25/MTok against Sonnet 5's $0.20, a 1.25x gap, while their input rates differ 5x). All four are hoisted above the `try` beside `total_cost`, and that is load-bearing rather than tidy: the except path READS them to build the fields, so leaving them beside the loop (where they used to live, unread from outside) makes an EARLY failure — anything raising before the loop — abort the handler with `UnboundLocalError`; the error message still reaches the queue, since it is queued first, but `_write_result_file` and the headless auto-close after it never run, so a waited parent sits out its whole timeout and an unattended run is left a zombie (pinned by `test_early_failure_completes_the_exception_handler`, which fails if they move back inside). They are written as plain integers and go blank ALL FOUR TOGETHER when `tokens` is None (a partially-filled group would read as *zero tokens billed* rather than *not recorded*, which is also how the viewers distinguish `-` from `0`); `input_tokens` is the NON-cached count and the cache buckets are disjoint, so `in+cache_write+cache_read` is the run's true billed input volume — never add input to a cache total expecting a subtotal. Both viewers render them as fixed-width TOK-IN / TOK-OUT / CACHE-W / CACHE-R columns joining the numeric cluster right of CALLS (still LEFT of the open-ended MODEL/PARAMETERS/INSTRUCTION, so the never-drop-the-cost invariant is unchanged), compacted to k/M, and feed a new SUMMARY block — **By model (tokens and effective blended rate)** — dividing real cost by real tokens, lifetime only (a blended rate over a handful of runs is noise) and skipping rows whose token group is blank — plus, since 2026-09-15, a **CACHE%** column: cache reads as a share of the input side (`cache_read / (in + cache_write + cache_read)`), the cache effect on its own. The blended rate's denominator also carries output tokens, which bill 5–6× input, so a blended figure under the input sticker can mean cheap cache reads OR little output (gpt-5.6-luna: 1.4% of the tokens were output yet 33% of the cost); only CACHE% separates the two, needs no pricing, and compares across providers. Two known biases remain in COST itself, so in the rate: Anthropic's server-side `web_search` / `code_execution` and OpenAI's `web_search_preview` are declared on every call and their per-invocation fees never reach `usage` (Anthropic reports the search count in `usage.server_tool_use.web_search_requests`, unread), whereas xAI folds its $0.005/tool fee into `cost_in_usd_ticks` — so cross-provider rates are not like-for-like on search-heavy runs; older 4-/5-/6-/8-field lines stay valid and render blank PARAMETERS/TIME/INSTRUCTION/CALLS/TOKENS columns, and SelfBot's lines (empty secs, prompt name + session call total in fields 7/8, its own session token totals in 9-12) line up in the same positions — to `APICOST_LOG_FILE` (`datapaths.resolve_costlog()`: `APICostLog_<machine>.txt` in the OneDrive share since 2026-08-03 — one file PER MACHINE because an append-only log can't be key-level-unioned, so machines must never share a synced file; every machine's log syncs side by side and the Cost Log viewers aggregate them all, with a legacy repo-root log folded in at first resolve, the claim made atomic by the local-file rename so concurrently-launching apps migrate exactly once; repo-root `APICostLog.txt` fallback without OneDrive, gitignored either way) — semicolon-delimited so a comma in a model name can't split a field, plain 4-decimal cost for spreadsheet summing. Zero-cost gate (since 2026-08-12): Ollama runs are free but LOG anyway as `0.0000` lines when at least one call returned usage (`had_usage`, hoisted beside `total_cost` so the exception path sees it) — local activity shows in the viewers without inflating spend — and, since 2026-09-15, WITH its token counts: the four accumulators run for every call that reported usage, priced or not (inside the pricing gate, where they sat until then, an unpriced Ollama call's counts were dropped and its line read `0;0;0;0`, which the viewers render as *no tokens billed*; `tests/test_costlog_run_fields.py`'s `_OllamaHost` pins the fix, and its paired unpriced-paid-model test pins that the gate below is unchanged); other zero-cost runs (a paid provider's unmatched pricing prefix, or a STOP before the first result) stay skipped, because a fabricated `$0.0000` for a paid provider would claim "free" when the truth is "price unknown" (line format characterized in `tests/test_costlog_params.py` — incl. the absent-vs-zero token group and the int coercion; the stream_worker → `_log_api_cost` wiring of instruction/calls/tokens on both loop-end paths in `tests/test_costlog_run_fields.py`, which drives the real loop against a stubbed `_stream_anthropic_call` — note its `_Host` usage stays input/output only because `tests/test_fable51_harness.py` subclasses it and asserts exact per-call costs, so the cache buckets are exercised by a separate `_CacheHost`). Best-effort, so a write failure warns via the queue but never interrupts the run. Before each append it runs the shared one-slot rotation `rotate_log_if_needed(APICOST_LOG_FILE, APICOST_LOG_MAX_BYTES)` (`myagent/helpers.py`; 100 KB cap in `constants.py`): over the cap the log is atomically renamed to `APICostLog.txt.old` (replacing the previous archive) and restarts with a timestamped marker line — semicolon-free, so the Cost Log viewers' field-count parsers (`NF>=4` / `$f.Count -lt 4`) skip it in their summaries. `Heartbeat.py` (`heartbeat.log`) and `UnreadSummary.py` (`unread_summary.log`) delegate their rotation to the same helper.

**State restore fallback** — `_restore_model_params()` checks the saved model exists in the saved provider's model list; on mismatch (e.g. an auto-save race pairing an Anthropic model with the OpenAI provider, or the saved provider's API key missing from the launching environment), it falls back to the provider's curated default via `_default_model_for_provider()` — NEVER `available_models[0]`: fetched lists are sorted, and lexicographic-first can be a terrible pick (xAI's sorts to the pinned `grok-4.20-0309-non-reasoning`, which is what a Heartbeat-launched FNE run silently ran on 2026-07-25 when its plist lacked `MOONSHOT_API_KEY`). Both drift warnings (provider unavailable / model fallback) are queued immediately AND stashed in `self._model_drift_warnings`, which `stream_worker` re-posts at run start — required because `_start_agent` clears the whole output window right after an `-l` auto-launch restore, erasing anything queued during it (that clear is why the FNE incident left zero visible trace in the window or the saved transcript). Corollary for ops: every NEW provider's API key must be added to every launchd plist / scheduled task that embeds keys, or instructions saved for that provider silently drift.
