01 The three-layer contract

SelfBot's own convention (from CLAUDE_SELFBOT.md) is that adding a tool requires three edits. The audit reverses that rule into a test: a tool is correctly wired only when all three layers agree. A gap in either direction is a bug.

Layer 1
Schema
A dict in a tool list (TOOLS, DESKTOP_TOOLS, …). Assembled by _get_tools() and shipped to the API.
→
Layer 2
Dispatch
_execute_tool(block) matches block.name and routes it to a handler — or returns "Unknown tool".
→
Layer 3
Implementation
A do_<name>() method (or inline code) that does the work and returns a string or content-block list.
Two deliberate exceptions. run_command has no do_run_command — it routes to run_powershell() so it can pass through the safety gate. get_skill has no handler method — it is resolved inline inside dispatch. Both are intentional, not gaps.

02 Dispatch precedence

_execute_tool() is an ordered sequence of early-returns, not a flat lookup. Prefix-routed subsystems are tested before the native chain — which is why no native tool may begin with a mail prefix or contain __.

  1. block.name in _mcp_tools_by_name → do_mcp_call(name, input)
  2. name.startswith("gmail_"/"proton_"/"outlook_") → getattr(self, "do_"+name)(input)
  3. name == "manage_skills" → do_manage_skills
  4. name == "manage_prompts" → do_manage_prompts
  5. name == "run_command" → run_powershell (safety-gated)
  6. name == "csv_search" → do_csv_search
  7. name in {13 desktop tools} → inner if-chain → do_<name> (guarded by desktop toggle)
  8. name in {11 browser tools} → inner if-chain → do_browser_* (guarded by browser toggle)
  9. name == "get_skill" → inline on-demand-skill lookup
  10. otherwise → "Unknown tool: {name}" (catch-all)

Because MCP (1) and mail (2) are matched first, their namespacing is load-bearing: MCP tools are <server>__<tool> (double underscore) and mail tools carry a family prefix — neither collides with any native name.

04 Inherited MyAgent subsystems

SelfBot gains MCP and three mail providers by inheritance — class App(MCPMixin, GmailMixin, ProtonMailMixin, OutlookMixin) — imported optionally at module top and gated by _HAS_MYAGENT_TOOLS plus a per-subsystem _HAS_* capability flag. The mixin order matches MyAgent's exactly, preserving the _proton_*/_outlook_* helper-prefix anti-shadowing.

SubsystemCountNamesRouteGate
MCP runtime <server>__<tool> from mcp_servers.json do_mcp_call :514 MCP box + _HAS_MCP
Gmail 16 gmail_* — search/read/send/reply/draft/label/trash/… do_gmail_* (GmailMixin) Google box + _HAS_GOOGLE
Proton (IMAP) 16 proton_* — 1:1 mirror of Gmail surface do_proton_* (ProtonMailMixin) IMAP box + _HAS_PROTONMAIL
Outlook 16 outlook_* — 1:1 mirror via MS Graph do_outlook_* (OutlookMixin) Outlook box + _HAS_OUTLOOK

Runtime enum patching

Each mail tool declares an account parameter whose enum is a placeholder in the schema. _get_tools() deep-copies the list and injects the live account names (_get_google_account_names() etc.) before shipping — so the model only ever sees configured accounts, and an empty accounts file yields an empty enum (a clearer failure than dropping the tools).

Correctness note — MCP_TOOLS aliasing. SelfBot does from myagent.constants import MCP_TOOLS, binding its name to the same list object. mcp_mixin.py populates it with MCP_TOOLS.clear() / .append() — in-place mutation, never rebinding — so the runtime-discovered tools are visible through SelfBot's alias. A MCP_TOOLS = […] reassignment would have left SelfBot holding a forever-empty list. This is the subtlest wiring point in the system, and it is correct.

06 Execution model & safety gate

Parallel vs. sequential

When a turn requests multiple tools, stream_worker partitions them by original index into PARALLEL_SAFE = {"csv_search", "get_skill"} (run concurrently via ThreadPoolExecutor) and everything else (run one at a time, in order). Results land in a pre-allocated list keyed by original position, preserving the API-expected ordering.

This is deliberately conservative: MCP, mail, and web tools are network-bound and could safely parallelize, but SelfBot keeps them sequential. Correct and safe — just not maximally fast. Desktop/browser tools must be sequential (shared UI state).

run_command safety — two tiers

run_powershell() funnels every command through _check_command_safety(), which regex-matches against platform-specific lists:

OutcomeTriggerBehavior
blockedCOMMAND_BLOCKED match (Format-Volume, diskpart, rm -rf /, …)Rejected outright — never runs
confirmCOMMAND_CONFIRM match, pattern not bypassedModal dialog naming the matched pattern
skippedCOMMAND_CONFIRM match, pattern in _disabled_confirm_patternsRuns, emits a red ⚠ "Confirm bypassed" warning
safeNo matchRuns silently

The same _disabled_confirm_patterns set — editable via the Safety dialog — also gates the 5 destructive tools per mail family (*_send/reply/send_draft/trash/delete_label), which the mail mixins consult through mail_common.confirm_action. It persists top-level in app_state.json (SelfBot has no per-instruction store).

07 Findings

Cross-referencing all three layers plus the safety and execution paths. One documentation-drift item; no code defects.

PASSSchema ↔ dispatch ↔ handler are consistent

All 29 first-party schemas resolve to a handler, and every do_<name> method is reachable from a schema. No orphan schemas (which would return "Unknown tool") and no dead handlers.

PASSDynamic mail dispatch resolves via the MRO

Dispatch uses getattr(self, f"do_{block.name}") with no local mail methods — the 48 handlers live only on the inherited mixins. Spot-checks (do_gmail_search/trash, do_proton_trash, do_outlook_trash) all resolve. The do_mcp_call(tool_name, arguments) signature matches its call site exactly.

PASSImage-returning tools honor the tool_result contract

do_screenshot and do_browser_screenshot return a list of text+image blocks, and the loop assigns it straight to tool_result.content — which Anthropic accepts as either a string or a block list. Valid either way.

NOTEServer-side tools are unconditionally on

web_search and code_execution are appended to every request with no gating checkbox. Intentional for an Anthropic-only app, but it means every conversation carries their capability (and potential billing) — unlike the desktop/browser/mail groups, which are opt-in.

NOTEParallelism is conservative

Only csv_search and get_skill run concurrently. Network-bound MCP/mail/web tools are executed sequentially even though they'd be safe to parallelize. No correctness impact — purely a latency trade-off.
