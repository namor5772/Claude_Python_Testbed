# SelfBot — The two-instance duo: peer detection, shutdown, opener handoff, turn-taking

<!-- Moved verbatim from .claude/rules/CLAUDE_SELFBOT.md on 2026-11-10; that file, which loads with every SelfBot task, is now an index pointing here. Edit the contract here. -->

**Peer detection (cross-platform)** — `_poll_for_peer` (2 s cadence) arms auto-chat and shows instance 1's Auto button + Delay spinner when another SelfBot is running. Windows enumerates visible "Claude SelfBot" windows via pygetwindow; that library is Win32-only and reading another app's window title on macOS needs a Screen Recording consent, so `_macos_peer_pids` detects by **process** instead — a python executable with a `SelfBot.py` argument in `ps -axo pid=,command=` output (a SelfBot process IS a live window: a Tk failure kills the process, and a zombie's parenthesised ps command never matches). Fixed 2026-07-13; before this, the non-Windows branch hardcoded `peers = []`, so macOS never paired — no Auto button, no delay spinner, and no cross-instance injection (the `complete` handler only writes `selfbot_auto_msg.json` when `_auto_chat` is on). The Auto button itself is a `tk.Button` on Windows but a click-bound raised `tk.Label` on macOS: Aqua tk.Buttons ignore `bg`, which rendered the green/red state as invisible white-on-white.

**Graceful duo shutdown** — Pressing [X] on either instance stops auto-chat, waits for any active streaming to finish, saves both instances' chats, then closes the peer: `WM_CLOSE` messages on Windows, `SIGTERM` on macOS. `_handle_sigterm` (installed in `__init__`, macOS only — Windows gets this via WM_CLOSE) schedules `_on_close` onto the Tk loop, so a plain `kill`/`pkill` also gets the graceful close-and-save (the macOS analog of `taskkill` without `/F`); the `_closing` guard stops the peers from bouncing the shutdown back and forth. A peer SIGTERMed mid-stream finishes its reply first (the `_on_close` streaming wait), then saves and exits — verified live 2026-07-13. **Ungraceful peer death is covered by a watchdog in `_poll_for_peer`**: once an instance has been paired (`_ever_had_peer`, hoisted to set on any peer sighting), three consecutive peer-less polls (~6 s; enumeration-failure polls don't count, so a pygetwindow hiccup can't false-fire) mean the peer died without reaching `_finish_close`'s broadcast — crash, `taskkill /F`, or a model-driven self-kill via `run_command` (`taskkill`/`Stop-Process` are only CONFIRM-tier, so a confirm click or Safety bypass allows them). The survivor posts a ⚠ warning and runs the same graceful `_on_close` (finish streaming, save chat, exit), making "close one → both close" hold for every death mode, not just [X]. Added 2026-07-13 after a live duo session where instance 1's model force-killed its own process on request and instance 2 lingered solo. Note the dying instance's own final in-flight reply is unavoidably lost on a force-kill (no close-save runs; the 5 s periodic auto-save bounds the loss) — a model wanting a clean exit should use `taskkill` *without* `/F` (WM_CLOSE → full graceful duo shutdown, both chats saved).

**Opener handoff (2026-10-14)** — beside the per-reply `AUTO_MSG_FILE`, the duo passes ONE more thing, once per process: the human's opening line (`INJECT_FILE`, `selfbot_inject.txt`), because the partner window's own conversation starts with the REPLY and would otherwise never show what the human typed. Until 2026-10-14 the handoff assumed the conversation was always opened in instance 1 — instance 1 captured its first `send_message` text and only instance 2 polled — so a conversation opened in instance 2's window (all four duo chats of that day) went wrong: instance 1's first message was instance 2's OWN reply arriving through `_poll_auto_msg`, instance 1 handed that back at its first `complete`, and instance 2 printed its reply a second time, inline (`Nigel: Hi Shaun! …` under `Nigel:\nHi Shaun! …` — the user's report). Display-only — the API histories were clean — but the `.txt` transcript is a dump of the display. Now the handoff follows where the opener was TYPED: `send_message(from_peer=False)` captures `_first_message_text` only while no reply has completed and only for text typed here, either instance (`_poll_auto_msg` and `_auto_msg_delayed_send` pass `from_peer=True`; Enter / Auto-send / the duo's send delay keep the default); `_write_inject_file` writes `{from_pid, label, text}` once (it clears the capture) and nothing without an opener, called with the FIRST reply only and only when that reply goes to a partner — `check_queue`'s `complete` in the auto-chat branch, just ahead of the reply (the reply follows in 1 s, the partner polls both files every 0.5 s, so the opener lands above it), and `_toggle_auto_chat`'s release of a held first reply — so a solo window leaves no orphan file for a later instance 2 to show; both instances run `_poll_inject_file` from launch (the `from_pid` rule of the auto-message file: a file this instance wrote is the partner's to take), which shows a partner's opener only into a conversation not yet started (`not self.messages` — the second guard, which alone would also have hidden the duplicate), takes a file once, re-reads a half-written one (the old reader stopped polling for good on a parse error), and ends at this window's first completed reply or at `_closing`; `_finish_close` removes the file in both instances. The opener keeps its inline `label: text` look, so in either window it reads as the line above the first reply, as it did in instance 2. Not handled, deliberately: openers typed in BOTH windows within the same half second, before either window's busy mark is up (an opener typed in the second window while the first is answering waits and joins the first reply — **Duo turn-taking** below), and a handoff file left by a forced kill in the half second before the partner takes it. Pinned in `tests/test_selfbot_opener_handoff.py` (capture, writer, reader, the `complete` and toggle paths, two-window replays of the reported chat and of the instance-1 flow, wiring scans); the key tests fail against the pre-fix code.

**Duo turn-taking (2026-10-14)** — two fixes the README's self-chat guide turned up the same day. (1) **One pause for both windows.** Each turn waits for the RECEIVING window's `_send_delay` (`_poll_auto_msg` parks the partner's message in the box for it), but only the first window has the Delay(s) spinner, and the second kept whatever its own `app_state_2.json` held — so every other turn ran on a different pause (15 s and 5 s on the laptop that day). `_on_delay_changed` now saves the state file at once, and the second window's `_poll_for_peer` calls `_sync_delay_from_first` on every poll while a peer is present, before the pairing branch reads `_delay_seconds`: the first window's `delay_seconds` from `APP_STATE_FILE`, clamped 0–30, applied to `_send_delay` only while paired; an unreadable file (absent, or half-written — `_save_last_state` writes in place) keeps the current pause. (2) **One message in flight** (the user's choice of three, asked the same day). The one shared `AUTO_MSG_FILE` holds one message, so a message typed into a window while the other was still answering was sent at once, crossed that answer, and one of the two was lost. The obvious fix — a message file per direction — was proposed and rejected on analysis: nothing is lost, but the second message is never absorbed either, so the chat forks into two conversations running side by side, both windows always busy at about double the cost, until closed. Instead each window marks itself BUSY (`_set_busy`: `DUO_BUSY_PREFIX` + `1|2.flag`, its pid inside) from taking a message — `_poll_auto_msg` sets it before the message leaves the file, `send_message` for a paired typed send — until its answer is handed over: `_inject_response_to_other` clears it AFTER writing the message, so the partner never sees neither; a turn that hands nothing over (no text, Auto off → held, an `error`) clears it at once; `_toggle_auto_chat`'s release sets it again with `_pass_pending`; each window removes its own at close and at launch (a killed predecessor's). `_awaiting_partner()` — paired (`_auto_chat`), and the partner's mark is up, or the shared file holds a message either way, or this window's own reply is in the 1 s before its hand-over (`_pass_pending`, set at `complete`) — makes `send_message` keep a typed message in the box (`_held_for_partner`, one grey `tool_info` notice per hold; the box stays editable) and `_send_as_enter` skip the send delay's parking; `_poll_auto_msg` then sends the partner's message with the held text after a blank line, and a draft that was never sent is set aside (`_stashed_draft`) and put back by `_restore_draft` once the arriving message is sent, on both the immediate and the delayed path (the old code wiped it). It never holds in a solo window (a stale mark cannot block one), nor after a partner turn that handed nothing over (Enter then sends at once — nothing waits on a reply that will not come); slash commands are intercepted before the hold. An opener typed in the second window while the first is answering joins the first reply, below the first window's opener. `LaunchSelfBot.bat` deletes both marks with the other stale files and `.gitignore` covers `selfbot_busy_*.flag`. Pinned in `tests/test_selfbot_duo_turns.py` (30 tests; the behavioural ones fail against the pre-fix code). Adding it made the full suite abort, deterministically, in `tests/test_selfbot_voice.py`'s `RowTests`: a Tk object an earlier test left in a cycle was finalised on a dictation's worker thread (`Tcl_AsyncDelete`) once the two new modules had shifted the collector's timing — fixed with the repo's `gc.collect()`-on-the-main-thread pattern at that class's setUp and tearDown and `SetupDialogTests`' tearDown.
