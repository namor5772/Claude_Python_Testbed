**Toolbar "last pressed" highlight (2026-09-08)** — the top-row START / STOP / Instruction buttons (left to right in that order since 2026-09-21, at the user's request; Instruction came first before — they are CREATED in that order too, since creation order is Tab order, pinned by `ToolbarOrderTests` on the real `setup_ui`) are one group wired by `_track_toolbar_presses` (ui_mixin): each button's `command` is wrapped so a press first paints that button `TOOLBAR_ACTIVE_BG` (`#add8e6`, light blue — constants.py) with a bold face and puts the other two back to their resting look, then runs the real handler. Three invariants: (1) **nothing is repainted at startup** — the resting look is captured from the widgets themselves (`cget` of bg / activebackground / highlightbackground / font), so the buttons first appear exactly as created — and since the same day all three ARE created alike, with one shared `toolbar_font = ("Arial", 10)` in `setup_ui` (Instruction used to inherit `TkDefaultFont`, Segoe UI 9 on Windows, and STOP had been bold since MyAgent's first commit; the user asked for identical initial fonts), so at startup they are visually identical and only the pressed one ever goes bold. (2) **Only the weight changes** — the resting and bold fonts are `tkfont.Font` twins derived from each button's own font, never a hardcoded `("Arial", 10, "bold")`, so a per-button font choice would be honoured automatically (pinned by a test that tracks a `TkDefaultFont` button and checks its bold twin keeps Segoe UI 9). (3) **Presses only, not handler calls** — the wrapper sits on the button `command`, so the `-l` auto-launch's programmatic `_start_agent()` and the run-start / run-end `state=` toggles of START / Instruction in safety_mixin / event_loop_mixin never touch the paint; a disabled button can't be pressed (`invoke()` is a no-op on it), and a highlighted START stays highlighted while it is disabled for the run. **STOP is disabled whenever it can't be used but never LOOKS disabled** (same day, two user requests in a row: first "not greyed out", then "not pressable/focusable when it can't be used, without greying"): it is created `state="disabled"`, enabled only by `_start_agent`, and re-disabled by `_stop_agent` (a press) and by the run-end branches of `check_queue` — a disabled Tk button ignores clicks, Space/Return and `invoke()`, and Tab traversal skips it (`tk::FocusOK` rejects a `-state disabled` widget) — while its `disabledforeground` is set to its normal `fg` at creation, which makes the disabled rendering pixel-identical to the enabled one on Windows (Tk draws disabled text in `disabledforeground`, falling back to a stipple only when that colour is empty; relief and background are unchanged). Greying and disabling are two separate options, which is what makes this possible. macOS caveat: Aqua hands the button FACE to the OS, which dims an unavailable button on its own, so on the Mac the idle STOP may still look slightly faded. Pinned in `tests/test_toolbar_highlight.py`: `_stop_agent` / `_start_agent` on stubs toggle `state` only, and a static scan asserts every `_stop_button.config(` outside `ui_mixin.py` passes exactly `state="normal"` / `"disabled"` (nothing may restyle it) and that the creator copies `fg` into `disabledforeground`. On macOS Aqua the button FACE ignores `bg`, which is why `highlightbackground` (the frame around the native button) is painted too — there the active button shows as bold + a light-blue frame (3 px wide since 2026-09-15, because that frame IS the button's focus-ring area — see Keyboard operation (8)). Pinned in `tests/test_toolbar_highlight.py`, the one module that builds a real (withdrawn) Tk root — it skips itself where no display exists.

**Keyboard operation (2026-09-10)** — MyAgent is usable with no mouse. Tk already makes every control a Tab stop (creation order = Tab order, which is why the Skills Manager creates SAVE / DELETE / NEW left-to-right inside a right-packed frame, and the instruction editor creates its text area last); `myagent/keyboard.py` adds the rest, and every window builder uses it (pinned by a static scan in `tests/test_keyboard.py`, whose widget tests run on a real, transparent, focus-forced Tk root — a synthetic key event only reaches a window that holds the focus — and skip where no display will grant it). Invariants: (1) **Escape leaves a field and never closes a window that holds a draft** — `install_class_bindings` (once, in `setup_ui`) binds Escape on the Text / Entry / Spinbox / TCombobox / Treeview classes (the last since 2026-09-11, for the editor's Instructions list) to focus the next control and `break`, so inside a text box (where Tab types a tab) it is the safe way out, alongside Tk's own Ctrl+Tab / Ctrl+Shift+Tab; the Instruction Editor, the Skills Manager, (since 2026-10-30) the editor's Notes dialog and (since 2026-10-31) the Skills Manager's Description dialog deliberately have NO Escape-to-close (closing discards the draft; Alt+F4 is the explicit close — and since 2026-10-31 the two dialogs have no Close button either, the user's request: the text is their only control and [X] / Alt+F4 the close, as for their parents), while the Safety dialog (every toggle saved as it happens) and the confirm-command dialog (Escape = Deny) do. (2) **Return presses the focused button** through `tk::ButtonInvoke`, the same deferred (100 ms) press flash Space uses, so a disabled button ignores it exactly like a click. (3) **Alt+letter mnemonics per window** via `bind_mnemonics(window, {letter: widget})`: one `<Alt-KeyPress>` binding on the toplevel, buttons pressed / fields focused; letters are unique per window (duplicates raise). **No underline cue**: the first version underlined the letter on each button and label, and the user asked for the plain look back the same day (2026-09-10), so the letters live in the README's Keyboard operation tables — and, since 2026-10-31, in `MyAgent_Keyboard_Reference.txt`, the repo-root plain-text reference of every keypress (the three rules, Windows' own window keys, every window's Tab order and Alt+letter set, the end words, how each window closes, the walkthroughs, what only a mouse can do, and — section 21, rewritten 2026-10-31 from real keystrokes sent to a Tk window on the M4 Mac Mini — the Mac: Tk on aqua has NO Alt modifier (Option is `<Option-…>` / Mod2, Command `<Command-…>` / Mod1, and an `<Alt-…>` binding never fires there — Option+letter inserts the layout's accented character into a text box), so the whole mnemonic layer and the lists' Alt+Up / Alt+Down were dead on the Mac until that day. **Fixed the same day:** `bind_mnemonics` binds `mnemonic_sequence(window)` — `<Command-KeyPress>` on aqua, `<Alt-KeyPress>` elsewhere — and on aqua `mnemonic_letter` steps aside for a letter in `MAC_COMMAND_RESERVED` (a c v x z w q m h: the Edit menu, Close, Quit, Minimize, Hide) unless Shift is held, because the plain Cmd+C / Cmd+M reach Tk's binding AND copy / minimise (measured), so the same letters serve both platforms and the four MyAgent uses among them (A, C, M, V) are Cmd+Shift+letter on the Mac; `sectioned_list.py` binds `list_move_sequences(tree)` — Cmd+Up / Cmd+Down on aqua — and a wiring scan forbids any literal `<Alt-` outside keyboard.py. Cmd+W runs the WM_DELETE_WINDOW handler like [X], Cmd+M minimises, Cmd+` cycles the instance's windows, and Cmd+Q — which ENDED THE PROCESS without `_on_close` (measured; Tk calls `::tk::mac::Quit` when it exists, plain `exit` otherwise) — goes through `install_quit_handler(self.root, self._on_close)` in `MyAgent.py`, right after the protocol line, so [X], Cmd+W and Cmd+Q are one close (`tests/test_keyboard.py`: `MnemonicLetterTests`, `QuitHandlerTests`, the aqua Shift test, the wiring scan; SelfBot still lacks both — its `_on_close` is as skipped by Cmd+Q). The native Yes / No alert's keys could not be measured reliably), kept in step with the tables BY HAND: a change to a key, a Tab order or a close rule edits the window's README table and that file together — and the `underline` option is never touched (that version had also tripped over Tk's option-abbreviation matching — `cget("text")` on a combobox answers with `-textvariable` — which is worth remembering if a cue ever comes back). Mnemonics live on the toplevel's bindtag, so each window's set is independent and a dialog never triggers its parent's. (4) **Read-only panes are Tab stops** (`takefocus=1` overrides Tk's disabled-state skip) with a 1-px highlight ring as the focus cue, since a disabled Text shows no cursor — **and no scrollbar is one** (2026-09-26): Tk's fallback rule for a widget whose `takefocus` is unset (`tk::FocusOK`) counts any viewable, enabled widget whose class carries a Key binding, and Tk 9.0.3's Scrollbar class binds Page Up / Page Down, so on the Mac Tab from the output pane landed on its scrollbar instead of Voice Setup (`tests/test_voice.py`'s Tab-order test had failed there since it was written, 2026-09-20) and the same rule put every scrollbar created right after a text box in the path of Escape's `focus_next`; `install_scrollbar_defaults(root)` (keyboard.py, called with `install_focus_ring_defaults` at the top of `setup_ui`, before the first scrollbar exists) sets `*Scrollbar.takeFocus` to 0 in the option database on every platform — the intended order is the same everywhere, and where a scrollbar was never a stop nothing changes; an explicit `takefocus=` still wins, and none of the twelve `tk.Scrollbar`s (main window, editor ×3, the Notes dialog, Skills Manager ×2 and its Description dialog, Safety / confirm / Agent Request ×4) carries one. Pinned in `tests/test_keyboard.py` (`ScrollbarDefaultTests`, on a mapped transparent root — the rule asks whether a widget is viewable — plus the wiring scan). SelfBot carries a byte-identical in-file copy, called next in its own `setup_ui` (CLAUDE_SELFBOT.md, `tests/test_selfbot_focus_ring.py`); CSVEditor and TodoList need nothing — their `ttk.Scrollbar`s (class TScrollbar, no Key bindings) were never stops. (5) **Embedded checkbuttons need their own traversal** — `tk_focusNext` skips unviewable widgets, and a checkbutton scrolled out of the Safety dialog's Text is unmapped, so `link_embedded_checkbuttons` binds Tab / Shift+Tab / Down / Up on each to `see()` the target, `update_idletasks()` (which maps it) and focus it. (6) **Initial focus** is set after each window is shown: Instruction (main — the THIRD button since the 2026-09-21 reorder, and kept there deliberately: Return presses the focused button, so focus on START, now the first, would let a stray Enter on a freshly opened window start a run on whatever instruction is applied), the text area with the cursor at the end (editor), the list (Skills), the reply box (Agent Request — or its Mike button when the applied instruction's Auto-send box is ticked, since 2026-09-30: Enter then starts and ends a hands-free dictation, see Voice input rule 14; the spoken cue follows the Announce box, rule 15, since 2026-11-02), Deny (confirm), the first checkbox (Safety), Provider (Voice Setup — which, like the Section… prompt (`SectionedList.ask_section`), cancels on Escape outside a field: five small settings are no draft worth protecting), Upgrade model (Model Setup, the same Escape rule), Choose… (Other Setup — Escape cancels from anywhere: it has no field), the notes text with the cursor at the end (the Notes dialog, 2026-10-30 — a draft, so no Escape-to-close), the description text with the cursor at the end (the Skills Manager's Description dialog, 2026-10-31 — likewise). (7) The sectioned lists — the editor's Instructions list and, since 2026-10-31, the Skills Manager's SKILLS list — add their own keys (below): Enter on a page jumps to the text, Alt+Up / Alt+Down move the selected row — bound on the tree WIDGET with `break`, because a Tk pattern without modifiers (`<Up>`, the Treeview class binding) also matches Alt+Up, and the class tag would otherwise step the selection as well. (8) **macOS buttons get a focus ring Aqua draws** (2026-09-15, the "graphical artefact over Instruction" on the M4 Mac Mini): a focused `tk.Button` wears a ring `highlightthickness` wide, and under 3 Tk draws it itself — and Tk 9.0.3 / macOS 26 draws it shifted up-left by the parent frame's offset within the window, so a button whose frame sits within a button's size of the top-left corner (the toolbar's, at (10, 10)) shows only the ring's bottom and right edges — a stray black line struck through the label plus a tick at a corner, seen at startup because Instruction holds the initial focus — while a button further down gets no ring at all (a plain button placed on the root itself draws correctly, which is how the offset was found); from 3 up Tk hands the ring to Aqua, which paints the system's rounded blue one in the right place (probed live at 1 and 2: garbage or nothing; 3, 4, 6: the native ring; colour-matching the 1-px ring still left a grey line across the face; 0 removed it but left no cue at all). `install_focus_ring_defaults(root)` (keyboard.py) therefore sets `*Button.highlightThickness` to 3 in the option database when the windowing system is `aqua` — called FIRST in `setup_ui`, before any button exists, because the option database only fills options at creation (pinned by the wiring scan); an explicit `highlightthickness=` on a widget still wins, ttk buttons have no such option, and checkbuttons are untouched (their default draws nothing wrong, and no cue at all on the Mac). Windows / X11 draw their default ring correctly (the dotted rectangle) and are left exactly as they were. Mac side effects, deliberate: the toolbar's light-blue "last pressed" frame is 3 px (it is the same area) and every button is 2 px larger per side. Pinned in `tests/test_keyboard.py` (`FocusRingDefaultTests`, on a withdrawn root). SelfBot carries a byte-identical in-file copy, called first in its own `setup_ui` (CLAUDE_SELFBOT.md, `tests/test_selfbot_focus_ring.py`).

**Window geometry persistence (main window + every dialog)** — rebuilt 2026-08-29 after the main window kept coming back on the primary monitor of the dual-2560×1440 desktop. ONE mechanism in `state_mixin.py` serves all seven persisted windows (`GEOMETRY_KINDS`: main, editor, ps_safety, prompt, confirm, skills and, since 2026-10-30, notes — the Instruction Editor's Notes dialog — the on-disk key names inside a layout entry are unchanged, so existing files restore): `_remember_geometry(kind, win)` captures a window's geometry into a per-process cache, `_place_window(win, kind, default_size, parent=, min_size=)` positions a dialog before it is shown, and `_save_last_state` / `_load_last_state` move the cache to and from this instance's state file under the current layout key (`_get_monitor_config_key()` — every monitor's rect from Win32 `EnumDisplayMonitors` / macOS `CGGetActiveDisplayList`, sorted; instance N writes `agent_state_N.json`, so instances persist independently). Three Windows facts, all reproduced live, drive the capture guards in `_remember_geometry`: (1) **a maximized window's `wm geometry` is a chimera** — the ZOOMED size at the NORMAL position (`2560x1417+-723+73`); the old code saved it verbatim every 5 s and the next launch restored it as a 2576×1456 *un-maximized* window straddling both monitors, which Windows counts as living on the primary — THE user-visible bug. Now a zoomed window is never captured; `main_zoomed` is recorded and the last normal geometry kept, tracked as the root moves/resizes by `_bind_geometry_tracking` (root `<Configure>`, filtered to the root's own events since the binding fires for every descendant), and the restore is `geometry(normal)` then `state("zoomed")`, which maximizes on the monitor of the normal position. (2) **A never-mapped root reports `1x1+X+Y`** until Tk's first idle pass, so the save in `__init__` used to write a junk size the next launch rejected as too small — capture requires `winfo_ismapped()`. (3) An iconified window still holds its normal geometry but is left alone so a minimize-from-maximized close restores maximized. `_geometries_for_save` writes this layout's entry only once something real was captured in this process (`_geometry_dirty`) — a GUI window that never showed passes the file's entries through untouched (possibly under a different key if a monitor came or went mid-run) — and a `--headless` run writes no state file at all since 2026-09-28 (see Headless mode). Saves are atomic (mkstemp beside the file + `os.replace`): the save runs every `PERIODIC_SAVE_MS` (10 s since 2026-10-08 — the user's request, the chats in OneDrive making every rewrite a re-upload; 5 s before — constants.py, the one tick behind both `MyAgent.py`'s first schedule and `_periodic_save`'s reschedule, which also autosaves the chat when the message count changed; pinned in `tests/test_periodic_save.py`), and a truncated file at a kill or power cut read back as no state. Restore: `_select_geometry_entry` takes this layout's entry, else the legacy flat fields, else the most recently saved layout (`saved_at`) whose main-window position is still visible here — a monitor that dropped off the bus, or a first launch after rearranging, keeps the window where it was rather than resetting to the primary; `_apply_geometry_entry` also migrates a legacy chimera entry (no `main_zoomed` key, width equal to a monitor's) to a maximized restore at the default size. **External window-manager reclaim (FancyZones et al.)** — added 2026-08-29 after the persistent "opens on screen 2 with a brief flash on screen 1" report on the same desktop turned out NOT to be MyAgent moving the window (grep confirms `self.root` geometry is set only in `_apply_geometry_entry`) but **PowerToys FancyZones** repositioning it just after it maps: FancyZones was running, unexcluded, with `openWindowOnActiveMonitor` + `appLastZone_moveWindows` on, so a new window is yanked to the active monitor / its last zone. This is *exactly* why the dialogs behaved and the main window didn't — every dialog already re-asserts its geometry on show (`after(100ms)` / withdraw→deiconify), the main window did not. Fix: `_apply_geometry_entry` records the restored geometry in `self._reassert_geo`; `_start_geometry_reassert` (called from `__init__` after `_load_last_state`) opens a `REASSERT_WINDOW_SECS`=1.5 s arm window and schedules fallback `after()` checks; `_maybe_reclaim_monitor` — driven by the root `<Configure>` (so it fires the instant the mover acts) and those fallbacks — re-applies the restored geometry **only when the window's centre has drifted to a DIFFERENT monitor** (`_monitor_index_of_center`) than it was restored to, and **only inside the arm window**. So an external cross-monitor yank right after launch is undone within a frame, while a same-monitor nudge, or ANY deliberate move after ~1.5 s, is never fought (a maximized restore and a withdrawn/headless root are also skipped). Live-verified: a simulated mover (SetWindowPos to the secondary monitor at launch) was reclaimed to the restored monitor in ~0.1 s, and a later move to the secondary monitor was left alone. **LaTeX to Unicode conversion** — Assistant text is converted to Unicode after each streaming segment via `_post_process_latex()`, which walks `tag_ranges("assistant")` and applies `_latex_to_unicode()` only to assistant-tagged text (so tool_info filenames/paths aren't mangled). The static converter handles all delimiters (`\( \)`, `$ $`, `\[ \]`, `$$ $$`), *braced* super/subscripts only (`^{...}`/`_{...}` — bare `^x`/`_x` left alone to avoid filename false positives), Greek letters, operators, `\frac{a}{b}`→`a/b`, functions, arrows, set notation, with unrecognised `\command` patterns falling back to backslash-strip. Since 2026-09-28 every alphabetic command is replaced only as a WHOLE command (a `(?![A-Za-z])` lookahead) and the sizing delimiters (`\left` / `\right` / `\big`…) go first: before, `\le` turned `\left(` into `≤ft(` and `\in` turned `\inf` into `∈f`. Every lone `$` is stripped, currency included ("$5" → "5") — accepted for prose; text that must survive verbatim (the Agent Request) wears its own tag. A `post_process_latex` queue message fires after each provider call returns text, and during `complete`.

**Multi-instance support** — Multiple instances run at once; each claims the lowest free number via lock files (`agent_lock_N.lock` holding the PID). Instance 1 uses `agent_state.json`, 2+ use `agent_state_N.json` for independent persistence. Stale locks (crashed PIDs) are detected via `OpenProcess` + executable-name verification (`GetModuleBaseNameW` confirms `python.exe`/`pythonw.exe`, guarding against recycled PIDs) and a command-line check for `MyAgent.py`, and reclaimed. The command line is read straight from the process since 2026-09-28 (`_win_process_cmdline`: `NtQueryInformationProcess`, class 60, which needs only query-limited access — `wmic`, which this used, is gone from current Windows 11 builds, and its failure fell through to "accept the exe name", so ANY python.exe that reused a stale lock's PID held the slot and the next launch became instance 2); an unreadable command line keeps the exe-name answer. A lock holding THIS process's own PID counts as stale when its mtime predates the process (`_PROCESS_STARTED`) — a crashed predecessor's PID that Windows handed us — while one written since is a live claimant's (the parallel-children tests model siblings as threads sharing one PID). The title bar shows `My Agent (N)` for 2+. **`_finish_close` releases the lock the moment `agent_state.json` is written — BEFORE the browser/MCP teardown and chat autosave** (`event_loop_mixin.py`, ordering locked by `tests/test_close_lock_order.py`). This is load-bearing for the single-instance close-then-relaunch case: releasing last (after a browser-automation instance's multi-second cleanup) meant a normal-speed relaunch found `agent_lock_1` still held, claimed instance 2, and restored from `agent_state_2.json` — so the window reopened on the *wrong monitor / stale size*, intermittently. It presents as a geometry bug (see **Window geometry persistence**) but the geometry layer is correct; the cause is the instance-slot race. Live-verified 2026-08-29: pre-fix an immediate relaunch spawned `My Agent (2)` on the secondary monitor, post-fix every delay reclaims instance 1 on the saved monitor. A redundant release at the end stays as an idempotent safety net. Since 2026-09-28 every step of `_finish_close` runs through `_close_step`, so one that raises (a browser teardown, an MCP shutdown, the chat autosave) is reported — to stderr where there is one — and the rest still run, the root's `destroy()` included: before, the first exception skipped everything after it and left a windowless process holding its lock.

**State restore fallback** — `_restore_model_params()` checks the saved model exists in the saved provider's model list — or, since 2026-09-28, among the ids that provider's live fetch SERVES but the picker hides (`helpers.note_served_models` → `_served_model_ids`, filled by the Anthropic / OpenAI / Gemini / xAI fetchers): a pinned model announced for retirement leaves the picker at once yet still runs until the provider pulls it (the retirement policy), and the fallback had been silently re-pointing such instructions at the default; it now keeps the model with a "hidden from the model picker" warning. On mismatch (e.g. an auto-save race pairing an Anthropic model with the OpenAI provider, or the saved provider's API key missing from the launching environment), it falls back to the provider's curated default via `_default_model_for_provider()` — NEVER `available_models[0]`: fetched lists are sorted, and lexicographic-first can be a terrible pick (xAI's sorts to the pinned `grok-4.20-0309-non-reasoning`, which is what a Heartbeat-launched FNE run silently ran on 2026-07-25 when its plist lacked `MOONSHOT_API_KEY`). Both drift warnings (provider unavailable / model fallback) are queued immediately AND stashed in `self._model_drift_warnings`, which `stream_worker` re-posts at run start — required because `_start_agent` clears the whole output window right after an `-l` auto-launch restore, erasing anything queued during it (that clear is why the FNE incident left zero visible trace in the window or the saved transcript). Corollary for ops: every NEW provider's API key must be added to every launchd plist / scheduled task that embeds keys, or instructions saved for that provider silently drift.
