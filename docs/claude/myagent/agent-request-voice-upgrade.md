**Agent Request over Telegram (2026-10-26)** — a run that Heartbeat's resident Telegram listener launched carries `--relay-dir`, and every Agent Request of such a run can be answered from the phone. Since 2026-10-31 a run `run_instruction` launched with `answers` carries `--relay-dir` too — a temp folder of its own — and the PARENT run answers it: `_relay_serve` (skills_mixin) runs once per second of the waited poll loop, or on a daemon thread (`_relay_server`) for a fire-and-forget child, and gives the open request — one whose seq has not been served — the next unused entry of the list, or, the list spent, the EMPTY reply, which stops the child as an empty reply typed at the PC does (`[]` therefore stops a child at its first question, so an unattended fan-out never leaves a dialog on the desktop); a request the PC answered first (answered.json, `take_answered`) is recorded and consumes no answer; the folder is removed when the child exits on every path (launch failure, STOP, timeout, the normal end, the thread's end), and the waited report lists each question with what it got (`_relay_report`). `prepend_text` (--prepend-file, a temp file like extra_text's) and `show_window` (--show-window, after --headless only) joined the same day; `tests/test_run_instruction_answers.py`. The dialog is unchanged in look and in the PC's use of it; what was added is a third hand on the one lever every reply already pulls — `on_inject`, which Enter and Mike's Auto-send call. `do_user_prompt` writes the dialog's text to the relay folder as the dialog is built (`_relay_request`: `relay.write_request`, a per-run `seq` from 1), arms a `RELAY_POLL_MS` (500 ms) `after` poller on the dialog that reads `relay.read_reply(seq)` and, when a reply for THIS seq has landed and no dictation is in flight, drops the text in the reply box and calls `on_inject`; `_capture_and_close` — reached by Enter, the poller and the [X] alike — cancels the poller and settles the request (`relay.clear`, plus `relay.mark_answered(seq)` when the PC answered, so the listener can withdraw the question in the chat). MyAgent never reads Telegram itself: the listener owns the bot's `getUpdates` connection, and a second reader would consume its messages, so the handoff is three files in the run's folder (`myagent/relay.py`: `request.json` / `reply.json` / `answered.json`, each a temp file + `os.replace`). On the listener's side the per-run watcher thread (which already waits on the child for the result reply) ticks the folder once a second — posting "❓ <name> asks: …" and marking the chat as awaiting that run — and the chat's next text message is written back as the reply (`telegram_handle_update`, before the trigger parse; `/help` and media are not replies; several open questions answer oldest first; a reply after the PC answered is refused with a note). First answer wins, the other side is told. Convo mode works unchanged (each turn a new seq), and the end words `quit` / `exit` are read from the relayed text exactly as from typed text. Text only — a photo from the phone is answered with the usual kind hint, never attached. A run without a relay folder (the window, a hand launch, a one-pass Heartbeat with no listener watching) behaves exactly as before: `_relay_request` returns None and nothing is armed. Pinned in `tests/test_relay.py` (the protocol), `tests/test_agent_request_display.py`'s `RelayDialogTests` (the REAL dialog over a relay folder: a reply from the folder answers it with no answered marker, a stale seq is ignored, a typed reply or a dismissal leaves the marker, no folder writes nothing) and `tests/test_heartbeat.py`'s `RelayHandleTests` / `RelayTickTests` / `WatchRunRelayTests`.

**Agent Request in the output pane (2026-09-22)** — the message the Agent Request dialog shows is also written into the main window's output pane, under an **Agent Request:** heading in the look of the **Agent:** text, followed by the reply's **You:** paragraph (the user's request: until then the pane — and so the saved `.txt` transcript, which is a dump of the pane — recorded the ANSWER but never the question, which lived in the dialog alone and was gone once answered). Invariants: (1) **Emitted inside `do_user_prompt`**, as a `user_prompt_request` queue message put BEFORE `root.after(0, ask)` — the twin of the `user_prompt_echo` the same function puts after the wait. One place covers both callers: the `user_prompt` tool (`_execute_tool`, the model's text) and Convo mode (`stream_worker`, the stock *Reply, or type empty / 'quit' / …* text), and any future one. **The pane line is the message ALONE; the dialog's box and the relayed request carry a `preface` above it (2026-10-28, the user's request)** — `do_user_prompt(message, convo, preface=)`: Convo mode passes the reply just streamed (`full_text`), the `user_prompt` branch what its turn said before the call (`self._turn_text`, which `stream_worker` sets from `full_text` before the turn's tools run) — `shown = preface + blank line + message` fills the box (14 lines tall with a preface, 6 without; a remembered geometry still wins) and is what `_relay_request` writes, so the chat's *❓ asks:* carries the reply too and a run can be followed from the phone or in headless mode, where the pane is not in view; the pane keeps the question alone because the reply is already its Agent: paragraph. Pinned in `tests/test_convo_exit.py` (both callers' prefaces, the worker's ordering) and `tests/test_agent_request_display.py` (the real box's text and height, the queue, the relayed text). It is a queue message because `do_user_prompt` runs on the streaming worker and only `check_queue` may touch the pane; FIFO order puts it after the turn's streamed text and the Activity-gated *Requesting user input...* line, and the dialog does not block it — `ask` builds the window and returns, so the 50 ms poll keeps running under the dialog's grab and the text is in the pane while the dialog is still up. Not gated by any checkbox (it is conversation, not activity); headless runs queue it too, which is what puts it in an unattended run's transcript. (2) **The body wears its OWN tag, `agent_request` — the `assistant` look (`#2e7d32`, the pane's font), never the `assistant` tag.** `_post_process_latex` rewrites EVERY `assistant` range on each pass — lone `$` stripped, `\word` loses its backslash, `{…}` its braces — acceptable for prose, wrong for a question the user acts on: "Pay $250.00 to …?" (the payment skill's mandatory pre-Confirm prompt) or a `C:\Users\…` path would read differently in the pane and the transcript than in the dialog that was answered. One tag, not a pair, for a second reason: that pass re-inserts a range with the single `assistant` tag, so a combined tagging would not survive it anyway. The heading reuses `assistant_label` (nothing reads that tag back). (3) **Paragraph spacing is computed, not hardcoded**: `_chat_insert(..., blank_line_first=True)` → `chat_mixin._ensure_blank_line`, which adds only the newlines missing for exactly one empty line above the heading (none on an empty pane; a lone `"\n"` already is one). The request ends `"\n\n"` like the instruction and the echo, so a DISMISSED dialog — no echo is queued for it — still leaves a blank line before the next **Agent:**; the echo moved from a hardcoded leading `"\n"` to the same rule, which is byte-identical in every existing flow (it differs only where the pane already ended in a blank line, where the old form gave two). (4) Trailing whitespace is stripped for display, an empty message shows the heading alone, and the content goes through `str()` — it is the model's tool input, a sloppy local model can send `null`, and `check_queue` swallows exceptions, so a `None.rstrip()` would drop the paragraph silently. Known and accepted: a model that streams its question as text AND passes it to `user_prompt` shows it twice (under **Agent:** and under **Agent Request:**) — the pane reports what happened. SelfBot has no such dialog and is untouched. Pinned in `tests/test_agent_request_display.py`: `PaneTests` on the REAL `setup_ui` pane (layout strings, tags, the look compared option by option with `assistant`, the LaTeX pass with the agent's own text as the control, `_ensure_blank_line`'s cases, the echo's spacing unchanged), `DialogTests` on the REAL dialog — transparent, inside a real `mainloop()` with `do_user_prompt` on a worker thread, because tkinter refuses a call from another thread unless the main thread is IN mainloop (`update()` does not count; `_tkinter`'s `WaitForMainloop`) — dismissed through its `WM_DELETE_WINDOW` handler (queue = the request alone) and answered with a synthetic Return (queue = request, then echo; skips where the display grants no focus). Live-verified 2026-09-22 with a zero-token scratchpad harness (real main window + real `check_queue` + real dialog, scripted model turns, screenshots).

**Agent Request image attachments** — the `user_prompt` dialog (safety_mixin `do_user_prompt`) carries the instruction editor's Attach Images / Remove Selected controls (file picking + compression shared via chat_mixin `_pick_image_files`, which `attach_image` now wraps). The return type stays a string: attached images travel on `self._prompt_attached_images`, popped exactly once by the caller via `_take_prompt_images()` (safe because the streaming thread blocks on the dialog and reads synchronously — popping prevents stale images leaking into a later prompt). Compression (`_compress_image`, shared with the editor's Attach Images) applies a photo's EXIF orientation before the JPEG re-save drops the tag, and converts the modes JPEG cannot store — LA, 16-bit `I;16` (scaled to 8 bits, since a plain convert clips it white) — since 2026-09-28; before, such a PNG failed the whole attach and a portrait phone photo reached the model sideways. Both consumer paths wire them as Anthropic-style image blocks via `_prompt_image_blocks()`: the `user_prompt` tool path returns a `[{text}, {image}…]` tool_result list (the screenshot shape, so every provider translator already handles it) and the Convo-mode path appends a list-content user message (the instruction-images-at-start shape). An image-only reply is substituted with "[See attached image(s)]" so it doesn't trip the empty-reply agent stop; the user_prompt_echo names the attached files. **Ctrl+V paste** (both the dialog's response box and the instruction editor's text area, `<Command-v>` added on macOS): the binding calls chat_mixin `_grab_clipboard_images` — `PIL.ImageGrab.grabclipboard()` behind a pure, tested `_clipboard_content_to_images` that handles its three result shapes (a bitmap → `pasted_<HHMMSS>.png`; a copied-files list → recognised image types kept, others skipped silently; None → `[]`). A non-empty result attaches and returns "break"; an empty one returns None so Tk's default text paste proceeds — text pasting is untouched. When Pillow sees nothing on Windows, a **CF_HTML fallback** kicks in (`_get_clipboard_html` — ctypes with explicit `c_void_p`/`c_size_t` restypes, since 64-bit handles truncate under the ctypes `c_int` default — then `_html_to_image_tuples`): web apps like OneDrive Photos copy an `<img>` REFERENCE instead of a bitmap, so the first `<img src>` is resolved — a `data:` URI decodes locally, an http(s) URL downloads best-effort (10 s timeout; may fail if the URL needs auth cookies) — and the bytes are **fully decoded with PIL before attaching** (`_normalize_image_bytes`: `Image.open` + `load()` — a magic-number sniff alone let a truncated download reach xAI as a 400 'Invalid PNG image', live 2026-08-24; exotic variants like 16-bit PNG re-encode to plain 8-bit PNG; `_fetch_image_url` loop-reads to EOF because a single `read(n)` can return short on chunked responses); anything that doesn't decode returns [] and paste stays a no-op rather than attaching garbage. The magic sniff (`_sniff_image_media_type`, RIFF≠WEBP guarded) remains only as the PIL-less fallback. Live-probed 2026-08-24 (real dialog driven end-to-end, incl. a real clipboard bitmap through the real Ctrl+V binding and a text-clipboard fallthrough); helpers characterized in `tests/test_prompt_images.py`.

**Voice input (2026-09-19)** — `myagent/voice_mixin.py` (mixin #24) lets a reply be dictated: the Agent Request dialog's **Mike** button is a toggle (press → red `■ Stop` + timer + level meter → press again → *Transcribing…* → the transcript is inserted into the reply box — or, with the **Auto-send** box right of Mike ticked, sent that moment as if Enter had been pressed: rule 14, 2026-09-23), and **Voice Setup** edits the settings and tests the chain — a button at the **bottom left of the MAIN window, left of the Debug checkbox** (Alt+V) since 2026-09-20: it began beside Mike, and the user moved it the next day because that dialog exists only while a run is asking something. `do_user_prompt` only embeds the row: `_voice_build_row(dlg, resp_text, self.dictation_auto_send, lambda: on_inject())` returns `(frame, mike_btn, auto_send_btn, dictation)` — the lambda because `on_inject` is defined after the row is built and is looked up only when a transcript lands (rule 14) — built BEFORE the image row so Tab order stays visual, and the dialog keeps ownership of three things — the ONE `bind_mnemonics` call per window (a second call would replace the binding, so `m` and `a` are merged into the existing `i` / `r` map), the Enter rule in `on_inject` (`recording` → `dictation.toggle()`, i.e. Enter ENDS the recording; `transcribing` → swallowed; both `break`, because sending mid-dictation would lose the speech), and `dictation.shutdown()` in `_capture_and_close` (a `<Destroy>` binding on the toplevel is the backstop for any other destroy path). Architecture invariants:
1. **One state machine, two buttons** — `_VoiceDictation(app, window, button, status, get_config, on_text)` runs idle → recording → transcribing → idle for the Mike button (`get_config` = the saved file, `on_text` = `_voice_insert_into` the reply box) and for Voice Setup's Test button (`get_config` = the dialog's UNSAVED fields, `on_text` = its read-only transcript box), so a provider / model / microphone can be tried before it is saved. The button's resting look is captured from the widget by `cget` and restored verbatim (the toolbar-highlight rule); the recording look is `VOICE_RECORDING_BG` (`#c62828`, constants.py) + white text, with `highlightbackground` painted too for Aqua, whose button face ignores `bg`. **Red means the stream is open**: the look changes only after `recorder.start()` returned, because the first press of a session pays the import below — the status line says *Opening the microphone…* meanwhile.
2. **Two threading rules.** (a) EVERY PortAudio call — the import, the device scan, stream open / close — runs on the Tk thread: PortAudio's Windows backends initialise COM on the initialising thread, and the main thread is the only one that is always there. The block callback runs on PortAudio's own thread and writes nothing but `_VoiceRecorder` fields. (b) Only the API call runs on a worker (`_work`), which touches no widget and hands `(job, text, info, error)` back through a `queue.Queue` that `_poll` drains via `after(80)` — the app-wide rule. A **job counter** makes delivery exact: `shutdown()` bumps it, so a transcript that lands after the window closed is dropped; `shutdown()` itself touches NO widget, because a toplevel's `<Destroy>` arrives after its children have died. The first poll is scheduled, never run inline, so the *Transcribing…* state always gets an event-loop pass (an instant fake API otherwise skipped it — found by the tests).
3. **`sounddevice` is imported at the first press, never at startup** — `_voice_sd()` is the single door (the `_excel_app` pattern: lazy import + the `pip install sounddevice` hint as a RuntimeError the status line shows). Measured 2026-09-19: the first PortAudio initialisation is ~460 ms on Windows (four host APIs), which every launch — the 5-minute headless Heartbeat children included — would pay for a feature only an interactive reply uses; a RE-scan (`_terminate` + `_initialize`) is ~22 ms, so `_voice_sd(rescan=True)` runs at every press and at Voice Setup open, and "system default" follows a headset plugged in mid-session. The rescan is skipped while `_VoiceDictation.live` (the app-wide open-stream count) is non-zero — terminating PortAudio would kill the stream — and it always attempts `_initialize` even if `_terminate` balked. Pinned by a static scan: no module-level `import sounddevice`.
4. **Capture** — `_VoiceRecorder`: `RawInputStream` (no numpy needed), 16 kHz mono int16 (what speech models work at; 1.9 MB/min), falling back to the device's native rate where the host API will not resample (the WAV header carries the rate); in memory only, never on disk; `full` at `VOICE_MAX_PCM_BYTES` = 24 MB (12.5 min, under the 25 MB upload cap) makes `_tick` end the recording by itself. Microphones are listed from ONE host API — the default one (MME on Windows, which resamples by itself; PortAudio otherwise lists every device four times: MME, DirectSound, WASAPI, WDM-KS) — and saved by NAME (`_voice_resolve_device`), since indices shift whenever a device comes or goes; a saved name that is absent today falls back to the default with a note. MME truncates names to 31 chars — cosmetic, and stable.
5. **Never send nothing** — a recording under `VOICE_MIN_SECONDS` (0.4 s, a slip) or whose peak is under `VOICE_SILENCE_PEAK` (50 of 32767) stops at a status message and is not sent. The threshold was measured on this laptop's noise-suppressed array: a quiet room idles at peaks of 2–50, ambient activity reaches 100–300, speech runs to thousands; exact zeros mean muted / denied. The message therefore says *only silence was recorded* (true in every case) rather than claiming a dead microphone — the first wording did, and a live microphone in a quiet room proved it wrong the same day. Silence is where speech models hallucinate a "Thank you."; `gpt-transcribe` returned empty text on ambient noise (status: *No speech recognised*).
6. **OpenAI path** (`/v1/audio/transcriptions`, the existing `openai_client`, 90 s timeout): live-probed matrix 2026-09-19 — `language` (one ISO code) and `prompt` are accepted by all four models (`gpt-transcribe`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe`, `whisper-1`; the docs' claim that gpt-transcribe rejects `language` is wrong); `languages` (several codes) + `keywords` via `extra_body` are gpt-transcribe ONLY — the 4o pair answers `The 'languages' parameter is not supported`, and **whisper-1 answers a bare `Invalid request.` with `param: None`**, so the chat models' "parse the rejected parameter out of the 400" ladder cannot work here. Hence `_voice_openai_params` decides per family up front (`VOICE_OPENAI_KEYWORD_PREFIXES`; the rest get one `language` — omitted when several codes are configured, since pinning a multilingual speaker is worse than auto-detect — and the hint as `prompt`), and the one reactive rung is blunt: any `BadRequestError` with optional params → resend the audio alone, with a note in the status line. `_voice_is_stt_model_id` filters `models.list()` to file-transcription ids (drops `realtime` / `-live-` / `diarize` and dated snapshots); `_voice_order_models` puts the curated ids first.
7. **Google path** (`generateContent` + an audio part, the existing `gemini_client`): `gemini-3.5-transcribe` is the dedicated model and the Google default — it rejects a system instruction (`Developer instruction is not enabled for this model`) and any `thinking_level` (both HTTP 400), and **returns its transcript in a part field, `audioTranscription.text`, that google-genai 1.67.0 does not model** (the part comes out of the SDK empty — `"parts": [{}]` — so `response.text` is None on an HTTP 200 that did carry the transcript; seen by comparing the SDK object with a raw REST call). `_voice_transcribe_gemini` therefore always sets `should_return_http_response=True` and `_voice_gemini_text` reads the transcript from the RAW JSON body — which serves the chat tiers' ordinary `text` parts too (thought parts skipped, first candidate only). Do not "simplify" this back to `response.text`, and do not upgrade the SDK for it. Request shapes step down one per 400: `tuned` (system instruction + temperature 0 + `thinking_level: low` — `minimal` is a 400 on 3.8-flash) → `untuned` (system instruction only) → `plain` (instruction folded into the user text); a dedicated model (`VOICE_GEMINI_DEDICATED_SUBSTRING` in the id) starts on `plain` and sends **the audio and nothing else, whatever is configured**: the 2026-09-20 audit showed it reads NO text part at all — a guard instruction, a language, a vocabulary list, before or after the audio, changed not one byte of its output — so its hints are not sent, its steerability cannot be fixed from our side, and its note in Voice Setup says both. `VOICE_GEMINI_SYSTEM` keeps a chat tier from ANSWERING a question it hears, but the audit's spoken COMMANDS got past it (flash-lite obeyed 2 of 7); `VOICE_GEMINI_GUARD`, a text part placed **BEFORE the audio**, took that to 0 of 7 (after the audio: 1), so chat tiers get `[guard + hints, audio]` in that order — wiring kept for a hand-edited config only, since the audit removed the chat tiers from the picker (rule 11). The picker lists live ids containing `transcribe` that support `generateContent` (the bidi-only `-live` one falls out), minus `VOICE_UNSUITABLE_MODELS`; because `transcribe` also joined `GEMINI_NON_AGENTIC_SUBSTRINGS` the same day, the model no longer appears in the main chat-model picker, where it could never run the agent loop.
8. **Settings are persistent, per-user, and NEVER part of an instruction** (the user asked for exactly this to be confirmed, 2026-09-20) — nothing in `instructions_mixin` / `state_mixin` / `skills_mixin` (`manage_instructions`) / `streaming_mixin` / `datapaths` / `Heartbeat.py` mentions voice (pinned by a static scan, `IndependenceTests`), so loading, applying or saving an instruction cannot touch them and they are absent from the instruction entry and the `applied_instruction` snapshot alike. The ONE dictation setting that IS per instruction is the Auto-send box (rule 14, 2026-09-23, the user's request): it says what the dialog does with a transcript, not how one is made, so it lives in the entry as `dictation_auto_send` — a key with no "voice" in it, so the scan still holds, and a second scan in the same class pins that every persistence site names it. `get_config` is `_voice_load_config`, i.e. the file is re-read at EVERY Mike press: a Save takes effect at once, in this instance and in any other running one, no restart (live-verified by rewriting the file between two presses). The file: `~/.config/myagent-voice/config.json` (`{provider, models: {OpenAI, Google}, language, hint, device}`; one model remembered PER provider so flipping the provider in the dialog loses nothing), sanitised on every load (`_voice_sanitize_config`: any JSON → a complete dict), saved atomically (mkstemp + `os.replace`). NOT `agent_state.json`: instance N and every headless child have their own state file, and a microphone chosen once must hold in all of them. API keys stay in the environment; the dialog only reports whether the provider's client exists (`_voice_key_status`).
9. **Cost is shown, never logged** — `VOICE_PRICING_PER_MIN` (constants.py; OpenAI's published per-minute estimates and xAI's $0.10/hour batch rate, longest prefix) × the locally known duration gives the `≈ $0.0004` in the status line; an unpriced id, and every Gemini model (audio input is a separate price column this table does not carry), shows no cost rather than a wrong one. A transcription is deliberately NOT written to the API cost log: each of its lines belongs to one chat provider / model, and the log is analysed per model. `MyAgent_Pricing.txt` carries the table for the audits.
10. **Voice Setup** (`_voice_setup_from_main` → `_open_voice_setup(self.root)`, modal over the main window like `_ask_section` over the editor: `wait_visibility` → `grab_set` → `wait_window`, a nested event loop in which `check_queue` keeps polling, so a run streams on underneath; placed by `_place_window` under the unpersisted kind `voice_setup`, i.e. centred on its parent — and then handed a POSITION-ONLY geometry (`+X+Y`), so Tk keeps sizing it from its content: the user cannot resize it, and under a fixed size a status message wrapping onto more lines would push Save / Cancel out of the window). In the Agent Request dialog the status line sits BESIDE the Mike button: that dialog's size is the user's saved one (567 px wide on one layout), where the longest message is five lines beside one button — while Voice Setup sat there too it was eight beside the pair, and went under them for that day. **One at a time**: `_voice_setup_dialog` on `self` makes a second open lift the first instead of nesting — the grab normally guarantees that, but an Agent Request arriving mid-setup takes the grab for itself (`do_user_prompt` always `grab_set`s), and once it closes the main window's button is pressable again with the setup dialog still up. The reverse is the move's one cost: while an Agent Request is open its grab makes the main window unclickable, so Voice Setup cannot be reached mid-request — typing still works, and the dialog's messages name "Voice Setup (main window)" so nobody hunts for it there. The rescan at open is skipped while any stream is live (rule 3). **Main-window placement** (`ui_mixin.setup_ui`, row 2): a 5-column grid — button · weighted gap · checkbox cluster · weighted gap · EMPTY column in one `uniform` group with the button's — keeps the six checkboxes centred on the WINDOW exactly where they were (the mirror column matches the button's width with nothing measured); the button is created before the checkboxes (Tab order = creation order: output pane → Voice Setup → Debug … Diag). Because three of the user's saved monitor layouts are narrower (638–791 px) than the ~798 px the pair needs side by side at 150 % scaling, a `<Configure>` handler re-grids the cluster onto the line BELOW the button when `_bottom_row_stacked` says so (below, not above: the button was created first), and back when widened — without it Diag fell off the right edge (grid never shrinks a weight-0 column; the overflow is clipped on the right). Pinned by `MainWindowButtonTests`, which run the real `setup_ui` on a stub with every assertion relative to the widgets' own requested widths (any DPI, either OS); note a Frame only knows its requested width after an idle pass — the first cut of that test read it too early and got 1. The microphone list is read synchronously on the Tk thread (rule 2a); the live model lists are fetched once per session on a worker and drained through a queue into `_voice_models_fetched`. Inserting follows Tk's own typing rule (`tk::TextInsert`): at the cursor, replacing the selection only when the cursor is inside it; `_voice_spaced` sets the transcript off from a word on either side but not from an opening bracket before or closing punctuation after.
11. **The 2026-09-20 suitability audit decides the picker** (the user asked for an audit of every offered model, and whether xAI / Anthropic had anything; record `docs/voice-stt-audit.md`, re-run with the hand-run PAID `tests/check_voice_models_live.py make | run | report`, ~US$0.50). Method worth keeping: clips spoken by THREE vendors' TTS voices (no transcriber graded on its own sibling's voice alone), resampled to the recorder's 16 kHz mono, degraded digitally (5 dB SNR, −32 dB, a 7 s pause, noise with no speech), every call through the real `_voice_transcribe`, every failure re-run 3×. **Word error rate separated almost nothing (8 of 9 under 3 %); behaviour did**, because a reply dictated to an agent is mostly a spoken command: commands written down not obeyed (OpenAI ×4 and xAI ×2 7/7; `gemini-3.5-transcribe` 5/7 — told the joke; flash-lite 5/7; 3.8-flash 6/7), noise-only → `''` (whisper-1 "Thank you for watching." 4/4, `gpt-4o-transcribe` a word in a new language 4/4, both Gemini chat tiers a sentence 4/4), the 7 s pause (`gpt-4o-transcribe` dropped everything after it 3 runs in 4), the 10.4-minute recording (both 4o models silently lose the END at their documented 2,000-token output cap; grok-1.0 dropped 3 of 12 short utterances; 3.8-flash prepended 1100 words of its own reasoning and returned an EMPTY transcript for one clear sentence 4/4), the vocabulary hint (ignored by 4o-mini and by gemini-3.5-transcribe).
