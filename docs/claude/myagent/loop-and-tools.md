# MyAgent — The agentic loop, the tool families, safety and launch modes

**Agentic loop** — `stream_worker()` runs a `while True:` loop: dispatches to `_stream_anthropic_call()`/`_stream_responses_call()`/`_stream_gemini_call()` by provider, streams the response, executes tool calls, appends results, loops. Exits on `end_turn` or when `stop_requested` is set via STOP. No fixed iteration limit. Three stop reasons have their own handling since 2026-09-28 (all of them used to end the run as if it had finished): `pause_turn` — Anthropic pausing a long server-tool turn (the 20260209 web tools run code execution underneath and hit the server's iteration limit) — appends the paused content and CONTINUES, which resumes the turn; `max_tokens` / `model_context_window_exceeded` post a ⚠ saying the reply was cut off (and that an unfinished tool call was not run) — on Anthropic naming the model's own output ceiling, which is what every call sends as `max_tokens` since 2026-10-11 (see **Anthropic output ceiling** below), with thinking counted against it — and a run that ends there writes its result file as `error` with that reason. STOP pressed during a turn's SEQUENTIAL tools leaves the rest unrun, each answered `[Not run: the user pressed STOP]` so every `tool_use` keeps its `tool_result` (a click, a keystroke or a command queued behind the STOP used to run anyway). Every call reads `self.model` and the thinking fields afresh, which is what lets the **Model upgrade** (below) switch a run mid-way; the "Call #N" counter is mirrored on the instance as `_run_call_num` for its pane line; and both loop-end tails (success and exception) go through the nested `_end_run` — the ONE caller of `_log_run` (the cost-log line, under the model the run ended on), then the removal of the run's in-progress cost record (`_run_progress_clear`, 2026-10-08 — see API cost tracking), then the upgrade's restore (`_upgrade_end_run`, getattr-guarded for bare test hosts), then `_write_result_file`.

**Tool system** — Seven static lists (`TOOLS`, `FILE_TOOLS`, `DESKTOP_TOOLS`, `BROWSER_TOOLS`, `EXCEL_TOOLS`, `PHYSICAL_TOOLS`, `META_TOOLS`) plus dynamic `MCP_TOOLS` in `constants.py`, assembled by `_get_tools()` in `streaming_mixin.py`. `TOOLS` and `FILE_TOOLS` are always included; the rest are gated by their checkboxes. Dispatch is in `_execute_tool()`. `find_element` is provider-gated — `_get_tools()` strips it for every provider but Google (it uses Gemini's native pointing API). Adding a static tool requires: (1) schema dict in the right list in `constants.py`, (2) `elif` branch in `_execute_tool()`, (3) `do_<name>()` in the appropriate mixin, and optionally (4) adding the name to `PARALLEL_SAFE_TOOLS` if thread-safe and stateless. MCP tools are added at runtime — see below.

**MCP integration** — `myagent/mcp_mixin.py` connects to Model Context Protocol servers (filesystem, GitHub, Slack, etc.) at startup, enumerates each server's tools via the `mcp` Python SDK, and exposes them through the same `_get_tools()`/`_execute_tool()` pipeline as native tools. Architecture invariants:
1. **Async-only SDK** — `MCPMixin` runs a dedicated asyncio loop in a background thread (`self._mcp_thread`); the sync streaming worker calls in via `asyncio.run_coroutine_threadsafe`.
2. **One `AsyncExitStack`, one long-lived runner** — all server connections live in a single stack owned by `_mcp_runner`, which connects, lists tools, then parks on `self._mcp_shutdown_event` for the whole session. Required because anyio binds task-group cancel scopes to the originating task: splitting the lifecycle across multiple `run_coroutine_threadsafe` calls would kill the stdio pumps and surface as `Connection closed` on the next `list_tools`. Shutdown signals the runner; the stack unwinds sessions/stdio_clients LIFO and subprocesses exit. A post-unwind `gc.collect()` + two `await asyncio.sleep(0)` cycles drain pending pipe-close callbacks to avoid harmless `Event loop is closed` finalizer tracebacks.
3. **Namespaced tool names `<server>__<tool>`** (double underscore — valid for all four providers' regexes); `_execute_tool` looks up `block.name` in `self._mcp_tools_by_name` and routes to `do_mcp_call` before the static dispatch chain. `do_mcp_call` waits for the call in `MCP_CALL_POLL` (0.25 s) slices up to `MCP_CALL_TIMEOUT` (120 s): STOP ends the wait, and a call given up — STOP or the timeout — is CANCELLED rather than left running on the MCP loop (since 2026-09-28; a slow server used to hold the run for the full two minutes, and the expired wait's bare `TimeoutError` produced an empty error text).
4. **Per-user config** in `mcp_servers.json` (root), the per-server entries in the same shape as Claude Desktop / Cursor (under a top-level `servers` key — a pasted `mcpServers` file loads nothing), so community servers drop in unchanged. A server whose name starts with `_` is disabled and never connected (`_load_mcp_config`, since 2026-09-28: the example file's `_example_with_secret_from_shell_env` entry, documented as off until its underscore is removed, used to be connected). `${NAME}` placeholders in `env` values are substituted at spawn time by `_substitute_placeholders`: `${RANDOM_PORT}` is reserved (each occurrence → an independent OS-assigned free port; does not consult `os.environ`), any other `${NAME}` → `os.environ[NAME]` (or empty + a one-shot warning). Substitution is scoped to user-typed `spec["env"]` keys only — not the ambient env, not `command`/`args` (so secrets don't leak via process listings). This keeps `mcp_servers.json` secret-free and safe to track.
5. **Graceful degradation** — without `mcp` installed, `_HAS_MCP` is False, the checkbox is disabled, and every method is a no-op.
6. **Background connect** — `root.after(100, self._connect_mcp_servers)` starts the loop thread and the runner and RETURNS at once (since 2026-09-28: it used to wait on `_mcp_ready_event` on the Tk thread, up to 300 s, so the window froze until every server was up — 1-3 s warm, minutes on a cold `npx -y`); `_mcp_watch_startup`, a 1 s Tk timer, logs a startup that outlives the 5-minute ceiling (`MCP_STARTUP_TIMEOUT`). The wait moved to where the tools are needed: `stream_worker` (both apps) calls `_mcp_wait_ready` at run start, which — when the run offers MCP tools and the servers are still connecting — waits on the WORKER, 0.25 s at a time so STOP ends it, within what is left of the ceiling. That keeps a `-l` / headless launch getting its servers' tools (its START used to run only after the blocking connect). Per-server failures are logged, not fatal. Pinned in `tests/test_review_followups.py` (a slow fake runner: the connect returns at once, the run's wait sees the tools).
7. **Dual-sink `_mcp_log`** — status lines go to both the GUI queue and `sys.stderr`; launch with `python.exe` or `pythonw.exe MyAgent.py 2> mcp.log` to capture the MCP stream off-process. `mcp_enabled` persisted per-instruction. To enable: `pip install mcp`, drop in `mcp_servers.json`, restart, tick the MCP checkbox.
8. **Windows ProactorEventLoop hardening** — three settings prevent `ClosedResourceError` / spurious EOF on the first RPC after `initialize()`, all rooted in IOCP fragility: (a) pass `errlog=os.devnull` (opened once in `_connect_mcp_servers`) to every `stdio_client` — under `pythonw.exe` `sys.stderr` is None, which corrupts IOCP routing; (b) create the loop with `asyncio.new_event_loop()` *inside* `_loop_runner`, since IOCP ownership binds to the constructing thread; (c) pass an explicit `list_roots_callback` returning `ListRootsResult(roots=[])` — the SDK default returns an error and skips advertising the roots capability, which some servers (e.g. `server-filesystem`) handle badly.
9. **Reconnect-on-close** — if `list_tools` raises `ClosedResourceError`/`Connection closed`, `_list_tools_for_server` opens a fresh session via `_open_server_session`, swaps it into `_mcp_sessions[name]`, and retries. Belt-and-braces; (8) is the real fix and this rarely fires.

**Gmail (Google) integration** — `myagent/gmail_mixin.py` adds native multi-account Gmail tools via `google-api-python-client`, NOT MCP. (The editor checkbox is labeled "Gmail" — renamed from "Google" when the Gemini provider took the "Google" label — but the persisted key and internals stay `google`/`google_enabled`/`_HAS_GOOGLE`.) Sixteen tools (`gmail_search`/`read`/`get_attachment`/`send`/`reply`/`create_draft`/`list_drafts`/`send_draft`/`trash`/`untrash`/`list_labels`/`create_label`/`delete_label`/`modify_labels`/`mark_read`/`list_threads`) flow through the same `_get_tools()`/`_execute_tool()` paths as native tools. `gmail_reply` builds proper In-Reply-To/References headers and reuses the original threadId so replies nest; `gmail_send`/`reply`/`create_draft` take optional `attachments: [filepath]` (combined raw cap 20 MB, under Gmail's 25 MB post-base64 ceiling; MIME auto-detected). Architecture invariants:
1. **Per-account OAuth, single process** — tokens at `~/.config/myagent-google/{account}_token.json`, shared client at `oauth_client.json`, account list at `accounts.json`. `_gmail_service(account)` runs `InstalledAppFlow...run_local_server(port=0, prompt="select_account")` once per account, then refreshes silently from the stored refresh token. Since 2026-09-28 the browser sign-in waits at most `OAUTH_SIGNIN_TIMEOUT` (300 s — unbounded, an abandoned tab parked the run for good) and is refused outright in a `--headless` run (nobody is there to finish it; the error says to run MyAgent with a window once).
2. **Account enum patched at runtime in `_get_tools()`** — each tool's `account` field gets `enum=[...accounts.json names...]` injected before schemas ship; empty `accounts.json` → empty enum (a clearer error than dropping the tools).
3. **Scope `gmail.modify` only** — read/send/draft/label/trash but NOT permanent delete (a deliberate safety boundary; permanent delete would need the broader `https://mail.google.com/` scope and a separate tool).
4. **Destructive ops gated by `_confirm_gmail_action`** — `gmail_send`/`send_draft`/`trash` pop a Tk `askyesno` (opening on No since 2026-09-28 — `mail_common.confirm_action` passes `default=NO`, so a reflexive Enter declines, the rule of the DELETE confirmations; the Proton and Outlook confirmations share it) showing recipient/subject/IDs; denial returns `"user denied: ..."` so the agent continues. Since 2026-09-28 a `gmail_modify_labels` that ADDS `TRASH` or `SPAM` asks too, under the `gmail_trash` key (so the same Safety-dialog bypass covers it) — a label move was a trash with no dialog. Dispatch routes via `block.name.startswith("gmail_")`. The batch tools (`trash` / `untrash` / `modify_labels` / `mark_read`, and Outlook's four) go through `mail_common.run_per_id`, which returns each id's own outcome — a failure part-way used to discard the ids already done and report the whole call as failed.
5. **`_HAS_GOOGLE` flag** mirrors `_HAS_MCP`: missing libs → checkbox disabled, methods no-op. `google_enabled` persisted per-instruction.
6. **Native, not MCP** — a tight 16-tool catalog (vs MCP's 55+) saves token budget; multi-account is one parameter instead of two subprocesses; destructive ops get a real dialog; and the OAuth/token plumbing is reusable for future Google services (Calendar, Drive, Sheets).

**Proton Mail integration** — `myagent/protonmail_mixin.py` adds native multi-account Proton tools via Proton Bridge over stdlib IMAP+SMTP — NOT MCP and NOT a REST API (Proton publishes none; E2E encryption means decryption is client-side, so Bridge is the official integration path). Its sixteen tools mirror the Gmail surface 1:1 (same names with `proton_` prefix), with the same In-Reply-To/References handling and optional `attachments` (20 MB cap, MIME auto-detected). Architecture invariants:
1. **Per-account Bridge credentials, no OAuth** — config at `~/.config/myagent-protonmail/accounts.json`: `email`, `username`, `app_password` (Bridge-generated, NOT the Proton login), per-account `imap_host`/`imap_port`/`smtp_host`/`smtp_port`, and optional `ca_cert_path` (Bridge's exported `cert.pem`) for verified TLS. Absent/missing cert → `CERT_NONE` (acceptable for localhost-only Bridge traffic, where a MITM already needs code execution on the machine). A failed STARTTLS (a Bridge quirk) falls back to the plain login ONLY for a loopback host (`_is_loopback_host`); any other host raises instead of receiving the password in clear (2026-09-28 — IMAP and SMTP alike; `UnreadSummary.py` follows the same rule). IMAP connections are cached per-account; SMTP opens fresh per send, parses recipients with `email.utils.getaddresses` (a quoted display name with a comma split into two bogus addresses) and reports the addresses the server refused as `refused_recipients`.
2. **Account enum patched at runtime** — same `_get_tools()` pattern as Gmail.
3. **No "scope" concept** — Bridge gates the surface server-side (no permanent delete, no settings); Trash is recoverable from Proton's UI.
4. **Destructive ops gated by `_confirm_proton_action`** — `proton_send`/`reply`/`send_draft`/`trash`/`delete_label`, and since 2026-09-28 a `proton_modify_labels` whose destination is the Trash or Spam folder (under the `proton_trash` key); same dialog + per-tool bypass as Gmail (stored in `disabled_confirm_patterns`). Dispatch via `block.name.startswith("proton_")`. **Moves go through `_imap_move`** (trash, untrash, modify_labels and its stray-UID re-moves; send_draft's Drafts cleanup is a UID EXPUNGE of that one draft): UID MOVE; a MOVE the server REFUSES (NO — a mistyped folder, `[TRYCREATE]`) raises; only a server that does not KNOW the command (BAD, which imaplib raises) gets COPY — checked — then `\Deleted` + `_imap_uid_expunge`, a UID EXPUNGE (RFC 4315) of exactly those UIDs, plain EXPUNGE only where UID EXPUNGE is BAD. The old fallback ran for refusals too and ignored its refused COPY, so a mistyped folder expunged the messages while the tool said ok.
5. **`_HAS_PROTONMAIL`** is always True on CPython (stdlib `imaplib`+`smtplib`+`email` transport); kept for parity. Bridge availability is detected at first-call time, not startup, so Bridge restarts reconnect transparently. `proton_enabled` persisted per-instruction.
6. **IMAP UIDs are per-folder** — per-message tools take a (`folder`, `uid`) pair; bulk ops take `folder` + `uids: [int]`. UIDs are never reused (RFC 3501), so a MOVE → MOVE-back round-trip yields three distinct UIDs for the same logical message.
7. **Four helpers renamed `_proton_*`** (`_format_proton_summary`, `_extract_proton_bodies`, `_extract_proton_attachments`, `_attach_proton_files`) to avoid MRO shadowing: the App's mixin order (`...GmailMixin, ProtonMailMixin...`) means Gmail's identically-named statics would otherwise win the left-to-right MRO and silently break Proton (empty bodies, arity crashes). A foundational footgun of flat-namespace mixins — defensively prefix non-shared helpers. Since 2026-10-19 `_attach_proton_files` and Gmail's `_attach_files` are thin wrappers over `mail_common.attach_files` (each passing its own size-cap wording) — a module function, which no MRO can shadow.
8. **Four empirical Bridge/dovecot quirks, mitigated**:
   - (a) **SUBJECT search** is reliable for single-word substrings but fragile for multi-word substrings against non-ASCII subjects (curly quotes, em-dashes, accented letters); the `proton_search` description steers toward single words, and `_uid_search` switches to `CHARSET UTF-8` byte-literals for non-ASCII queries.
   - (b) **`Labels/X` MOVE is additive, not exclusive** — INBOX→`Labels/Foo` just adds the label; moving back removes it. System folders (INBOX/Sent/Drafts/Trash/Archive/Spam) are true exclusive destinations. Documented in `proton_modify_labels`.
   - (c) **Label removal can leave a transient new UID** in the source (Bridge↔Proton eventual consistency); `do_proton_modify_labels` snapshots source UIDs, detects strays after the MOVE, and re-MOVEs them up to 2×, reporting `label_removal_retries: N` (0 = clean).
   - (d) **Bare-token SEARCH works on Bridge, dovecot rejects it** — `q="invoice"` is a loose full-text match on Bridge but errors `BAD Unknown argument` on dovecot/cPanel (WebCentral). The description steers toward the explicit-key form (`SUBJECT`/`BODY`/`TEXT`/`FROM`/`TO "..."`), which works on both.
9. **Native, not MCP** — same rationale as Gmail, plus credential hygiene via Bridge's per-install app-password (never the real Proton login or mailbox password).

**Outlook / Microsoft 365 integration** — `myagent/outlook_mixin.py` adds native multi-account Outlook tools via the **Microsoft Graph API** authenticated with **MSAL** — NOT MCP and NOT IMAP/SMTP (Microsoft disabled Basic Auth for personal outlook.com IMAP/POP/SMTP in late 2024; even IMAP now needs OAuth2, so Graph is the modern path and maps onto the Gmail OAuth pattern). Its sixteen tools mirror the Gmail surface 1:1 (same names with `outlook_` prefix), with proper conversation threading and optional `attachments` (~3 MB cap, MIME auto-detected). Architecture invariants:
1. **OAuth via MSAL, single process** — token caches at `~/.config/myagent-msmail/{account}_token.json` (chmod 600), Azure app client_id at `msal_app.json` (or `OUTLOOK_CLIENT_ID`/`MS_CLIENT_ID` env), account list at `accounts.json`. `_outlook_token(account)` tries `acquire_token_silent` first, falls back to `acquire_token_interactive(prompt="select_account")` (transient localhost redirect server), then refreshes silently. Since 2026-09-28 the interactive fallback is refused in a `--headless` run and bounded by `OUTLOOK_SIGNIN_TIMEOUT` (300 s), and the `PublicClientApplication` gets `timeout=OUTLOOK_HTTP_TIMEOUT` (60 s) — MSAL's HTTP calls default to no timeout and override `socket.setdefaulttimeout`. A `PublicClientApplication` is cached per account in `self._outlook_apps`. A 401 forces one token re-acquire + retry inside `_outlook_graph`.
2. **Account enum patched at runtime in `_get_tools()`** — each tool's `account` field gets `enum=[...accounts.json names...]`; empty `accounts.json` → empty enum (clearer error than dropping the tools). Same pattern as Gmail/Proton.
3. **Scope `Mail.ReadWrite` + `Mail.Send` only** — read/send/draft/move/categories/mark-read but NOT permanent delete (a deliberate safety boundary mirroring Gmail's; Deleted Items is recoverable from Outlook's UI).
4. **Destructive ops gated by `_confirm_outlook_action`** — `outlook_send`/`reply`/`send_draft`/`trash`/`delete_label` pop a Tk `askyesno`; denial returns `"user denied: ..."`. `outlook_reply` deletes its server-side `createReply` draft on denial so nothing is left behind. Dispatch routes via `block.name.startswith("outlook_")`. Confirm bypass via the Safety dialog's "Outlook destructive tools" section (shared `_disabled_confirm_patterns`).
5. **`_HAS_OUTLOOK` flag** mirrors `_HAS_GOOGLE`/`_HAS_PROTONMAIL`: missing `msal` → checkbox disabled, methods no-op. `outlook_enabled` persisted per-instruction and in `agent_state.json`.
6. **Gmail "labels" → Outlook "categories"** — `outlook_list/create/delete_label` wrap `/me/outlook/masterCategories`; `outlook_modify_labels` operates on category **display names** (not ids) because Graph stores `message.categories` as a name array, reading current categories and applying the add/remove diff. `outlook_trash` is a Graph `move` to the well-known `deleteditems` folder (each move yields a NEW message id, returned as `moved_ids` — same per-move-id-churn gotcha as Proton's per-folder UIDs).
7. **Single body, not multipart** — Graph messages have one body (`contentType: html|text`); when `body_html` is supplied it is sent as the body and the plain `body` is dropped (`_outlook_body_field`). A draft IS a message, so `outlook_send_draft` takes the draft's message id.
8. **All non-shared helpers prefixed `_outlook_`** — `OutlookMixin` is last of the three mail mixins in the App's MRO (`...GmailMixin, ProtonMailMixin, OutlookMixin...`), so prefixing avoids the flat-namespace shadowing footgun (Gmail's `_header`/`_extract_bodies`/etc. would otherwise win the MRO).
9. **Native, not MCP** — same rationale as Gmail: a tight 16-tool catalog, multi-account by one parameter, real confirmation dialogs, and reusable MSAL/token plumbing for future Microsoft Graph services (Calendar, OneDrive).

**Local document reader** — `myagent/document_mixin.py` adds one tool, `read_document(path, max_chars?, pages?)`, extracting text from PDF (`pypdf`), DOCX (`python-docx`), HTML (via `extract_text_from_html` in `helpers.py`), and most plain-text/source formats. Architecture invariants:
1. **Provider-agnostic** — operates on local file paths, so it pairs with `gmail_get_attachment`/`proton_get_attachment`/`fetch_webpage` with no source-specific wiring. The local filesystem is the boundary between provider-specific download and format-specific extraction.
2. **Always-available** — in static `TOOLS` (no checkbox) and in `PARALLEL_SAFE_TOOLS` (read-only, stateless).
3. **Graceful degradation** via `_HAS_PYPDF`/`_HAS_DOCX` — a missing lib makes only that format return a `pip install` hint; others keep working. Plain text and HTML have no dependency.
4. **Per-format extras** — PDFs return `page_count`/`pages_extracted`/`metadata`; DOCX returns `paragraph_count`/`table_count`/core properties, with tables rendered as `|`-separated rows to preserve column structure.
5. **PDF page ranges** — optional `pages` accepts `"1-5"`/`"3"`/`"1,3,5-7"` (1-indexed); out-of-range values are dropped for a partial result rather than an error.
6. **Encrypted-PDF detection** — tries empty-password decryption (common for owner-password-only PDFs) BEFORE the first page access, and decides by `decrypt("")`'s RESULT (a `PasswordType`, 0 = not decrypted); on failure returns a clear message and suggests `qpdf --decrypt` via `run_command`. Until 2026-09-28 it tested `reader.is_encrypted` after the decrypt — which only says the trailer has `/Encrypt` and stays True after a successful one — so EVERY encrypted PDF was refused, the owner-password-only statements and invoices pypdf reads perfectly well included, while a user-password PDF died on the page count with a raw `FileNotDecryptedError` first.
7. **Per-page error isolation** — a malformed page gets a `[page N: extraction error]` placeholder and extraction continues.
8. **Unknown extensions** — tries UTF-8 decode (catches mislabelled text), else a 256-byte hex preview; suggests `file`/`unzip`/`pandoc`/`ffprobe` for the deliberately-unsupported long tail (XLSX, ZIP, RTF, EPUB, A/V).
9. **Paired with the on-demand skill "email-attachment-processing"** (`skills/` store) documenting the `_read → _get_attachment → read_document → reason` pattern; on-demand so it costs zero base-prompt tokens.

**Native file tools** — `myagent/file_mixin.py` (mixin #21) adds five always-available tools (`read_file`/`edit_file`/`write_file`/`glob_files`/`grep_files`) via `FILE_TOOLS`, modeled on Claude Code's tool contracts — the reliable-editing surface for coding tasks, replacing PowerShell round-trips (PS 5.1 `Set-Content` defaults to the ANSI codepage, here-strings mangle `$`/backticks, CRLF is invisible in tool output). Architecture invariants:
1. **Fail-loud editing** — `edit_file` requires an exact `old_string` match that is UNIQUE in the file: zero matches, or several without `replace_all=true`, returns a retryable error naming the problem — never a guess applied to the wrong place. The pure core `_file_apply_edit` (no IO) is what makes shell-free editing trustworthy.
2. **Read-before-edit tracking** — `self._file_read_paths` (lazy init in `_file_reads()`) gates `edit_file` and `write_file`-over-existing: the model must have `read_file`'d the file first, so edits are grounded in actual content, not a stale imagination of it. Per RUN since 2026-09-28 — `_start_agent` clears it — where it used to live for the process: a GUI session runs several instructions, and a later run's model inherited the earlier one's reads.
3. **Byte-exact round-trips** — all IO uses `encoding="utf-8", newline=""` so `\r\n` stays literal in the string; `_file_apply_edit` retries an LF-normalized `old_string` expanded to CRLF (only when the file is CRLF and `old_string` carries no `\r` of its own), and a LITERAL match in a pure-CRLF file turns `new_string`'s bare LFs into CRLF too (one edit used to leave mixed endings); a leading BOM decodes to U+FEFF and re-encodes unchanged. Uniqueness counts OVERLAPPING occurrences (`_file_count` — `"end\nend"` is ambiguous in `"end\nend\nend"`, which `str.count` calls one). Writes are atomic (`_file_write_atomic`: mkstemp beside the target + `os.replace`, through a symlink to its target, keeping a POSIX mode) and non-string `content` / `old_string` / `new_string` is refused before anything is touched — a plain `open("w")` emptied the file first, so a write that then failed (a JSON object sent as content, a lone surrogate) left the user's file at 0 bytes. Every file tool expands `~` (write_file had created a literal `~` folder). Structurally unit-tested in `tests/test_file_mixin.py` (uniqueness, CRLF fallback, BOM round-trip, refusal paths, glob/grep pruning) and `tests/test_review_tools.py`.
4. **`read_file` is the gate and the viewer** — cat -n numbering, `offset`/`limit` paging (default 1000 lines), 500-char line truncation, binary sniff (NUL in the first 8K) that steers to `read_document`/`run_command`. The 80K output cap ends the window at a WHOLE line and the header / `re-read with offset=` note name the last line actually shown (they claimed the full window, so the note skipped every line past the cut); a file that is not valid UTF-8 is read with U+FFFD for the bad bytes AND says so (edit_file refuses it; a write_file of what was shown would re-encode them).
5. **glob/grep prune heavy dirs DURING the walk** (`FILE_SKIP_DIRS`: `.git`/`.venv`/`node_modules`/`__pycache__`/`.claude` — the last because `.claude/worktrees/` holds full repo copies that would double every hit) and skip binary / over-2 MB files. Since 2026-10-04 `glob_files` walks by hand (`_file_glob`: glob's `*` / `?` / `[]` per component, `**` any depth, a wildcard never matching a leading dot — and never following a symlinked directory; every directory listed once; the literal lead-in of the pattern is the walk's root) because `glob.glob(recursive=True)` can only be FILTERED after it has crawled everything: a `**` whose base reached `~/Library/CloudStorage` crawled the whole OneDrive through the macOS File Provider — every never-listed cloud folder enumerated from the server, each stat waiting seconds — and the run looked hung for 50 minutes with STOP powerless. Both walks share one enterability rule (`_file_dir_enterable`): a skip-dir name, a symlink, or a **remote root** (`_file_remote_roots`: macOS `~/Library/CloudStorage` — every File Provider domain — `~/Library/Mobile Documents` and `/Volumes`, and since 2026-10-06 `~/Library/Containers` and `~/Library/Group Containers` — other apps' sandbox data, where one stat raises the "would like to access data from other apps" dialog, `kTCCServiceSystemPolicyAppData`, a per-process consent macOS never saves (`DB Action: None` in tccd's log), so a `**` from `~` would have asked on every run — see the launcher README's Full Disk Access paragraph; Windows the `OneDrive` / `OneDriveConsumer` / `OneDriveCommercial` env roots) is never ENTERED from outside — the walk's root itself (`path`, or the pattern's literal lead-in) is never pruned, so naming one searches it — and both honour STOP and a ceiling (`FILE_WALK_TIMEOUT`, 60 s) between directories (`_file_walk_continues`), returning what they have marked PARTIAL; what was skipped or cut short is appended to the result (`_file_walk_notes`) and posted to the output pane (`_file_walk_announce`). One stat on a stalled filesystem can still block one call: the remote-root rule is what keeps the walk off the filesystems known to do that — and off the folders known to raise a dialog. Pinned in `tests/test_file_mixin.py` (equivalence with `glob.glob` on a plain tree, pruning observed through `os.scandir`, remote roots, STOP, the ceiling). `grep_files` is pure-Python regex (no ripgrep dependency) with `files_with_matches`/`content`/`count` modes and a `glob` filter matching the file NAME (`*.py`) or, for a pattern with a slash, the path relative to the search root (`src/**/*.py`; a leading `**/` also matches at the root — `_file_glob_matches`; it matched the basename only, so `**/*.py` silently found nothing).

A `.books.count` liveness probe guards against a just-quit instance lingering in the ROT with a dead window handle (otherwise: cryptic `FindWindowEx` 1400 errors).
2. **Attaches to the USER'S running Excel by design** — so `excel_close(quit_app=true)` quits ONLY when no other workbooks remain open. Found live 2026-08-01: the first smoke test's quit saved-and-closed the user's own open personal workbook. NEVER involve user workbooks in tests (see memory `deathbook-protected-workbook`); smoke-test with scratchpad workbooks only. The same hazard one call earlier is guarded since 2026-09-28: `excel_close` WITHOUT a `workbook` refuses while several are open (it closed — and by default saved — whichever the user had active); `_excel_book` tries the exact name before the stem and never matches a different extension (`Accounts.xlsm` acted on an open `Accounts.xlsx`); and `excel_open` of a path whose NAME is already open from another path refuses (Excel holds one workbook per name, so a scratch copy attached to the user's real file and every write landed there; a cloud-hosted book's URL cannot be compared, so the note names it instead).

6. **The wedged-Excel silent-write hazard** (found live on macOS 2026-08-01, on two separate long-running instances). A long-lived Excel process can enter a state where reads, formatting and sheet ops all keep working while **every cell-value write is silently discarded** — no error, and `saved:true` proves Excel never even marks the document dirty. Confirmed NOT an xlwings bug: raw AppleScript `value` / `value2` / `formula` / `formula r1c1` / via `selection` / frontmost all fail identically. Not caused by launch method or save order (both tested and cleared). **Restarting Excel fixes it.** The danger is that `_excel_app`'s `.books.count` liveness probe does NOT detect it — it reports healthy — so `excel_write` announced *"Wrote 5x5 cells"* over a no-op. Mitigation: `_excel_write_dropped` (pure, unit-tested) now checks every write. Small writes (≤200 cells) compare against the existing read-back echo; larger writes get a bounded first-row probe, closing the gap where big writes had **no** verification at all. It is deliberately conservative — it fires only when every expected cell was non-empty and every cell read back empty, and never for a write that holds a formula (since 2026-09-28): a formula's read-back is its RESULT, legitimately blank at times (`=IF(A1="","",A1)`, `IFERROR(…,"")`), and counting the formula text as "expected non-empty" raised a false VERIFICATION FAILED over a write that had landed. Diagnostic tell for a wedged instance: `osascript` `count of workbooks` times out while `count of windows` answers instantly.
7. **Unattended opens of protected workbooks: the dialogs, and the read-only trap** (worked through live 2026-08-01 against `DeathBook.xlsm`, a `CDFV2 Encrypted` OLE container in OneDrive). Three separate blockers, only one of which is an open parameter.
   - **The workbook gallery / DocStage HANGS the agent** (hit live 2026-08-01: MyAgent locked on its very first `excel_open`). `_excel_app(launch=True)` launches with `add_book=False`, so Excel comes up with NO document and shows its start screen — the template gallery with Cancel/Create. That window blocks Excel's Apple Event queue **completely**: `books.open` never returns, and even `tell application "Microsoft Excel" to activate` times out. Accessibility does not expose it either (`count of windows` returns 0), so it cannot be clicked away programmatically — the only recovery is killing Excel, which makes the pending call fail and releases the agent. Prevent it with `defaults write com.microsoft.office ShowDocStageOnLaunch -bool FALSE` (also set on `com.microsoft.Excel`; GUI equivalent is Excel → Preferences → General → "Open Excel Workbook Gallery when application opens"). Verified: launch-with-no-workbook went from hanging indefinitely to returning in 0.5 s. This is the single most important macOS setting for unattended Excel runs — a modal that blocks the event queue is unrecoverable from inside the agent, unlike every other dialog here.
   - **Macro prompt** on `.xlsm` — NOT an open parameter but an Office-wide preference: `defaults write com.microsoft.office VisualBasicMacroExecutionState -string EnabledWithoutWarnings` (documented values `DisabledWithWarnings` *(default)* / `DisabledWithoutWarnings` / `EnabledWithoutWarnings`; read at launch, so Excel must restart). It spans Word and PowerPoint and makes any macro-bearing file run silently — a security trade the user opts into, never a default to set. Windows needs no equivalent: its Trust Center already trusts the location.
   - **Password dialogs** — `password` and `write_res_password` are DIFFERENT passwords and one workbook can carry both: the first decrypts the file, the second claims write access on a write-reserved workbook. `_excel_open_kwargs` (pure, unit-tested) assembles the `books.open()` kwargs, omitting anything blank so an ordinary open stays byte-identical to a bare `open(path)`; `ignore_read_only_recommended` is plumbed for the softer read-only *recommendation* prompt. **DeathBook turned out NOT to be write-reserved** (`write_reserved=False`, `read_only_recommended=False`) — it needs only the one open password — so these params are general capability, not that file's fix.
   - **Silent read-only is the real trap, and its cause is UNRESOLVED.** DeathBook opened read-only for an agent run and, minutes later, fully editable on three consecutive fresh-Excel runs with successful write probes — same single password, file untouched. Neither a sidecar `~$` lock file (a zero-filled one does not reproduce it) nor Excel session state reproduced it on demand, so **do not repeat the plausible-sounding "Excel caches a path's read-only state for the session" explanation — it was tested and did not hold.** What ships is detection, not a diagnosis: `_excel_is_read_only` (`api.ReadOnly` on Windows, `api.read_only.get()` on macOS, chained so the wrong-platform probe's `AttributeError` falls through) and `_excel_read_only_note`, which lists what to check (sidecar lock, genuine write-reservation, disk writability, open-elsewhere/OneDrive) and gives the remedy that actually worked: quit Excel completely and retry. This matters because read-only is silent and only bites at the first save — the same silent-failure class as the dropped-write hazard in 6.

(b) `_excel_get_sheet`'s friendly *"Sheet 'X' not found. Sheets: …"* never fired on macOS, because `book.sheets[name]` returns a LAZY reference that only blows up later at use (leaking a raw `OSERROR -1728` from whatever call happened to touch it). **Physical tools (2026-09-21)** — `myagent/physical_mixin.py` (mixin #25) adds the **Physical** tool set (`PHYSICAL_TOOLS`, Physical checkbox, persisted per instruction as `"physical"`): tools that sense the room the computer sits in rather than the computer itself. One tool today, `camera_capture` — a still photo from a webcam via **OpenCV**, returned as the same `[text, image]` block pair `do_screenshot` returns, so the Anthropic tool_result path and every hoisting translator carry it unchanged. Optional `camera` (index, default 0), `save_path` and `delay_seconds` (a self-timer — invariant 13). Architecture invariants:
1. **Its own set, never a Desktop tool** — asked and answered at design time (the user's question was "Desktop, or a new Physical category?"). *Consent*: a camera sees the room and whoever is in it; the many Desktop-enabled instructions, unattended Heartbeat runs included, must not gain it by ticking a box that means "drive the mouse". *Coordinates*: see (2). *Dependency*: OpenCV, not pyautogui. `tests/test_surface.py` pins `DESKTOP_TOOLS` to an exact name list besides. "Physical" rather than "Camera" so that whatever else senses or acts on the world outside the computer has a home; `blocked_tools` is the per-tool control inside the set.
2. **A photo is not a click surface.** `do_camera_capture` reads and writes NONE of the screenshot pipeline's state — `_screenshot_scale` / `_offset` / `_dims`, `_display_states`, `_display_full_states`, the cached images — so a photo taken between a screenshot and a `mouse_click` leaves the click where it would have landed (pinned: the test sets all eight attributes and compares them after a capture). The click pipeline stays frozen; the camera has its own `_camera_fit` and its own copy of the per-provider limits (`CAMERA_IMAGE_CAPS`: 2048 / 4 MP Google, 2048 / 5 MP OpenAI, 1568 / 1.15 MP everyone else — the same numbers, for the same reason: past them the API downscales anyway).
3. **The hoisted-image hint knows about photos** (`helpers.is_camera_result` / `camera_aware_hint`). The Responses (OpenAI + xAI), Gemini, Kimi and Ollama translators defer tool-result images to a follow-up user message introduced by a hardcoded *"Below is the screenshot image … use the pixel coordinates … for mouse_click"* — over a webcam photo, an invitation to click at the furniture. Each translator records one bool per deferred image (`is_camera_result(tc_content)`: the result's first text block opens with `CAMERA_RESULT_MARKER`, the one constant the mixin writes and the helper reads) and passes its hint through `camera_aware_hint`: no photo → the SAME string object back (byte-identical for screenshots — pinned against the literal pre-camera text for all four translators); photos only → a photo hint; a mixed turn → the screenshot hint plus "of the N images below, image K is a camera photo". The photo's own result text deliberately never contains a parenthesised `(WxH pixels)` — that is the shape the translators' dimension regex looks for, and in a mixed turn it must find the *screenshot's* size (dimensions are written `1430x804 pixels` unparenthesised, the saved size `1920 by 1080`; both pinned). The markers live in `helpers.py`, not `constants.py`, because `Heartbeat.py` / `UnreadSummary.py` import helpers and it must stay stdlib-only. Known, deliberately untouched: `user_prompt` reply images and `browser_screenshot` images still get the screenshot wording.
4. **Auto-exposure needs an ADAPTIVE settle, not a frame count.** Measured 2026-09-21 on the development laptop (integrated 1080p camera): the first 20 DirectShow frames ran mean brightness 79 → 138 → 64 and were still falling; from a cold start DirectShow levelled at ~1.9 s and Media Foundation at ~2.65 s, the latter after a dip whose turning point (~0.95 s) looks flat for several frames. `_camera_settled(samples, window, span)` therefore requires the samples to reach back a FULL `CAMERA_SETTLE_WINDOW` (0.75 s) with every frame in it within `CAMERA_SETTLE_SPAN` (1.0 of 255); a 0.25 s window is fooled by the turning point (pinned, with both measured ramps as fixtures). `CAMERA_SETTLE_CAP` (4 s) takes the latest frame regardless — a TV or trees in the wind never settle — and the result then says brightness may be off. The exposure signal is the mean of every 8th pixel each way (1/64 the cost). A photo takes 3–4 s.
5. **Stateless per call: open → settle → one frame → release**, `cap.release()` in a `finally` on every path (pinned across success, no-open, no-frames, STOP). No handle outlives a call, so the indicator light is on only during a photo and another app gets the camera straight back. Never PARALLEL_SAFE — one device.
6. **The grab runs on its own daemon thread** (`_camera_grab_guarded`), bounded by `CAMERA_TIMEOUT` (25 s): a blocking driver call cannot be interrupted by STOP, so a wedged driver must cost a timeout rather than the run (the Excel gallery hang is the precedent for "unrecoverable from inside the agent"); a fresh thread also carries no COM apartment for Media Foundation to collide with (the Excel tools `CoInitialize` the worker). The waiting side polls every 0.1 s, so STOP sets the `cancel` event and the grab exits within a frame; a STOP is reported as such (`_CameraStopped`), WITHOUT the "check your camera" hint every real failure gets.
7. **Backends are named, in order** (`_camera_backends`): Windows tries Media Foundation (opened in 0.45 s, 26 fps at 1080p) then DirectShow (0.4 s + 0.55 s to change mode, 16 fps) so one failing falls through to the other; macOS `CAP_AVFOUNDATION`; else `CAP_ANY`. 1920×1080 is requested and the driver answers with its nearest mode. On this laptop the Windows Hello **IR camera** is a second PnP device, but neither backend exposes it as an index — index 0 is the colour camera on both. OpenCV's log level is lowered to ERROR at first use: an index that will not open is a tool result here, not console noise.
8. **`save_path`** goes through `normalize_save_path` (the mail tools' guard against a Windows path invented on the Mac), gains `.jpg` when it has no extension, accepts only `.jpg` / `.jpeg` / `.png`, and REFUSES an existing file or a folder — all before the camera is opened (pinned: `opened_with == []`) — and since 2026-09-28 the file is created with `"xb"` (exclusive), so one appearing during the 3–4 s the photo takes is not overwritten either. The file is the FULL-resolution frame at JPEG quality 92 (the model's copy is 85, after the resize), written with Python's `open`, never `cv2.imwrite`: that goes through the ANSI code page on Windows and returns False — silently — for a path with characters outside it (live-verified with `saved photo é.jpg`). A failed save is a `⚠ NOT saved` note on a result that still carries the photo.
9. **JPEG, not PNG** — the one place tool-result images are not PNG; every translator already reads `source.media_type` rather than assuming. A 1080p photo is ~2 MB as PNG and 100–170 KB as JPEG. A nearly black frame (mean < 6) comes back WITH the image plus a privacy-shutter / lens-cover / dark-room warning.

13. **`delay_seconds` — the self-timer, and how a monitoring loop is paced** (added the same day, after the user's first "photo every 10 s" run stopped by itself). MyAgent has no clock; a polling loop exists only as long as the model keeps calling tools, and `stream_worker` ends a run on any reply without a tool call (only Convo mode and the `user_prompt` nudge override that). Pacing with `run_command` `Start-Sleep` gives the model a turn whose newest input is an empty sleep result, and `claude-haiku-4-5` ended the run there twice with near-identical text ("Monitoring continues. Waiting for STOP command.") — call 16 of the user's run, turn 31 of a control run; both times right after an action → sleep pair, and "until I press STOP" in the prompt was read as something to wait for. Asking for sleep + capture in ONE reply does not help: Haiku emits one tool call per turn regardless (77 calls for 30 photos). 14. **`microphone_listen` (2026-09-22) — the second sense**, built the day the Mac Mini got a BRIO 500 (camera + microphone). `do_microphone_listen` records for `seconds` (`_mic_seconds`: default `MIC_DEFAULT_SECONDS` 5, ceiling `MIC_MAX_SECONDS` = the camera timer's 600, a bad value refused before the microphone is touched) and returns `MIC_RESULT_PREFIX` + the transcript. It spans two mixins by design: voice input's `_voice_sd` (rescanned, so a microphone plugged in mid-session is found), `_voice_resolve_device` on the Voice Setup microphone (a missing one falls back to the default WITH a note), `_voice_new_recorder`, `_voice_wav_bytes`, `_voice_transcribe` and `_voice_error_text` — so what the Mike button hears, the tool hears, and one Voice Setup serves both. **Click accuracy pipeline** — Desktop click invariants, refined for cross-provider accuracy:
- All providers receive **pixel coordinates** (no [0, 1000] normalization) — what the model reads in the image is what it passes to `mouse_click`. The old Gemini [0, 1000] convention caused ~1-pixel drift and broke entirely under multi-monitor mixed-DPI.
- `do_mouse_click`/`_scroll`/`_drag`/`_read_screen_text` use `round(float(x))` (not `int(x)`) to avoid truncation bias.
- A pre-screenshot guard refuses click/scroll/drag/OCR with "Take a screenshot first" when `_screenshot_dims == (0, 0)`.
- Tiered out-of-bounds policy: ≤2px overflow clamps silently; >2% of the dimension refuses with a "re-take a screenshot" message; in between clamps with a `⚠ clamped` warning.
- A 50ms `time.sleep` after `pyautogui.click` lets the UI settle before the next screenshot.
- `mouse_scroll` with coordinates MOVES the cursor there first (2026-09-28): a wheel event lands on whatever is under the cursor, and pyautogui's Windows backend sends it without moving, so "scrolled at (x, y)" had scrolled MyAgent's own pane. (No coordinate or scaling rule changed — the pipeline stays frozen.)
- The `_capture_single_display` region branch snapshots `entry_scale`/`entry_offset` at entry so chained region screenshots don't drift through stacked offsets.

**Per-display state tracking** — Multi-display coordinate state lives in two parallel dict pairs:
- `_display_states[N]`/`_display_images[N]` — the **most recent capture** (full or region) for display N. Used by `mouse_click`, `find_element`, and any `display=N` tool.
- `_display_full_states[N]`/`_display_full_images[N]` — the **most recent FULL capture** for display N, never overwritten by region captures. Region screenshots (`screenshot(display=1, x, y, width, height)`) interpret their coordinates in this full-image space, not relative to the last capture — without this two-slot split, chained region screenshots drift through stacked offsets.

`_resolve_coord_state(display)` is the shared lookup: returns `_display_states[display]` if a `display` param is given, else the current `_screenshot_scale/offset/dims`. `mouse_click`, `mouse_scroll`, `mouse_drag`, `read_screen_text`, and `find_element` all accept an optional `display` so the model can disambiguate screens without re-screenshotting.

**Image resolution caps per provider** — `_capture_single_display` resizes to each API's actual limit:
- **Anthropic**: `1568` long edge / `1.15 MP` — the API silently downscales to this anyway.
- **OpenAI**: `2048` long edge / `5 MP` — verified the API silently downscales above 2048 (gpt-5.2 reported `PIL.Image.size == (2048, 1152)`), so 2048 keeps `_screenshot_scale` matching what the model sees.
- **Gemini**: `2048` long edge / `4 MP` — higher than Anthropic's because Gemini's 768×768 tile system gives small UI elements more pixel density.

**find_element tool (Gemini-only)** — Uses Gemini's native spatial pointing API to locate UI elements by description. `gemini_mixin.py:do_gemini_find_element` uses Google's *exact* documented prompt (`"Point to the X. The answer should follow the json format: [{\"point\": <point>, \"label\": <label1>}, ...]. Takes an optional `display` so the cached-image lookup hits the right screen (`_display_images[display]`). Returns pixel coordinates (converted from [0, 1000]) and names the exact `mouse_click` to make. Stripped from `_get_tools()` for every provider but Google.

**Grid overlay** — `do_screenshot` accepts optional `grid=true`; `_capture_single_display` then calls `_draw_coord_grid(img)` after the API-limit resize (so labels match what the model sees), drawing 100px magenta gridlines with `(x,y)` labels at intersections (skipping (0,0)). **Multi-display desktop tools** — On macOS `pyautogui.screenshot()` only grabs the primary display, so `_macos_display_screenshot()` uses Quartz `CGWindowListCreateImage` with a per-display `CGRect`; on Windows, `ImageGrab.grab(bbox=..., all_screens=True)` via `_get_windows_display_rects()` (EnumDisplayMonitors). Both index the primary (origin 0,0) as display 0. The `screenshot` tool's `display` param: omit it to capture ALL displays as separate images (the recommended first step, stated explicitly in the schema), or pass a number for one. For OpenAI/Google/Moonshot, screenshot images are delivered as separate user messages (not embedded in tool outputs) with coordinate-system hints. Region screenshots interpret (x, y, width, height) relative to display N's FULL image (`_display_full_states[N]`), capture, then store the result in `_display_states[N]` for subsequent clicks. The result text tells the model to "use pixel coordinates AS YOU READ THEM... Do NOT scale or convert" to stop it pre-converting after inspecting dimensions via code_interpreter (see CI gating).

**`view_image` (2026-10-13)** — the Desktop tool that reads an image FILE into the conversation, the user's placement (the Desktop group, not a new one). Why: `JustChat_2026-10-13_180525` (Opus 5.5) was asked to review a trail camera's JPEGs and had no way to look at a file but the screen — it wrote a borderless, topmost Tk viewer, paged it through contact sheets and screenshotted it 32 times, until the 32 MB request limit the screenshots filled ended the run (the 413 rung above is the other half of that day's fix). `do_view_image(path)` (desktop_mixin): `~` expanded; a directory, a missing file, a file over `VIEW_IMAGE_MAX_BYTES` (100 MB, refused before decoding) and anything PIL cannot open are sentences, not exceptions; EXIF orientation applied (`ImageOps.exif_transpose`, the Attach Images rule — a phone photo would arrive sideways); resized, never up, to `_api_image_caps()` — the per-provider (long edge, pixels) table that `_capture_single_display` used to hold inline and now reads from the same method, so a file and a screenshot are sized alike (Google 2048 / 4 MP, OpenAI 2048 / 5 MP, else Anthropic's 1568 / 1.15 MP); encoded as PNG unless that exceeds `VIEW_IMAGE_PNG_LIMIT` (1.2 MB — a photo), then JPEG at quality 85, because the history keeps every image; returned as the `[text, image]` pair a screenshot returns, so every provider path carries it. NOT a click surface: it reads and writes none of `_screenshot_scale` / `_offset` / `_dims` or the per-display states (pinned), its text says so and opens with `helpers.FILE_IMAGE_MARKER` ("Image file"), the twin of the camera's marker — `is_camera_result` now returns the KIND ("camera" / "file" / False; truthy as before, so the four hoisting translators needed no change) and `camera_aware_hint` words the hoisted-image hint per kind, the camera-only wording byte-identical to before (pinned against the old strings) — and writes no parenthesised `(WxH pixels)`, the shape the translators' dimension regex reads a screenshot's size from. Dispatch is the Desktop tuple's gate plus a `view_image` branch ahead of `screenshot`'s in `_execute_tool`; PARALLEL_SAFE (a file read, no device); PIL imported inside the call, so the tool needs no pyautogui of its own. Pinned in `tests/test_view_image.py` (the schema and group, the dispatch scan, the caps table serving both, the real tool on temp files — a small PNG whole, a 3200x1800 photo resized per provider and sent as JPEG, EXIF orientation, GIF / BMP / WebP, a `~` path, the error sentences, the untouched coordinate state — and the hint helper) and `tests/test_surface.py`'s Desktop list.
