**Multi-provider support** — A Provider combobox switches between Anthropic, OpenAI, Google, xAI, and Moonshot (plus Ollama for local inference). Provider labels are company names; the Google provider serves the Gemini models and the Moonshot provider the Kimi models — legacy saved provider values ("Gemini", "Kimi") normalize to the company labels in `_restore_model_params`. The internal message format stays Anthropic-style; translation happens only at the API boundary: OpenAI uses `_messages_to_responses()`/`_tools_to_responses()`/`_stream_responses()`, Gemini uses `_messages_to_gemini()`/`_tools_to_gemini()`/`_stream_gemini_call()`, xAI reuses the Responses translators with its own `_stream_xai_call()`, and Moonshot (Kimi models) — Chat-Completions-only, so the Responses translators do NOT apply — has its own `_messages_to_kimi()`/`_tools_to_kimi()`/`_stream_kimi_call()` (see below). The `_ToolBlock` wrapper gives OpenAI/Google/xAI/Moonshot/Ollama dict-based tool responses the same `.name`/`.id`/`.input` interface as Anthropic's Pydantic objects, so `_execute_tool()` works identically for all providers. Gemini tool call IDs are synthesized as `gemini_{name}_{index}` (the API doesn't use IDs), and its arguments pass through `_normalize_gemini_args(args, properties)`, which is SCHEMA-AWARE since 2026-09-22: protobuf hands numbers back as float64 and Gemini sometimes string-encodes them (`"500.0"` for a coordinate), so declared-numeric and undeclared parameters get numeric-looking strings parsed — but a declared STRING is never parsed and a number sent for one is stringified (integral floats as integers), because the first, type-blind cut turned `type_text(text="12345")` — a docket number — into the int 12345 and `len(text)` in the dispatch killed a 47-call run. That failure also motivated `_run_tool`, the one wrapper both tool-execution sites (parallel and sequential) go through: every `do_*` returns its own error strings, so an exception escaping `_execute_tool` is a dispatch bug, and it now becomes an error tool_result naming the exception (plus a ⚠ warning line) rather than the end of the run. Both pinned in `tests/test_gemini_args.py`. Provider is saved per-instruction and in `agent_state.json`. The Instruction button is disabled while running. Google (Gemini) requires `GEMINI_API_KEY` or `GOOGLE_API_KEY`; xAI requires `XAI_API_KEY`; Moonshot requires `MOONSHOT_API_KEY` (or `KIMI_API_KEY`).

**OpenAI model filtering** — `_fetch_openai_models()` filters to Responses-API-compatible families via `OPENAI_RESPONSES_PREFIXES` (`gpt-4.1`, `gpt-5`, and `gpt-6` since 2026-09-06 — pruned in the 2026-07 audit: gpt-4.5 left the API 2025-07, gpt-4o retired 2026-02-16, and the whole o-series is scheduled out to gpt-5.6, o1/o1-pro/o3-mini/o4-mini on 2026-10-23 and o3/o3-pro on 2026-12-11); non-chat types (embedding, audio, search, realtime, preview, transcribe, tts) and legacy models (gpt-3.5-turbo, base gpt-4, gpt-4-turbo) are excluded. Scheduled-retirement ids that still pass the family prefixes are dropped too, via `OPENAI_DEPRECATED_MODEL_PREFIXES` (gpt-5-mini/-nano/-chat/-codex, gpt-5-2025 dated, and since the 2026-11-02 audit of the deprecations page gpt-5-pro — announced 2026-06-11, shutdown 2026-12-11, missed in July — the whole gpt-5.1 family, gpt-5.2-chat / -codex, the gpt-5.3 ids, gpt-5.4-nano and the whole gpt-4.1 family, 4.1 and 4.1-mini retiring 2027-01-14 with 4.1-nano shut down 2026-10-23 yet still listed) plus the exact-match `OPENAI_DEPRECATED_MODEL_IDS` (bare `gpt-5`, exact so it does not match everything); policy is retiring-models-removed-ahead-of-shutdown, and their pricing entries are removed as well — a retiring SUB-tier whose family row survives (gpt-5.4-nano under gpt-5.4, the 5.2 -chat / -codex ids under gpt-5.2) keeps an explicit `None` row instead, because the longest-prefix rule would otherwise price it by the family's (nano at gpt-5.4's $2.50, 12x over): `_get_pricing` returns None on it and `_unpriced_model_warning` tests the entry, not the prefix. The picker went from 40 ids to 10 plus their dated snapshots that day (`tests/test_openai_detect.py` runs the REAL `_fetch_openai_models` over a fake listing); the audit write-up is `docs/model-audit-2026-11-02.md`. GPT-5.6 (2026-07-09) ships as three tiers — sol (flagship $4/$20), terra (balanced $2/$12, the fallback default), luna (fast $0.20/$1.20) — priced in `OPENAI_PRICING` (re-trued 2026-08-25: sol had been carrying gpt-5.5's $5/$30; there is no bare `gpt-5.6` family row any more, so an unknown future 5.6 id is unpriced rather than mispriced); all three accept `reasoning.effort: "max"` (`_has_reasoning_max`, minor ≥ 6 — 5.5/5.4 reject it, probed live); gpt-5-chat-latest / gpt-5.1-chat-latest / gpt-5-codex / bare gpt-5.1-codex retired 2026-07-23. `OPENAI_REASONING_PREFIXES` (`o1`, `o3`, `o4`, `gpt-5`, `gpt-6`) get `reasoning` params instead of `temperature`. **GPT-6 Astra** (`gpt-6-astra`, 2026-09-03 — the new flagship, listed second in `OPENAI_FALLBACK_MODELS` so terra keeps the default) is always-reasoning with billed cache writes; its own paragraph is below. `gpt-5.x-chat-*` "Instant" variants (`_is_gpt5_chat_model()`) are non-reasoning, reject temperature, but support `text.verbosity`. The client uses `httpx.Timeout(600.0, connect=10.0, read=120.0)` to avoid indefinite hangs.

**Gemini model filtering** — `_fetch_gemini_models()` calls `gemini_client.models.list()`, strips the `"models/"` prefix, then applies a two-stage agentic filter: require the `generateContent` action (drops bidi-only live/audio models, embeddings, imagen, veo), then drop `GEMINI_NON_AGENTIC_SUBSTRINGS` name matches — specialized output modalities (TTS, the `-image`/Nano Banana lines, lyria music, omni AV), speech-to-text (`transcribe`, added 2026-09-19: `gemini-3.5-transcribe` answers on `generateContent`, so the action test passes it, but only with an `audioTranscription` part — it belongs to the Voice Setup picker, see **Voice input**), Interactions-API managed agents (deep-research, antigravity), the computer-use preview (needs its own tool protocol), gemma (no function calling), robotics — plus shut-down generations (`gemini-2.0-*`, `gemini-1.*`, which the API still lists) the legacy `gemini-2.5*` family (picker-hidden and unpriced since the 2026-07 audit — Google's page now says it is served "until further notice" to accounts that used it, with 3.x / 4 for new work — though the `thinking_budget` param wiring stays so a pinned 2.5 instruction keeps working until Google pulls it) and, since the 2026-10-17 audit, the 3.x tiers Google's deprecations page names (`GEMINI_DEPRECATED_MODEL_PREFIXES` — 3.1-flash-lite with its -preview, shutdown 2027-05-07; 3.7-flash, replaced by 3.8; the shut-down 3-pro-preview — and the exact `GEMINI_DEPRECATED_MODEL_IDS`, 3.5-flash, replaced by 3.6, an exact id because a prefix would take the current 3.5-flash-lite — and since 2026-11-02 3-flash-preview, replaced by 3.6-flash on the same page, when the user asked for every model with an announced succession gone), falling back to `GEMINI_FALLBACK_MODELS`. Every served id goes into `_served_model_ids` first, so a pinned instruction on a hidden tier still runs on it with the "hidden from the model picker" warning. What remains: Gemini 4 Argon, the pro/flash/flash-lite text tiers, dated previews/variants (incl. `-customtools`, which is tuned to prefer registered custom tools — exactly MyAgent's pattern), and the floating `-latest` aliases. EVERY current text tier supports thinking — including Flash-Lite (verified live 2026-07) — so `GEMINI_THINKING_PREFIXES` has no "lite" carve-out; `gemini-4` joined the prefixes 2026-10-17, the day Argon was found served — without it the checkbox was hidden and Argon thought at its default, unshown. The config style is version-split by `_gemini_uses_thinking_level()`: Gemini 3+ (and the non-versioned `-latest` aliases, which float to 3.x+) send `thinking_level` (low/medium/high mapping 1:1 from the strength combo; a stale saved max coerces to high — every served 3.x tier accepts all three, 3.1-pro included, probed live 2026-09-23, and the retired gemini-3-pro-preview's low|high-only coercion went with it), while 2.5 still requires the legacy `thinking_budget` (low=1024, medium=8192, high=24576 — sending `thinking_level` to a 2.5 model is HTTP 400). Both styles set `include_thoughts=True` so thought summaries stream to the Show Thinking pane (without it Gemini returns no thought parts at all). A reactive fallback in `_stream_gemini_call` retries once with the other style on a thinking-related 400, covering models/aliases whose style the version rules mispredict. **The Thinking checkbox OFF reaches the wire too (2026-09-23)**: until then an unticked box sent NO thinking_config, and a Gemini 3.x tier sent nothing thinks at its DEFAULT — probed live: 168 thoughts on 3.8-flash, 148 on 3.7, 237 on 3.6, 233 on 3.5-flash, 295 on 3.1-pro, 113 on 3-flash-preview for one short question, billed at the output rate with nothing shown; only the -lite tiers idle at 0. The quietest setting differs per tier, so `GEMINI_QUIET_STYLES` is a ladder — `minimal` (thinking_level, 0 thoughts on 3.6 / 3.5 / both lites / 3-flash; HTTP 400 on 3.8, 3.7, 3.1-pro, 4-argon), `budget0` (thinking_budget=0: 0 thoughts where accepted — 4-argon among them, ~50 on 3.8 / 3.7 which have a floor; 400 on 3.5-flash-lite and 3.1-pro), `low` (the floor of a tier that cannot stop: 3.1-pro 197 against 295), `none` (no config, the old behaviour — the last rung, so the ladder can never end in a failure the old code lacked) — pre-seeded per served tier in `GEMINI_QUIET_STYLE_PREFIXES` (4-argon / 3.8 / 3.7 / flash-latest → budget0, 3.1-pro / pro-latest → low, 2.5 Pro → none, 2.5 Flash → budget0, everything else minimal), learned per model per session by `_gemini_quiet_style` (a 400 ABOUT the thinking config — its text names thinking or the budget — while a quiet config is in flight steps down one rung, records it, retries — verified against the real errors on 3.8 and 3.5-flash-lite; since 2026-09-28 any other 400 — a bad image, an MCP schema, an overflow — no longer walks the ladder, which it had taken to `none`, teaching the session to send no config; errors are classified by the SDK's status code first, the message text only when there is none, since a 400's text can contain "500"), and announced once per model per session as an Activity line ("Thinking is off: gemini-3.1-pro-preview is sent thinking_level=low (this tier cannot stop thinking)"); the budget0 line is worded per tier since 2026-10-17 — "no thinking tokens on this tier" where budget 0 leaves none (`GEMINI_BUDGET0_SILENT_PREFIXES`: 4-argon, the 2.5 family) and "a few thinking tokens remain" on 3.8 / 3.7, whose floor keeps ~50 — because the Argon end-to-end check that day showed the floor wording on a tier that idles at 0. `_gemini_thinking_kwargs` is the ONE decision — (config, quiet rung) — behind the live call and the Debug dump; the title / cost-log params still say `thinking=off` (the user's setting), the tokens tell the rest. Pinned in `tests/test_gemini_quiet.py`. SDK is `google-genai`, initialized with `GEMINI_API_KEY` or `GOOGLE_API_KEY`.

**xAI (Grok) integration** — `myagent/xai_mixin.py` rides on the already-installed `openai` SDK with `base_url="https://api.x.ai/v1"` (`XAI_DEFAULT_BASE_URL`) and `XAI_API_KEY` — no new dependency. xAI's primary surface is an OpenAI-style **Responses API** (same `input` items, flat `type:"function"` tool declarations, `function_call_output` results), so the existing `_messages_to_responses()`/`_tools_to_responses()` translators are reused verbatim; only the streaming caller is xAI's own. Architecture invariants:
1. **Raw event iteration, not the SDK stream wrapper** — `_stream_xai_events` consumes `client.responses.create(stream=True)` events directly instead of `responses.stream()`, whose client-side snapshot state machine is tuned to OpenAI's exact event sequences. Usage comes from the `response.completed` event (not `get_final_response()`); reasoning deltas are accepted as BOTH `response.reasoning_text.delta` and `response.reasoning_summary_text.delta` (models differ) and feed the Show Thinking pane.
2. **Server-side tools ON, mixing verified** — live probes (2026-07-05) proved xAI's built-ins mix cleanly with client-side function tools in one request (correct routing whichever the task needs), so xAI follows the OpenAI pattern: `_get_tools()` strips the local DuckDuckGo `web_search`/`fetch_webpage` and `_stream_xai_call` appends `{"type": "web_search"}` + `{"type": "x_search"}`, plus `{"type": "code_interpreter"}` gated off while desktop tools are on (same double-scaled-clicks rationale as OpenAI). Each invocation bills a flat $0.005, folded into the authoritative cost (below). Server activity streams as `web_search_call`/`code_interpreter_call`/`custom_tool_call` (x_search) output items → surfaced as activity notices; a 400 naming a built-in strips just that tool and retries.
3. **Reasoning knob per model, read from the listing (2026-09-23)** — `/v1/language-models` (the listing `_fetch_xai_models` reads since that day; its `/v1/models` twin carries ids alone) publishes each model's `capabilities.reasoning_effort` (+ `default_reasoning_effort`), its `input_modalities` and its `aliases`. `_parse_xai_language_models` (pure) turns the body into `_xai_caps`: the model id AND every alias → `{"reasoning_effort": ladder | None, "vision": bool}` (the ladder ordered by `XAI_EFFORT_LADDER`, quietest first), and `_xai_reasoning_values` / `_is_xai_vision_model` answer from it FIRST — the static `XAI_REASONING_EFFORT` / `XAI_NON_VISION_PREFIXES` tables (longest prefix wins) answer only for a model the listing did not describe: a failed fetch (which clears the caps), or a model listed WITHOUT a capabilities block. Why: the table is hand-maintained, and `grok-4.7` (created 2026-09-01, the same $2/$6 tier as 4.6) sat in the picker for three weeks with NO Reasoning combobox — the user's report — because nothing named it; a new tier now gets its knob the day it appears. Live matrix 2026-09-23: `grok-4.3` none/low/medium/high/**xhigh** (xhigh is new since the 2026-07 verification — the listing said so and a live call accepted it; low = API default, "none" disables reasoning), `grok-4.5` / `grok-4.6` / `grok-4.7` low..xhigh (always-reasoning — "none" is HTTP 400 "This model does not support `reasoning_effort` value `none`" on all three; API default HIGH — and xAI's reasoning guide, read 2026-10-17, says 4.5 runs xhigh AS high: the listing publishes the rung and a live call accepts it, so it stays offered), `grok-4.20-multi-agent` low..xhigh FROM THE TABLE (listed without capabilities; the knob is agent collaboration count, unvalidated — even `"banana"` is accepted — yet honoured: xhigh billed 6x low's tokens on the same question, and "none" does not stop the reasoning, so None is not offered). Knobless: the pinned `grok-4.20-*-reasoning`/`-non-reasoning` variants and `grok-build-0.1` (HTTP 400 "does not support parameter reasoningEffort"), and the aliases (bare `grok-4.20` → the pinned reasoning variant; `grok-latest` → whatever xAI currently serves as latest — grok-4.3 until 2026-08, grok-4.6 then, **grok-4.7 since 2026-09** (the response's own `model` field says so) — at its server default; the listing names it under no model, so it deliberately never gets a knob and a server-side re-point can't strand a saved effort value). A live alias DOES inherit its target's knob (`grok-build-latest` → grok-4.5's ladder; statically it had none). `_model_supports_thinking()` returns "extended" for a knob model → the OpenAI-style Reasoning combobox. **Every xAI request carries `reasoning.summary: "auto"`**, with an `effort` only for a knob model: the knobless pinned reasoning variant and grok-build DO reason (reasoning tokens billed) and stream their summaries only when asked — grok-build-0.1 streamed 18 summary deltas in the in-process run; the pinned variant did in a bare probe and kept its reasoning to itself once the tool catalog was declared, the model's per-call choice, as with GPT-6 — while the `-non-reasoning` variant accepts the field and streams none. Before this every knobless model got no reasoning param at all, so the Show Thinking pane stayed dark on models that were reasoning. Zero-cost probe technique (from the 2026-08-25 audit, still valid): an invalid effort makes a knob model enumerate ("Invalid reasoning effort.") and a knobless one say so ("does not support parameter reasoningEffort") — but the multi-agent model validates nothing, so its knob had to be measured, not asked.
4. **One params builder, nearest-rung coercion** — `_xai_model_params()` is the ONE builder of the temperature + reasoning params behind both the live request (`_stream_xai_call`) and the Debug payload (`_payload_for_display`), so the dump cannot drift from the wire (the 2026-09-06 OpenAI pattern; before it the two sites carried duplicate coercion code). Temperature alongside reasoning (Gemini-style) — always shown in the UI and always sent. `_xai_effective_effort()` (via `_xai_nearest_effort`, which applies `_openai_nearest_effort`'s rule to the xAI ladder) is the ONE coercion of a stale saved effort, shared by the request builder, the Debug dump, the Reasoning combobox (`_on_model_selected`) and the title / cost-log params string: a supported value passes; a Claude `off` / `adaptive` becomes None where it exists (grok-4.3) else Low; a `max` steps down to Xhigh; a `none` carried onto an always-reasoning tier steps up to Low; anything unknown takes the floor. Before 2026-09-23 every stale value became "low" — so an Anthropic instruction saved at Max and re-pointed at grok-4.7 now runs at xhigh, which is what the user asked for, rather than silently at low. `_stream_xai_call`'s BadRequest downgrade ladder (drop temperature → drop the reasoning summary — the whole `reasoning` key when the summary was all there was, never an empty `{}` → drop reasoning, each via `continue` so successive 400s converge) degrades gracefully if a model refuses. `openai.AuthenticationError` is surfaced as a clear "check XAI_API_KEY" error instead of ten retries. Pinned in `tests/test_xai_params.py` (every rung's api_kwargs, the coercions, the ladder's three rungs, the Debug mirror, the param summary, headless restore of a stale Max entry).
5. **Model fetch + filtering** — `_fetch_xai_models()` GETs `/v1/language-models` through the SDK's own transport (`xai_client.get(path, cast_to=httpx.Response)` — key, base URL, timeouts and retries for free; a 4xx/5xx raises like any SDK call), keeps `grok*` ids, drops `XAI_NON_AGENTIC_SUBSTRINGS` (the grok-imagine image/video models — which that listing does not even carry, unlike `/v1/models`) and, since 2026-09-30, `XAI_UNRUNNABLE_SUBSTRINGS` (the user asked that the picker offer only Grok models that actually run: every listed model was run through the real `_stream_xai_call` — a client-side function call, then an answer from its result — and seven passed, while `grok-4.20-multi-agent-0309` answered HTTP 400 "Client-side tools for multi-agent models require beta access"; MyAgent always declares client-side tools and the listing carries no field that tells such a model apart, so the rule is the verified substring `multi-agent` — the class xAI's error names, covering a later multi-agent tier too — with its reason; the entry's aliases go with it and it leaves the served set as well, so a pinned instruction falls back to the default model with a ⚠ drift line instead of a 400 every run; the knob and price rows stay, so deleting the entry re-enables it once the account has the beta — and, since 2026-10-17, `non-reasoning`: the pinned grok-4.20 non-reasoning variant passed that one-call vetting yet looped 253 `run_command` calls on a four-step coding task, see item 10, so the picker shows SIX), sorts, and stores the parsed capabilities on the instance; a failed or empty fetch clears them and serves `XAI_FALLBACK_MODELS` (grok-4.3 default) — which matches the live catalog 1:1 (verified 2026-07-17, re-verified 2026-08-18, 2026-09-23 and 2026-10-17): the API serves exactly grok-4.3, grok-4.5 (500K context, vision, added 2026-07), grok-4.6 (the 2026-08-12 flagship), **grok-4.7** (created 2026-09-01 — same $2/$6, cached $0.50/M, vision, no aliases of its own; `grok-4.7-latest`, `grok-4.6-fast` and `grok-4.7-fast` all return 404 "does not exist or your team does not have access", so none is wired), the three grok-4.20 variants, and grok-build-0.1 (the fallback list mirrors the picker — seven from 2026-09-30, six since 2026-10-17: the multi-agent and non-reasoning variants are served but hidden, see above and item 10); ALL legacy families (grok-4/-fast, grok-3, grok-2) are retired, with grok-code-fast-1 surviving only as an alias of grok-build-0.1. Aliases are alias *fields*, not list entries, so the picker shows canonical ids only — but every alias is in `_xai_caps`, so a pinned instruction naming one gets its target's knob and modalities. `XAI_NON_VISION_PREFIXES` drives the weak-desktop-combo and blind-camera warnings and is **EMPTY** since 2026-09-23: the listing reports text + image input for every served model INCLUDING grok-build-0.1 (the docs once called it text-only; live it read a 48-px red test square as "Red"), so the old `grok-build-0` entry was flagging a sighted model as blind; the tuple stays so a future text-only tier is one entry away, and the live `input_modalities` decide for any model the listing describes.
6. **Exact cost tracking via `cost_in_usd_ticks`** — xAI is the only provider that returns the authoritative billed cost in the response (`usage.cost_in_usd_ticks`, 1 tick = $1e-10, verified to the digit against hand-computed pricing — again 2026-09-23 on grok-4.7: 103 uncached in + 1152 cached at $0.50/M + 81 out = $0.001268, ticks 12680000). `_xai_usage_dict` (split out of `_stream_xai_events` 2026-09-15, when it also began subtracting the subset-style `cached_tokens` from `input_tokens` — see the disjoint-buckets paragraph in the 2026-07-31 caching section) converts it to `usage_dict["cost_usd"]` and `stream_worker` prefers it over the table estimate, so the cost line is exact — including the cached-input discount ($0.20/M vs $1.25/M full rate; xAI caches aggressively) and the $0.005/server-tool fees, neither visible to a 2-tuple estimate. `XAI_PRICING` (verified live against the listing's price fields, unit $1/10000 per MTok: grok-4.3 + all grok-4.20 variants $1.25/$2.50, grok-4.5 / grok-4.6 / grok-4.7 $2/$6 — incl. the re-aliased grok-build-latest (still → grok-4.5), whose longer entry outranks the grok-build prefix — grok-build and its grok-code-fast alias $1/$2, and the floating grok-latest alias priced at its CURRENT target — $2/$6 since it re-pointed to grok-4.6 in 2026-08, unchanged by the 2026-09 move to grok-4.7; cached input is $0.20/M on most families, $0.30/M grok-4.5, $0.50/M grok-4.6 and grok-4.7) remains as the fallback when the field is absent; >200K-input long-context doubling keeps the ≤200K tier (gemini-3.1-pro convention). **Context-overflow compaction (Anthropic)** — a long agentic run can exceed the context window mid-task; the API returns 400 `prompt is too long: <T> tokens > <M> maximum`, which is not retryable as-is. `_stream_anthropic_call`'s BadRequestError handler now recovers instead of surrendering: `parse_overflow_counts` + `trim_history_for_context` (pure functions in `myagent/helpers.py`, ported 1:1 from SelfBot's sliding-window recovery) drop the oldest conversation rounds **in place** — cutting only at genuine user-turn boundaries so a `tool_use`/`tool_result` pair is never orphaned, sizing the cut to 0.75·M from the reported counts (oldest-half fallback), always keeping the last two rounds — then post a red ⚠ warning and `continue` the retry loop (`api_kwargs["messages"]` is the same list object, so the retry sends the shorter prompt and the trim persists into `stream_worker`'s ongoing loop). When even the last two rounds overflow (`removed == 0`), an actionable warning naming 1M-context models is posted and the call RAISES (`RuntimeError("Context window exceeded on <model> — nothing left to trim")`), so the run ends through stream_worker's exception tail with status `error` in its result file — until 2026-09-28 it returned `end_turn`, which reported a failed run as completed (a waiting parent read it as a success). Structurally unit-tested in `tests/test_context_trim.py`. Other providers keep their existing behavior (their overflow errors differ per API; the Anthropic path was the documented gap). **Anthropic prompt caching (`cache_control`)** — added 2026-07-31 after a cost audit found a `Balance Westpac Mastercard account` run costing $2.15 on claude-sonnet-5 versus $0.30 on kimi-k3 — despite Sonnet 5 being the CHEAPER model per token ($2/$10 vs Kimi's $3/$15). The whole gap was caching: Moonshot caches context automatically server-side (`kimi_mixin` prices the hits at $0.30/M vs the $3.00/M miss), while Anthropic's caching is strictly **opt-in** and MyAgent had never set a breakpoint — so every turn of an agentic loop re-sent the entire growing prefix (system prompt + full tool catalog + every prior screenshot and tool result) at the full miss rate, a cost that grows ~quadratically with turn count. `_stream_anthropic_call` now places three breakpoints, under Anthropic's ceiling of four:
1. **One static marker on the system prompt** (`_anthropic_cache_system`). The cache prefix is built in the order tools → system → messages and a breakpoint caches everything *before* it, so this single marker covers the entire tool catalog too — no need to touch the server-side tool dicts. An empty prompt stays a bare string (a text block with `""` is a 400).
2. **Two rolling markers on the newest eligible turns** (`_anthropic_cache_messages`). Turn N writes a cache ending at its last message; turn N+1 matches that prefix and reads it at 0.10x. The second, older marker is the safety net for a write that hasn't landed or a prefix aged past the 5-minute TTL. Default TTL is deliberate: 5-min writes cost 1.25x and match `ANTHROPIC_PRICING`'s cache-write column exactly, so the cost line stays accurate (`ttl: "1h"` would need the `extended-cache-ttl-2025-04-11` beta and 2x writes).

Two invariants make it safe. **History is never mutated** — only the messages receiving a breakpoint are shallow-copied, because `messages` is the live list `stream_worker` appends to and `trim_history_for_context` trims in place; mutating it would accumulate stale breakpoints past the limit of four. **The wire copy is rebuilt inside the retry loop**, not once above it: the overflow handler's in-place trim previously relied on `api_kwargs["messages"] IS messages`, which the copy breaks — rebuilding per attempt restores that and re-places the markers on the post-trim tail. Assistant turns are skipped entirely (`streaming_mixin:1062` appends `final_message.content` verbatim — SDK Pydantic blocks, not dicts), which naturally lands the markers on the user turns carrying `tool_result`s, the real turn boundaries. Structurally unit-tested in `tests/test_anthropic_cache.py`; live-verified 2026-07-31 against claude-sonnet-5 (call 1 `cache_write=2829`, call 2 `cache_read=2829`, `input=2`). Watch it work by ticking **Activity** — the per-call cost line prints `cache_read:N` (`event_loop_mixin.py:176-195`), which read `0` on every Anthropic call before this change. SelfBot carries the same breakpoints (its own `_cache_system` / `_cache_messages` — see the Prompt caching paragraph of CLAUDE_SELFBOT.md).

**Cached-input accounting (OpenAI / Gemini)** — added 2026-07-31 as the follow-on to the Anthropic caching work above. Anthropic was the only provider whose caching needed switching ON; OpenAI (automatic above ~1024 tokens) and Gemini (implicit caching, automatic on 2.5+ tiers) were **always** getting the discount on the bill — MyAgent simply never reported it, so every OpenAI/Google line in `APICostLog.txt` was overstated. Three fixes, all live-verified 2026-07-31:
1. **Cached rates in the tables.** `OPENAI_PRICING` / `GEMINI_PRICING` entries are now 3-tuples `(input, output, cached_input)`; `_get_pricing` returns a `cache_read` key for them. Since 2026-09-06 the OpenAI rows that BILL cache writes — the GPT-5.6 tiers and gpt-6-astra, 1.25x input (terra $2.50/M, sol $5.00, luna $0.25, astra $12.50) — are 4-tuples with the write rate, exposed as `cache_write`; the families before 5.6 list no write price and stay 3-tuples. OpenAI's cached rate is 1/10 of input on the GPT-5 families and **1/4 on GPT-4.1**; Gemini's is exactly 1/10 across the Gemini 3 family. A `None` cached slot (the OpenAI `-pro` tiers, which have no cached tier) makes `_get_pricing` **omit** the key rather than emit `0` — a zero would silently price cached tokens *free*, so absence keeps the accumulator's `.get("cache_read", 0)` the explicit choice. The per-million→per-token conversion passes `None` through untouched (dividing it raises).
2. **Disjoint buckets — the load-bearing correctness point.** Anthropic reports cached tokens as a SEPARATE bucket; OpenAI's `input_tokens_details.cached_tokens` and Gemini's `cached_content_token_count` are **SUBSETS** of their input totals. `stream_worker` prices `input × input_rate + cache_read × cache_read_rate`, so feeding it the raw overlapping totals would **double-charge every cached token** — trading one wrong number for another. The new `_openai_usage_dict` / `_gemini_usage_dict` staticmethods (named for the existing `_kimi_usage_dict` convention, and unit-testable unlike the old inline blocks) subtract before emitting, `min(cached, input)`-clamped so a bad report can't go negative. xAI and Kimi report the same subset shape (`input_tokens_details.cached_tokens` / `prompt_tokens_details.cached_tokens`), but both supply an authoritative per-call cost, so their gross pass-through was never priced and went unnoticed until the cost log started writing the buckets themselves (2026-09-14): TOK-IN then counted every cached token twice and the viewers' blended $/MTok came out low by the cache share — $0.54 shown against a real $0.93 on the 2026-09-15 grok-4.6 row (input 246,964 with cached 183,424 inside, output 2,226, authoritative $0.2321), whose cost the table rates reproduce ONLY under the subset reading. Since 2026-09-15 `_xai_usage_dict` (new — the usage block split out of `_stream_xai_events` so it is unit-testable like the others; since the same day's simplify pass it and `_openai_usage_dict` are thin wrappers over ONE `helpers.responses_usage_dict`, so the subset rule for the Responses shape lives in a single place) and `_kimi_usage_dict` subtract too (Kimi's own cost formula always had; only the emitted bucket lagged), and `tests/test_cached_usage.py`'s `DisjointContractCase` pins all four normalizers at once: input + cache_read (+ cache_creation) must equal the provider's gross input.
3. **Gemini thinking tokens were UNDER-reported.** `thoughts_token_count` is its own bucket, NOT part of `candidates_token_count` — the provider's own totals only reconcile when counted separately (live: prompt 15009 + candidates 1 + thoughts 133 = total 15143). They bill at the OUTPUT rate, so `output_tokens` is now `candidates + thoughts`. This error ran *opposite* to the cached over-report and had been partly masking it. (OpenAI needs no equivalent fix — its `output_tokens` already includes reasoning tokens.)

Also caught in the same audit: **eight OpenAI base rates were wrong**, re-verified against the live Standard-tier table (gpt-5.2, gpt-5.2-pro, gpt-5.1, gpt-4.1-mini, gpt-4.1-nano and codex-mini all sat at exactly HALF the standard rate — Batch-tier numbers; gpt-5.6-terra carried gpt-5.4's numbers; gpt-5.6-luna was 5x too high), and `gemini-3.6-flash` was missing entirely so it fell through to the bare `gemini-3` entry at $0.50/$3.00 instead of $1.50/$7.50 (`gemini-3.5-flash-lite` was added at the same time — the longer prefix must be listed or it matches the pricier `gemini-3.5-flash`). Gemini's implicit-cache floor is **4,096 tokens** on the Gemini 3 tiers, so a zero `cache_read` on short prompts is normal, not a broken probe — a live probe at 2,710 tokens reported `None` and only fired at 15,009. Live end-to-end: an OpenAI cache hit priced **−89.8%** versus the old all-at-full-rate number and a miss priced **±0.0%** (no regression); a Gemini cache hit **−44.4%**, and a Gemini *miss* **+6.0%** — the thinking-token correction making the log *more expensive* and more accurate. Structurally unit-tested in `tests/test_cached_usage.py`; rates documented in `MyAgent_Pricing.txt`. xAI and Moonshot needed none of this for COST — both return an authoritative per-call cost that already nets out their own cached-input discount — but they DID need the disjoint buckets once the cost log began recording tokens (2026-09-14): their gross pass-through double-counted every cached token in TOK-IN until the 2026-09-15 fix described in item 2 above.
