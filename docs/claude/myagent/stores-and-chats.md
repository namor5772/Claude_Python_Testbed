# MyAgent — Shared stores, the skills tree, instructions and chats

**Shared-store sync (`myagent/datapaths.py`)** — the authored-content stores (`agent_instructions.json`, SelfBot's `system_prompts.json`, and the `skills/` SKILL.md tree) resolve to **`<OneDrive>/MyAppShare/`** when a OneDrive client is present (`MYAGENT_DATA_DIR` env override; repo-root fallback on solo machines) — OneDrive, not git, syncs them across machines, mirroring TodoList's todos.json move. (Named `MyAgent` until 2026-07-19: `_shared_dir` adopts a legacy dir via in-place `os.rename` — synced as a cheap rename, no re-upload — and if the rename fails it keeps serving the legacy dir for the session rather than an empty new-name store, retrying next launch.) `constants.py` resolves `INSTRUCTIONS_FILE` through `resolve_store()` and `SKILLS_DIR` through `resolve_skills_dir()` — and, since 2026-10-08, `CHATS_DIR` through `resolve_chats_dir()` (see **Chats in the OneDrive share**) — at import (path decision + mkdir only; all route through the one `_ensured_shared_dir()` use-the-share-else-repo-root fallback shared with `resolve_costlog`, so the stores, the chats and the cost log can never diverge on placement); `load_store()` runs the **one-shot migration** lazily (a leftover repo-root copy is seeded or key-level-unioned into the shared file — shared entries win their names, a differing local entry survives as `name__<hostname>` — then renamed `*.migrated.bak` so deletions can't resurrect); `save_store()` is atomic via unique `mkstemp`+`os.replace` (SelfBot and MyAgent can save a store concurrently) and re-`makedirs` the parent (OneDrive GCs a still-empty shared dir). `_load_saved_instructions` also calls `absorb_conflict_forks()` — OneDrive's `<stem>-<Computer>.json` concurrent-write forks are unioned back in and deleted, so a sync race costs nothing (conflicting entries surface as `name__label` for reconciling in the UI). A shared file that exists but doesn't parse (half-synced cloud write) is served as empty/Default for the session and **never overwritten** — enforced at the save since 2026-09-28, where it had held only by luck: the stand-in is an `_UnreadableStore` (a dict subclass) and `_save_instructions_to_disk` refuses it, and any file `datapaths.store_unreadable` reports, with a warning + dialog and `StoreUnreadableError` (any save in such a session — an editor SAVE, a Model Setup Save, an Auto-send tick — would have written the stand-in plus its one entry over the whole library, synced to every machine); `_read_text` and the load handlers catch `ValueError` beside `OSError` (bad JSON and non-UTF-8 bytes are ValueErrors); `STORES_SYNCED` drives a "— synced" title-bar suffix. `Heartbeat.py` resolves the same path (its marker-rewrite temp file must live beside the store — `os.replace` across the repo→File Provider volume boundary is EXDEV). Structurally unit-tested in `tests/test_datapaths.py`.

**Skills tree (per-file store, 2026-08-07)** — the skills library alone is NOT a JSON store: each skill is `<share>/skills/<Name>/SKILL.md`, Agent-Skills-shaped — a tolerant frontmatter block (`name` / `description` / `mode` — and since 2026-10-31 the Skills Manager list's `section` / `order`, `SKILL_LAYOUT_KEYS`, written after `mode:` only when set, so a skill never filed or moved keeps its old file byte for byte, and read back tolerant: a blank section or a non-int order is dropped and the skill lands unfiled / unordered; the keys are the list's state, not the skill's, so `_same_skill` compares two copies with them set aside — a conflict fork, or a duplicate folder, that differs only in placement heals as an identical one, the main file's placement kept, instead of becoming a `<name>__<label>` sibling; `tests/test_skills_list.py` — no YAML dependency, folded continuation lines for hand-wrapped values, BOM tolerated on read — and since 2026-09-28 a file some editor saved in another encoding is read anyway, UTF-16 by its BOM, else cp1252 (`_read_text`; one such file's `UnicodeDecodeError`, not an `OSError`, crashed both apps at startup on every machine sharing the tree)) over the verbatim markdown body (the writer ends it with one newline, adding it when missing, and the reader strips one — a body WITHOUT a trailing newline round-trips exactly; one WITH it loses it once and is then stable, pinned by `test_round_trip_exact` — so a json-era entry whose content ends in `\n` compares unequal to its file-era twin in `union_stores`; this was documented as "byte-exact" until the 2026-09-28 review). The frontmatter `name:` is the source of truth; the folder name is only a sanitized container (Windows-invalid chars and reserved device names guarded). Names follow the **Agent-Skills naming convention** since 2026-08-07: lowercase letters/digits/hyphens, ≤64 chars (`westpac-login`, `process-payment-emails` — folder = name exactly, H1 body titles stay human-readable). **ENFORCED on create** (same day, upgraded from warn at user request): `_is_kebab_name` gates `manage_skills` create (rejected with the `_kebabize` suggestion in the error — 'Test_skill' → try 'test-skill') and the Skills Manager SAVE of a NEW name (askyesno offering the auto-converted name; if the converted name already exists the prompt says SAVE will overwrite its content). Existing legacy-named skills are grandfathered — update/SAVE on a name already in `self.skills` is never blocked, so nothing bricks. The tool schema's `name` description states the rule so models pick conforming names up front. SelfBot carries in-file copies of both statics. All 12 skills were renamed 2026-08-07 with cross-references in contents/descriptions updated and `skill_modes` keys remapped across `agent_instructions.json` (381 keys) and `system_prompts.json` (65) — a rename MUST remap those snapshots, because unknown skill names silently default to disabled at instruction load. `load_skills_tree()` runs the one-shot skills.json→tree migration (via `load_store`, so the legacy repo→shared union composes underneath; tree entries win names, differing json entries survive as `<name>__json`; the json then parks as `.migrated.bak`) and heals per-file conflict forks (`SKILL-<Computer>.md`: identical — the list placement aside — → deleted, different → materialized as a `<name>__<label>` sibling skill — numbered `<name>__<label>_2` … when a DIFFERENT preserved variant already holds that name, since 2026-09-28, where the second fork used to overwrite the first — orphaned → promoted to main). `save_skills_tree()` is diff-aware (unchanged files untouched — no OneDrive churn) and **WRITE-ONLY**: it never deletes folders, so a stale in-memory dict can't wipe a skill another machine synced in — deletion is explicit via `delete_skill_tree_entry()`. **A Skills Manager SAVE under a NEW name is a save-as and copies the source's bundled resources** (2026-09-25, the user's report: renaming a loaded skill and saving created a folder holding only SKILL.md — `references/`, `scripts/`, `tests/` silently left behind, although the folder IS the skill): the dialog tracks the loaded skill (`loaded["name"]`, set by the list selection, cleared by NEW and by deleting it), and a SAVE creating a NEW name while a DIFFERENT skill is loaded calls `datapaths.copy_skill_resources(SKILLS_DIR, src, name)` after the save — both folders resolved by FRONTMATTER name (`_skill_dir_for`, the read-only twin of delete's loop, so numbered `_N` siblings and legacy dirnames resolve), everything copied except the root SKILL.md / `SKILL-<label>.md` conflict forks / `SKILL.md.*.tmp` writer leftovers, existing destination files never overwritten (a re-save must not clobber files the new skill has grown), best-effort per file, and an info dialog names the count; a SAVE onto an EXISTING name never touches that skill's files. Pinned in `tests/test_skills_tree.py` (`ResourceCopyTests`); the dialog closures verified live in-process (real listbox select → rename → SAVE over a temp tree). Mirrored into SelfBot's Skills Manager the same day (its `_copy_skill_resources` IS this function via the try-import, with an in-file stub for standalone SelfBot; the wiring lines pinned byte-identical across both apps by `tests/test_selfbot_skill_copy.py` — see CLAUDE_SELFBOT.md) at the Skills Manager DELETE / `manage_skills` delete callsites (it removes the whole folder; bundled resource files ride along). Since 2026-09-02 the Skills Manager DELETE button — like the Instruction editor's — asks first (`messagebox.askyesno`, warning icon, default **No**, parented to the dialog), because a click is one slip away from removing a folder from the OneDrive-shared tree on every machine with no undo; the `manage_skills` / `manage_instructions` tool delete branches are deliberately NOT gated (a tool delete is the model acting on an explicit instruction, and an unattended run has nobody to answer a dialog) — pinned in `tests/test_gui_delete_confirm.py`. Deletion goes through `_rmtree_verified` (found live 2026-08-07 across THREE husk incidents): OneDrive both holds a directory handle transiently AND stamps a stuck-delete directory **ReadOnly (+ReparsePoint)** — and a read-only DIRECTORY defeats rmtree/rmdir on Windows, which is why husks survived later retries (clearing only file attributes was the gap; PowerShell's `Remove-Item -Force` always worked because `-Force` clears it). The remover chmods the root + every subdir + every file, retries briefly inline (~0.75 s — the Skills Manager DELETE runs on the Tk main thread), then hands a still-blocked directory to `_sweep_dir_later` (background daemon, ~2 min of 3 s retries) so the husk vanishes seconds after the click returns; `_scan_skills_tree` is the cross-launch backstop, sweeping a SKILL.md-less folder that is EMPTY (no files anywhere — nothing to lose), >60 s old AND — since 2026-11-05 — on the **husk record** (`.pending_skill_deletes.json` beside the skill folders: the folder names whose delete `_rmtree_verified` could not finish, written when it gives up and cleared when the folder is gone; `_note_pending_husk` / `_forget_husk` / `_sweep_recorded_husk`). The record is required because the empty + aged test alone describes a NEW skill mid-sync as well as a husk: a sync client creates the folder minutes before it delivers the SKILL.md, and a launch in that window removed the folder — and OneDrive then removed the real skill from every machine (how `cba-pay-anyone` most likely vanished on 2026-11-05, 08:10 by the OneDrive recycle bin, with no DELETE in any saved chat; it was rebuilt from the transcripts). A folder nobody tried to delete is now never touched, whatever its age (`tests/test_skills_tree.py` `HuskSweepTests`). `delete_skill_tree_entry` additionally reclaims a husk folder sitting at the deleted name's sanitized dirname (matched case-insensitively). **The layer is case-folding-aware** (second live incident 2026-08-07: renaming Test-skill→test-skill then deleting the old one left folder `Test-skill` containing `name: test-skill` PLUS a spurious `test-skill_2` — Windows/macOS resolve `test-skill` into an existing `Test-skill`, so path checks alone can't tell whose folder it is): `_real_basename` reads the true on-disk casing, `_write_skill_file` claims a numbered sibling instead of writing into a differently-cased folder, and `_scan_skills_tree` HEALS on load — a case-mismatched folder renames to its natural name (pure case-fix or freed slot), a stranded `<name>_N` sibling relocates once the natural slot frees up, and a second folder holding an IDENTICAL entry is deleted as junk (like an identical conflict fork) — since 2026-09-28 only when its bundled resource files are the same too (`_same_resources`; a folder whose SKILL.md matched but whose `references/` differed was deleted with them), and two folders whose frontmatter claims the same name no longer overwrite one another: the second becomes a numbered variant (`_claim_duplicate` / `_variant_slot`). The SKILL.md-family guard is case-insensitive and a `:` in ANY path component is refused by `skill_resource_path`. The folder is the skill: future skills can carry helper scripts/resources next to their SKILL.md. SelfBot mirrors the same format in its no-myagent stub fallbacks (`_sb_skill_*`). Unit-tested in `tests/test_skills_tree.py`. **Transition caveat:** a machine still running pre-tree code sees no skills until it pulls (its skills.json was parked as `.migrated.bak` by the first tree-code launch to sync); recovery is `git pull` — the data is all in the tree.

**Agent Instructions** — Stored in `agent_instructions.json` as `{name: {text, notes, images: [{data, media_type, filename}], desktop, browser, meta, mcp, google, proton, outlook, excel, physical, conversational, dictation_auto_send, provider, model, temperature, thinking_enabled, thinking_effort, thinking_budget, thinking_mode, text_verbosity, fast_mode, upgrade_target: {provider, model, level}, skill_modes: {name: mode}, disabled_confirm_patterns: [str], blocked_tools: [str]}}`. Images are base64-embedded and re-attached on load. **`notes` (2026-10-20, the user's request)** is free text ABOUT the instruction — what it is for, caveats, what a run taught — shown and edited in the editor's **Notes dialog** since 2026-10-30 (the user's request: the three-row box that stood above the instruction text from 2026-10-20 became a **Notes** button right of Safety, Alt+O — at the left of the Auto-send / Announce row under the tool toggles since 2026-11-03, the user's request, still Alt+O — the dialog's contract follows) and carried like the text: `_save_instruction` stores it (stripped) and makes it the applied instruction's `agent_instruction_notes` (MyAgent.py `__init__`, `""`), Apply sets the live value without a store write, a page selection loads the entry's (an entry without the key shows an empty box), CLEAR empties it, `_apply_instruction_entry` restores it for `-l` and the relaunch, the applied snapshot carries it, and `manage_instructions` reads / creates / updates it (`""` clears). It is NEVER part of the prompt or of any provider request — a scan in `tests/test_instruction_notes.py` pins that no provider / prompt module names it — and not environment either: `_editor_env_snapshot` leaves it alone, so [X] after browsing pages changes nothing about it. **The Notes dialog (2026-10-30)** is a window onto the editor's notes DRAFT: `_instr_notes_text` holds the draft while the dialog is closed and the dialog's text box IS the draft while it is open — `_notes_draft` reads whichever applies, `_set_notes_draft` writes both and refreshes the title (`Notes — <name>` after the editor's name box; `Notes` with none) — so the editor's SAVE / Apply with the dialog still open take what is typed there, a page selection and CLEAR replace what it shows (the draft is set AFTER the name on both paths, so the title follows), and closing it — Close, [X], or the editor's close (`_close_editor` calls `_close_notes_dialog` before destroying the editor, the Safety dialog's treatment) — writes the box back into the string and remembers the geometry. Nothing reaches the disk but through the editor's SAVE, so the dialog has no Cancel and — a window holding a draft — no Escape-to-close — and, since 2026-10-31, no Close button (the user's request: the keys do it), so the text is the dialog's only control, [X] / Alt+F4 the close, and Escape in the text has nowhere to go (Alt+N the text). One at a time (a second press raises it), a child of the editor, transient on Windows, resizable, default 560×320, placed by `_place_window` under the kind `notes` — `notes_dialog_geometry`, the seventh `GEOMETRY_KINDS` entry, `_notes_dialog` in `_open_geometry_windows` — and the dialog's own close saves the state file at once (the Safety dialog's and the Skills Manager's rule) while the editor-driven close leaves that to the editor's path; coloured and title-barred by Other Setup like every Toplevel. Verified with the zero-token visual harness on Windows 2026-10-30 (the button right of Safety, the text pane the text alone, the dialog over the editor on the draft, typing read live, the text kept on close, the geometry cached under `notes`); pinned in `tests/test_instruction_notes.py` — the REAL dialog on a mapped transparent root, the draft helpers through the real editor paths, the wiring scan. Tool toggles, model params, skill modes, and disabled confirm patterns are all saved per-instruction and restored on load. Restoring an instruction's skill modes is **session-only**: `_restore_skill_modes` updates the live `self.skills` (which drives `_build_system_prompt`) but does NOT write back to the skills store, so loading an instruction — or restoring the last applied state on launch — never overwrites the user's global skill modes. Nor does a LATER skill save, since 2026-09-28: the tree's global modes are kept apart in `_skill_global_modes` (read by `_load_skills`), `_skills_for_tree` gives every entry its global mode at each `_save_skills`, and only `_set_skill_mode` (Cycle Mode, `manage_skills` create / update with a mode) changes one — a new skill joins the map with its own mode, a deleted one leaves it. Until then any skill save (a Skills Manager SAVE / Cycle Mode / DELETE, a `manage_skills` change) wrote `self.skills` whole — the instruction's session modes included — into the shared tree (reproduced in a scratch tree: saving an unrelated skill flipped two others' modes on disk). SelfBot carries in-file copies; pinned in `tests/test_review_followups.py`. The `skills/` tree is the sticky source of truth, changed only by explicit Skills Manager / `manage_skills` edits. Skills absent from the snapshot default to disabled (for that session only) — and since 2026-08-07 that forcing-off is VISIBLE: `_restore_skill_modes` posts a ⚠ naming any skill whose sticky store mode is non-disabled but which the applied snapshot omits (stashed in `_model_drift_warnings` so stream_worker re-posts it at run start past the `-l` output clear; SelfBot's prompt-bundle restore warns the same way). Found live: a freshly-[ON] skill silently vanished from the payload because the Default instruction's snapshot predated it — re-saving the instruction with the skill set is the remedy the warning names. Deleted skills are skipped. Old entries without `thinking_mode` infer it from `thinking_enabled`+`thinking_effort`; without `text_verbosity` default to `"medium"`.

**Every run saves its chat (2026-10-07)** — until then chats saved (on close or via the periodic auto-save) only if a name was typed in "Save Chat as", blank → no file, so a GUI run left no transcript while a `-l` / headless launch, which filled the box with `<Name>_<timestamp>`, always did (the user's request: the GUI should auto-name too). Now `_start_agent` calls `chat_mixin._name_run_chat` before resetting the run: the box's text when the user typed one, else a fresh `<Instruction>_<YYYY-MM-DD_HHMMSS>` (`Agent_…` with no instruction applied; `_new_auto_chat_name`) put into the box — also when the box still holds the auto name this app gave the PREVIOUS run (`_auto_chat_name`), because each START is a new conversation and reusing the name would overwrite that run's files; a typed or edited name is kept (and the next run overwrites it, as before). `_auto_launch` now just clears the box and relies on the same code — one place, one form. The helper records the file stem — the name as `_sanitize_filename` writes it, no extension — in `_run_chat_name`, which `stream_worker` snapshots at start beside the instruction name and hands to `_log_api_cost` as `chat=` → the cost log's 14th field (see **API cost tracking**). Both attributes start in `__init__`. Pinned in `tests/test_chat_autoname.py` (the helper on a fake box, the fresh name per START, the sanitised stem, wiring scans of `_start_agent` / `_auto_launch` / `stream_worker`, the line with and without a split, the real loop on both tails).

**Chats in the OneDrive share (2026-10-08)** — the chat files every run saves (`<name>.json` + `<name>.txt`) and the code-interpreter outputs (`ci_output_*`) go to `CHATS_DIR` = `<OneDrive>/MyAppShare/saved_chats/` (`datapaths.resolve_chats_dir`, the twin of `resolve_skills_dir`: the shared dir through the one `_ensured_shared_dir()` fallback — `MYAGENT_DATA_DIR` honoured, which is what keeps the test suite off the real folder — else the repo-root `saved_chats/`, where they always lived; `LOCAL_CHATS_DIR` in constants.py names that folder). The user's request: the folder was per machine (gitignored) while the stores and the cost log had been shared since July / August, so the cost log's CHAT column named a file only the machine that ran it could open; now every machine's runs write one folder and any machine reads it. Machines never write the same name — a run's files are `<Instruction>_<YYYY-MM-DD_HHMMSS>`, a typed "Save Chat as" name the user's own — so OneDrive only ever sees new files, and the worst case of a same-second run on two machines is a `<stem>-<Computer>.json` conflict fork nobody reads (MyAgent never loads a chat back). Every writer goes through `CHATS_DIR`: `_save_chat_file` / `_auto_save_on_close` (the periodic autosave and the close) always did; `check_queue`'s code-interpreter saves used a relative `"saved_chats"` — the process's CWD, not even the repo root — and `run_instruction`'s timeout message names the folder. **The history follows**, as it did for the stores and the cost log, but at launch and in the background rather than at resolve time: `MyAgent.py` `__init__` calls `chat_mixin._fold_local_chats_in` right after `_run_progress_fold_in`, which runs `datapaths.migrate_local_chats(LOCAL_CHATS_DIR, CHATS_DIR)` on a daemon thread (a first pass moves a few hundred files, and a copy into OneDrive's File Provider volume on the Mac must never hold the Tk thread) and posts one Activity line when files moved; a no-op where no shared dir is in use. What moves: ONLY MyAgent's chats — a `<stem>.json` whose top level carries `agent_instruction_name` (`_is_myagent_chat`) and its `<stem>.txt` twin. What stays: SelfBot's chats (the same folder, the same shape, `system_prompt_name` instead — SelfBot is per machine by design, and its duo chats are the 39 files git tracks), the `ci_output_*` files (either app's, unattributable), an unparseable file, a `.txt` without its `.json`, and a chat touched within `CHATS_SETTLE_SECS` (120 s — an instance still running rewrites its chat every `PERIODIC_SAVE_MS`, 10 s; the next launch folds it). Nothing is ever overwritten (`_chat_slot`): a file of the same name holding the SAME bytes absorbs the local copy (a half-done earlier pass), other content keeps its name and the local file lands as `<stem>__<machine label>`, numbered `_2`, `_3` … while that too is taken — the stores' conflict rule — and the `.txt` follows its `.json` to the stem it got, with a check of its own. `_move_file` renames on one volume and otherwise copies into a dot-prefixed `.<name>.<random>.part` temp file BESIDE the destination (mkstemp, exclusive), carries the mtime over so the share lists the chats in their order, renames it onto the final name — one atomic step within the share's volume, so the name never exists until it is complete, whatever kills the process mid-copy (a headless Heartbeat child ending while its fold-in still runs) — and deletes the source; a copy that fails is removed at once, a destination that appeared meanwhile is never replaced, and `_sweep_part_files`, run at the start of every pass, removes `.part` files older than `CHATS_PART_STALE_SECS` (an hour: a younger one may be a sibling instance's live copy, or another machine's arriving through the sync). Per chat best-effort: an error leaves it local for the next launch, which repeats the pass — idempotent, a folder with no MyAgent chat costs one listing. SelfBot's `CHATS_DIR` stays the repo root (pinned).
