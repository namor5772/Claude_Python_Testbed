## Architecture (MyAgent.py)

**Mixin-based modular design** — The `App` class in `MyAgent.py` inherits from 20 mixin classes in the `myagent/` package, each grouping related methods by concern (UI, streaming, tools, persistence, etc.). Constants and tool schemas live in `myagent/constants.py`; helper classes in `myagent/helpers.py`. Only `__init__` and the entry point remain in `MyAgent.py`. All mixins share state through `self.*` — no inter-mixin imports.

**Multi-provider support** — A Provider combobox switches between Anthropic, OpenAI, Gemini, and xAI (plus Ollama for local inference). The internal message format stays Anthropic-style; translation happens only at the API boundary: OpenAI uses `_messages_to_responses()`/`_tools_to_responses()`/`_stream_responses()`, Gemini uses `_messages_to_gemini()`/`_tools_to_gemini()`/`_stream_gemini_call()`, xAI reuses the Responses translators with its own `_stream_xai_call()` (see below). The `_ToolBlock` wrapper gives OpenAI/Gemini/xAI/Ollama dict-based tool responses the same `.name`/`.id`/`.input` interface as Anthropic's Pydantic objects, so `_execute_tool()` works identically for all providers. Gemini tool call IDs are synthesized as `gemini_{name}_{index}` (the API doesn't use IDs). Provider is saved per-instruction and in `agent_state.json`. The Instruction button is disabled while running. Gemini requires `GEMINI_API_KEY` or `GOOGLE_API_KEY`; xAI requires `XAI_API_KEY`.

**OpenAI model filtering** — `_fetch_openai_models()` filters to Responses-API-compatible families via `OPENAI_RESPONSES_PREFIXES` (`gpt-4o`, `gpt-4.1`, `gpt-4.5`, `gpt-5`, `o1`, `o3`, `o4`); non-chat types (embedding, audio, search, realtime, preview, transcribe, tts) and legacy models (gpt-3.5-turbo, base gpt-4, gpt-4-turbo) are excluded. `OPENAI_REASONING_PREFIXES` (`o1`, `o3`, `o4`, `gpt-5`) get `reasoning` params instead of `temperature`. `gpt-5.x-chat-*` "Instant" variants (`_is_gpt5_chat_model()`) are non-reasoning, reject temperature, but support `text.verbosity`. The client uses `httpx.Timeout(600.0, connect=10.0, read=120.0)` to avoid indefinite hangs.

**Gemini model filtering** — `_fetch_gemini_models()` calls `gemini_client.models.list()`, strips the `"models/"` prefix, then applies a two-stage agentic filter: require the `generateContent` action (drops bidi-only live/audio models, embeddings, imagen, veo), then drop `GEMINI_NON_AGENTIC_SUBSTRINGS` name matches — specialized output modalities (TTS, the `-image`/Nano Banana lines, lyria music, omni AV), Interactions-API managed agents (deep-research, antigravity), the computer-use preview (needs its own tool protocol), gemma (no function calling), robotics — plus shut-down generations (`gemini-2.0-*`, `gemini-1.*`, which the API still lists), falling back to `GEMINI_FALLBACK_MODELS`. What remains: the pro/flash/flash-lite text tiers, dated previews/variants (incl. `-customtools`, which is tuned to prefer registered custom tools — exactly MyAgent's pattern), and the floating `-latest` aliases. EVERY current text tier supports thinking — including Flash-Lite (verified live 2026-07) — so `GEMINI_THINKING_PREFIXES` has no "lite" carve-out. The config style is version-split by `_gemini_uses_thinking_level()`: Gemini 3+ (and the non-versioned `-latest` aliases, which float to 3.x+) send `thinking_level` (low/medium/high mapping 1:1 from the strength combo; a stale saved max coerces to high, and `gemini-3-pro-preview` coerces medium→high since it accepts only low|high), while 2.5 still requires the legacy `thinking_budget` (low=1024, medium=8192, high=24576 — sending `thinking_level` to a 2.5 model is HTTP 400). Both styles set `include_thoughts=True` so thought summaries stream to the Show Thinking pane (without it Gemini returns no thought parts at all). A reactive fallback in `_stream_gemini_call` retries once with the other style on a thinking-related 400, covering models/aliases whose style the version rules mispredict. SDK is `google-genai`, initialized with `GEMINI_API_KEY` or `GOOGLE_API_KEY`.

**xAI (Grok) integration** — `myagent/xai_mixin.py` rides on the already-installed `openai` SDK with `base_url="https://api.x.ai/v1"` (`XAI_DEFAULT_BASE_URL`) and `XAI_API_KEY` — no new dependency. xAI's primary surface is an OpenAI-style **Responses API** (same `input` items, flat `type:"function"` tool declarations, `function_call_output` results), so the existing `_messages_to_responses()`/`_tools_to_responses()` translators are reused verbatim; only the streaming caller is xAI's own. Architecture invariants:
1. **Raw event iteration, not the SDK stream wrapper** — `_stream_xai_events` consumes `client.responses.create(stream=True)` events directly instead of `responses.stream()`, whose client-side snapshot state machine is tuned to OpenAI's exact event sequences. Usage comes from the `response.completed` event (not `get_final_response()`); reasoning deltas are accepted as BOTH `response.reasoning_text.delta` and `response.reasoning_summary_text.delta` (models differ) and feed the Show Thinking pane.
2. **Server-side tools ON, mixing verified** — live probes (2026-07-05) proved xAI's built-ins mix cleanly with client-side function tools in one request (correct routing whichever the task needs), so xAI follows the OpenAI pattern: `_get_tools()` strips the local DuckDuckGo `web_search`/`fetch_webpage` and `_stream_xai_call` appends `{"type": "web_search"}` + `{"type": "x_search"}`, plus `{"type": "code_interpreter"}` gated off while desktop tools are on (same double-scaled-clicks rationale as OpenAI). Each invocation bills a flat $0.005, folded into the authoritative cost (below). Server activity streams as `web_search_call`/`code_interpreter_call`/`custom_tool_call` (x_search) output items → surfaced as activity notices; a 400 naming a built-in strips just that tool and retries.
3. **Reasoning knob per family** — `XAI_REASONING_EFFORT` (constants) maps prefixes to accepted `reasoning.effort` values, longest prefix wins: `grok-4.3` none/low/medium/high (low = API default; "none" disables reasoning), `grok-4.5` low..xhigh (always-reasoning — "none" is HTTP 400, verified live 2026-07-17), `grok-4.20-multi-agent` low..xhigh (the knob is agent collaboration count, not depth). Families absent from the table — the pinned `grok-4.20-*-reasoning`/`-non-reasoning` variants and the aliases (bare `grok-4.20` → the pinned reasoning variant, `grok-latest` → grok-4.3 at its server default) — get NO reasoning param; behaviour is baked into the model id. `_model_supports_thinking()` returns "extended" for knob families → the OpenAI-style Reasoning combobox; a stale saved effort coerces to the family default ("low") instead of erroring. Reasoning summaries verified streaming live (grok-4.3 emits them even at effort=low).
4. **Temperature alongside reasoning** (Gemini-style) — always shown in the UI and always sent; `_stream_xai_call`'s BadRequest downgrade ladder (drop temperature → drop reasoning summary → drop reasoning, each via `continue` so successive 400s converge) degrades gracefully if a model refuses. `openai.AuthenticationError` is surfaced as a clear "check XAI_API_KEY" error instead of ten retries.
5. **Model fetch + filtering** — `_fetch_xai_models()` lists `/v1/models`, keeps `grok*` ids, drops `XAI_NON_AGENTIC_SUBSTRINGS` (the grok-imagine image/video models), falls back to `XAI_FALLBACK_MODELS` (grok-4.3 default) — which matches the live catalog 1:1 (verified 2026-07-17): the API serves exactly grok-4.3, grok-4.5 (the agentic-coding flagship, 500K context, vision, added 2026-07), the three grok-4.20 variants, and grok-build-0.1; ALL legacy families (grok-4/-fast, grok-3, grok-2) are retired, with grok-code-fast-1 surviving only as an alias of grok-build-0.1. Aliases are alias *fields*, not list entries, so the picker shows canonical ids only. `XAI_NON_VISION_PREFIXES` (grok-build-0, grok-code) drives the weak-desktop-combo warning — text-only per docs; the prefix is `grok-build-0`, not `grok-build`, because `grok-build-latest` re-aliased to grok-4.5 (vision) in the 2026-07 catalog.
6. **Exact cost tracking via `cost_in_usd_ticks`** — xAI is the only provider that returns the authoritative billed cost in the response (`usage.cost_in_usd_ticks`, 1 tick = $1e-10, verified to the digit against hand-computed pricing). `_stream_xai_events` converts it to `usage_dict["cost_usd"]` and `stream_worker` prefers it over the table estimate, so the cost line is exact — including the cached-input discount ($0.20/M vs $1.25/M full rate; xAI caches aggressively) and the $0.005/server-tool fees, neither visible to a 2-tuple estimate. `XAI_PRICING` (verified live against /v1/models' price fields, unit $1/10000 per MTok: grok-4.3 + all grok-4.20 variants $1.25/$2.50, grok-4.5 $2/$6 — incl. the re-aliased grok-build-latest, whose longer entry outranks the grok-build prefix — grok-build and its grok-code-fast alias $1/$2, grok-latest alias) remains as the fallback when the field is absent; >200K-input long-context doubling keeps the ≤200K tier (gemini-3.1-pro convention). Documented in `MyAgent_Pricing.txt`.
7. **Live-verified end-to-end 2026-07-05** — a real grok-4.3 `stream_worker` run (tool round trip via local `web_search`, effort=low) confirmed: streaming text + reasoning-summary deltas arrive, xAI's UUID-style `call-…` tool ids round-trip through `function_call_output`, usage lands in `response.completed`, and the cost tracker matched hand-computed pricing to the digit ($0.002954 for 1771 in / 296 out).

**Temperature/thinking UI visibility** — Model parameter controls are dynamically shown/hidden (not just disabled) based on the selected model's capabilities. `_forget_all_model_widgets()` resets all widgets at the start of `_on_model_selected()` to guarantee correct pack order when switching model types. Rules:
- Models without thinking support hide the thinking checkbox + strength combo, showing only temperature (or just verbosity for `gpt-5.x-chat-*` Instant models, which reject temperature).
- OpenAI reasoning models hide temperature entirely.
- Anthropic adaptive models replace checkbox+strength with a **Thinking mode combobox** whose values are built per-model by `_anthropic_mode_values()`: Off/Adaptive/Low/Medium/High, plus Xhigh (Opus 4.7+, Sonnet 5+, Fable/Mythos 5) and Max (Opus 4.6+, Sonnet 4.6+, Fable/Mythos 5); temperature is hidden when thinking is active. The per-family gates were verified live 2026-07 against the Models API capability tree (`m.capabilities["effort"]`); minor-less Claude 5 ids parse as `(major, 0)` in `_parse_claude_major_minor`, so `claude-sonnet-5` hits the `claude-sonnet- >= (5, 0)` rules without a hardcoded list.
- **Claude Sonnet 5 (`claude-sonnet-5`)** is adaptive-only (`budget_tokens` is HTTP 400), rejects non-default temperature (`_anthropic_rejects_temperature` covers sonnet >= 5.0), supports effort up to Xhigh/Max, and — unlike Sonnet 4.6 — **runs ADAPTIVE thinking when the `thinking` param is omitted**. `_anthropic_thinking_on_by_default()` detects this family, and `_stream_anthropic_call`'s off-branch sends an explicit `thinking={"type": "disabled"}` for it so "Off" really is off (otherwise the model silently thinks against the non-thinking 8K max_tokens cap with the Show Thinking pane dark). Pricing is in `ANTHROPIC_PRICING` at the launch intro rate ($2/$10 per MTok through 2026-08-31 — flip to $3/$15 from September).
- **Claude 5 Mythos-class models (`claude-fable-5`/`claude-mythos-5`, matched by `ALWAYS_ON_THINKING_PREFIXES`) have always-on thinking** — an explicit disable or `budget_tokens` is HTTP 400. The combo drops "Off" (a stale saved "Off" coerces to Adaptive; headless runs, which skip the UI coercion, get the same override inside `_stream_anthropic_call`), temperature is never sent (`_anthropic_rejects_temperature` covers them alongside Opus 4.7+), and pricing ($10/$50 per MTok) is in `ANTHROPIC_PRICING`. Adaptive thinking is sent as `{"type": "adaptive", "display": "summarized"}` so the Show Thinking pane gets readable text on Fable 5 / Opus 4.7+, whose API default became "omitted" (empty thinking deltas); 4.6 already summarizes, so the field is a no-op there. Fable 5 safety classifiers can end a call with `stop_reason="refusal"` (HTTP 200, possibly empty content) — `_stream_anthropic_call` surfaces it as a ⚠ warning with the `stop_details` category/explanation instead of letting the run end silently.
- Gemini shows temperature alongside thinking controls (the API accepts both).
- GPT-5.1+ use a **Reasoning combobox** (None/Low/Medium/High; Xhigh for gpt-5.2+/codex-max, but mini/nano cap at High). GPT-5.4+ show temperature when reasoning is "None"; older gpt-5 keep it hidden. GPT-5.0 base adds "minimal".
- All gpt-5 (incl. `-chat`) show a **Verbosity combobox** (Low/Medium/High → `text.verbosity`).

The Thinking/Reasoning label and its dropdown are always packed adjacently; `_on_thinking_toggled()` delegates to `_on_model_selected()` to maintain pack order. Detection helpers: `_parse_gpt5_minor()`, `_is_gpt5_family()`, `_is_gpt5_chat_model()`, `_has_reasoning_none()`, `_has_reasoning_xhigh()`, `_has_openai_verbosity()`, `_gpt5_supports_temp_at_none()`.

**Agentic loop** — `stream_worker()` runs a `while True:` loop: dispatches to `_stream_anthropic_call()`/`_stream_responses_call()`/`_stream_gemini_call()` by provider, streams the response, executes tool calls, appends results, loops. Exits on `end_turn` or when `stop_requested` is set via STOP. No fixed iteration limit.

**Tool system** — Four static lists (`TOOLS`, `DESKTOP_TOOLS`, `BROWSER_TOOLS`, `META_TOOLS`) plus dynamic `MCP_TOOLS` in `constants.py`, assembled by `_get_tools()` in `streaming_mixin.py`. `TOOLS` is always included; the rest are gated by their checkboxes. Dispatch is in `_execute_tool()`. `find_element` is provider-gated — `_get_tools()` strips it for non-Gemini providers (it uses Gemini's native pointing API). Adding a static tool requires: (1) schema dict in the right list in `constants.py`, (2) `elif` branch in `_execute_tool()`, (3) `do_<name>()` in the appropriate mixin, and optionally (4) adding the name to `PARALLEL_SAFE_TOOLS` if thread-safe and stateless. MCP tools are added at runtime — see below.

**MCP integration** — `myagent/mcp_mixin.py` connects to Model Context Protocol servers (filesystem, GitHub, Slack, etc.) at startup, enumerates each server's tools via the `mcp` Python SDK, and exposes them through the same `_get_tools()`/`_execute_tool()` pipeline as native tools. Architecture invariants:
1. **Async-only SDK** — `MCPMixin` runs a dedicated asyncio loop in a background thread (`self._mcp_thread`); the sync streaming worker calls in via `asyncio.run_coroutine_threadsafe`.
2. **One `AsyncExitStack`, one long-lived runner** — all server connections live in a single stack owned by `_mcp_runner`, which connects, lists tools, then parks on `self._mcp_shutdown_event` for the whole session. Required because anyio binds task-group cancel scopes to the originating task: splitting the lifecycle across multiple `run_coroutine_threadsafe` calls would kill the stdio pumps and surface as `Connection closed` on the next `list_tools`. Shutdown signals the runner; the stack unwinds sessions/stdio_clients LIFO and subprocesses exit. A post-unwind `gc.collect()` + two `await asyncio.sleep(0)` cycles drain pending pipe-close callbacks to avoid harmless `Event loop is closed` finalizer tracebacks.
3. **Namespaced tool names `<server>__<tool>`** (double underscore — valid for all four providers' regexes); `_execute_tool` looks up `block.name` in `self._mcp_tools_by_name` and routes to `do_mcp_call` before the static dispatch chain.
4. **Per-user config** in `mcp_servers.json` (root), same shape as Claude Desktop / Cursor, so community servers drop in unchanged. `${NAME}` placeholders in `env` values are substituted at spawn time by `_substitute_placeholders`: `${RANDOM_PORT}` is reserved (each occurrence → an independent OS-assigned free port; does not consult `os.environ`), any other `${NAME}` → `os.environ[NAME]` (or empty + a one-shot warning). Substitution is scoped to user-typed `spec["env"]` keys only — not the ambient env, not `command`/`args` (so secrets don't leak via process listings). This keeps `mcp_servers.json` secret-free and safe to track.
5. **Graceful degradation** — without `mcp` installed, `_HAS_MCP` is False, the checkbox is disabled, and every method is a no-op.
6. **Deferred connect** via `root.after(100, self._connect_mcp_servers)` so a slow handshake never blocks launch; per-server failures are logged, not fatal.
7. **Dual-sink `_mcp_log`** — status lines go to both the GUI queue and `sys.stderr`; launch with `python.exe` or `pythonw.exe MyAgent.py 2> mcp.log` to capture the MCP stream off-process. `mcp_enabled` persisted per-instruction. To enable: `pip install mcp`, drop in `mcp_servers.json`, restart, tick the MCP checkbox.
8. **Windows ProactorEventLoop hardening** — three settings prevent `ClosedResourceError` / spurious EOF on the first RPC after `initialize()`, all rooted in IOCP fragility: (a) pass `errlog=os.devnull` (opened once in `_connect_mcp_servers`) to every `stdio_client` — under `pythonw.exe` `sys.stderr` is None, which corrupts IOCP routing; (b) create the loop with `asyncio.new_event_loop()` *inside* `_loop_runner`, since IOCP ownership binds to the constructing thread; (c) pass an explicit `list_roots_callback` returning `ListRootsResult(roots=[])` — the SDK default returns an error and skips advertising the roots capability, which some servers (e.g. `server-filesystem`) handle badly.
9. **Reconnect-on-close** — if `list_tools` raises `ClosedResourceError`/`Connection closed`, `_list_tools_for_server` opens a fresh session via `_open_server_session`, swaps it into `_mcp_sessions[name]`, and retries. Belt-and-braces; (8) is the real fix and this rarely fires.

**Google (Gmail) integration** — `myagent/gmail_mixin.py` adds native multi-account Gmail tools via `google-api-python-client`, NOT MCP. Sixteen tools (`gmail_search`/`read`/`get_attachment`/`send`/`reply`/`create_draft`/`list_drafts`/`send_draft`/`trash`/`untrash`/`list_labels`/`create_label`/`delete_label`/`modify_labels`/`mark_read`/`list_threads`) flow through the same `_get_tools()`/`_execute_tool()` paths as native tools. `gmail_reply` builds proper In-Reply-To/References headers and reuses the original threadId so replies nest; `gmail_send`/`reply`/`create_draft` take optional `attachments: [filepath]` (combined raw cap 20 MB, under Gmail's 25 MB post-base64 ceiling; MIME auto-detected). Architecture invariants:
1. **Per-account OAuth, single process** — tokens at `~/.config/myagent-google/{account}_token.json`, shared client at `oauth_client.json`, account list at `accounts.json`. `_gmail_service(account)` runs `InstalledAppFlow...run_local_server(port=0, prompt="select_account")` once per account, then refreshes silently from the stored refresh token.
2. **Account enum patched at runtime in `_get_tools()`** — each tool's `account` field gets `enum=[...accounts.json names...]` injected before schemas ship; empty `accounts.json` → empty enum (a clearer error than dropping the tools).
3. **Scope `gmail.modify` only** — read/send/draft/label/trash but NOT permanent delete (a deliberate safety boundary; permanent delete would need the broader `https://mail.google.com/` scope and a separate tool).
4. **Destructive ops gated by `_confirm_gmail_action`** — `gmail_send`/`send_draft`/`trash` pop a Tk `askyesno` showing recipient/subject/IDs; denial returns `"user denied: ..."` so the agent continues. Dispatch routes via `block.name.startswith("gmail_")`.
5. **`_HAS_GOOGLE` flag** mirrors `_HAS_MCP`: missing libs → checkbox disabled, methods no-op. `google_enabled` persisted per-instruction.
6. **Native, not MCP** — a tight 16-tool catalog (vs MCP's 55+) saves token budget; multi-account is one parameter instead of two subprocesses; destructive ops get a real dialog; and the OAuth/token plumbing is reusable for future Google services (Calendar, Drive, Sheets).

**Proton Mail integration** — `myagent/protonmail_mixin.py` adds native multi-account Proton tools via Proton Bridge over stdlib IMAP+SMTP — NOT MCP and NOT a REST API (Proton publishes none; E2E encryption means decryption is client-side, so Bridge is the official integration path). Its sixteen tools mirror the Gmail surface 1:1 (same names with `proton_` prefix), with the same In-Reply-To/References handling and optional `attachments` (20 MB cap, MIME auto-detected). Architecture invariants:
1. **Per-account Bridge credentials, no OAuth** — config at `~/.config/myagent-protonmail/accounts.json`: `email`, `username`, `app_password` (Bridge-generated, NOT the Proton login), per-account `imap_host`/`imap_port`/`smtp_host`/`smtp_port`, and optional `ca_cert_path` (Bridge's exported `cert.pem`) for verified TLS. Absent/missing cert → `CERT_NONE` (acceptable for localhost-only Bridge traffic, where a MITM already needs code execution on the machine). IMAP connections are cached per-account; SMTP opens fresh per send.
2. **Account enum patched at runtime** — same `_get_tools()` pattern as Gmail.
3. **No "scope" concept** — Bridge gates the surface server-side (no permanent delete, no settings); Trash is recoverable from Proton's UI.
4. **Destructive ops gated by `_confirm_proton_action`** — `proton_send`/`reply`/`send_draft`/`trash`/`delete_label`; same dialog + per-tool bypass as Gmail (stored in `disabled_confirm_patterns`). Dispatch via `block.name.startswith("proton_")`.
5. **`_HAS_PROTONMAIL`** is always True on CPython (stdlib `imaplib`+`smtplib`+`email` transport); kept for parity. Bridge availability is detected at first-call time, not startup, so Bridge restarts reconnect transparently. `proton_enabled` persisted per-instruction.
6. **IMAP UIDs are per-folder** — per-message tools take a (`folder`, `uid`) pair; bulk ops take `folder` + `uids: [int]`. UIDs are never reused (RFC 3501), so a MOVE → MOVE-back round-trip yields three distinct UIDs for the same logical message.
7. **Four helpers renamed `_proton_*`** (`_format_proton_summary`, `_extract_proton_bodies`, `_extract_proton_attachments`, `_attach_proton_files`) to avoid MRO shadowing: the App's mixin order (`...GmailMixin, ProtonMailMixin...`) means Gmail's identically-named statics would otherwise win the left-to-right MRO and silently break Proton (empty bodies, arity crashes). A foundational footgun of flat-namespace mixins — defensively prefix non-shared helpers.
8. **Four empirical Bridge/dovecot quirks, mitigated**:
   - (a) **SUBJECT search** is reliable for single-word substrings but fragile for multi-word substrings against non-ASCII subjects (curly quotes, em-dashes, accented letters); the `proton_search` description steers toward single words, and `_uid_search` switches to `CHARSET UTF-8` byte-literals for non-ASCII queries.
   - (b) **`Labels/X` MOVE is additive, not exclusive** — INBOX→`Labels/Foo` just adds the label; moving back removes it. System folders (INBOX/Sent/Drafts/Trash/Archive/Spam) are true exclusive destinations. Documented in `proton_modify_labels`.
   - (c) **Label removal can leave a transient new UID** in the source (Bridge↔Proton eventual consistency); `do_proton_modify_labels` snapshots source UIDs, detects strays after the MOVE, and re-MOVEs them up to 2×, reporting `label_removal_retries: N` (0 = clean).
   - (d) **Bare-token SEARCH works on Bridge, dovecot rejects it** — `q="invoice"` is a loose full-text match on Bridge but errors `BAD Unknown argument` on dovecot/cPanel (WebCentral). The description steers toward the explicit-key form (`SUBJECT`/`BODY`/`TEXT`/`FROM`/`TO "..."`), which works on both.
9. **Native, not MCP** — same rationale as Gmail, plus credential hygiene via Bridge's per-install app-password (never the real Proton login or mailbox password).

**Outlook / Microsoft 365 integration** — `myagent/outlook_mixin.py` adds native multi-account Outlook tools via the **Microsoft Graph API** authenticated with **MSAL** — NOT MCP and NOT IMAP/SMTP (Microsoft disabled Basic Auth for personal outlook.com IMAP/POP/SMTP in late 2024; even IMAP now needs OAuth2, so Graph is the modern path and maps onto the Gmail OAuth pattern). Its sixteen tools mirror the Gmail surface 1:1 (same names with `outlook_` prefix), with proper conversation threading and optional `attachments` (~3 MB cap, MIME auto-detected). Architecture invariants:
1. **OAuth via MSAL, single process** — token caches at `~/.config/myagent-msmail/{account}_token.json` (chmod 600), Azure app client_id at `msal_app.json` (or `OUTLOOK_CLIENT_ID`/`MS_CLIENT_ID` env), account list at `accounts.json`. `_outlook_token(account)` tries `acquire_token_silent` first, falls back to `acquire_token_interactive(prompt="select_account")` (transient localhost redirect server), then refreshes silently. A `PublicClientApplication` is cached per account in `self._outlook_apps`. A 401 forces one token re-acquire + retry inside `_outlook_graph`.
2. **Account enum patched at runtime in `_get_tools()`** — each tool's `account` field gets `enum=[...accounts.json names...]`; empty `accounts.json` → empty enum (clearer error than dropping the tools). Same pattern as Gmail/Proton.
3. **Scope `Mail.ReadWrite` + `Mail.Send` only** — read/send/draft/move/categories/mark-read but NOT permanent delete (a deliberate safety boundary mirroring Gmail's; Deleted Items is recoverable from Outlook's UI).
4. **Destructive ops gated by `_confirm_outlook_action`** — `outlook_send`/`reply`/`send_draft`/`trash`/`delete_label` pop a Tk `askyesno`; denial returns `"user denied: ..."`. `outlook_reply` deletes its server-side `createReply` draft on denial so nothing is left behind. Dispatch routes via `block.name.startswith("outlook_")`. Confirm bypass via the Safety dialog's "Outlook destructive tools" section (shared `_disabled_confirm_patterns`).
5. **`_HAS_OUTLOOK` flag** mirrors `_HAS_GOOGLE`/`_HAS_PROTONMAIL`: missing `msal` → checkbox disabled, methods no-op. `outlook_enabled` persisted per-instruction and in `agent_state.json`.
6. **Gmail "labels" → Outlook "categories"** — `outlook_list/create/delete_label` wrap `/me/outlook/masterCategories`; `outlook_modify_labels` operates on category **display names** (not ids) because Graph stores `message.categories` as a name array, reading current categories and applying the add/remove diff. `outlook_trash` is a Graph `move` to the well-known `deleteditems` folder (each move yields a NEW message id, returned as `moved_ids` — same per-move-id-churn gotcha as Proton's per-folder UIDs).
7. **Single body, not multipart** — Graph messages have one body (`contentType: html|text`); when `body_html` is supplied it is sent as the body and the plain `body` is dropped (`_outlook_body_field`). A draft IS a message, so `outlook_send_draft` takes the draft's message id.
8. **All non-shared helpers prefixed `_outlook_`** — `OutlookMixin` is last of the three mail mixins in the App's MRO (`...GmailMixin, ProtonMailMixin, OutlookMixin...`), so prefixing avoids the flat-namespace shadowing footgun (Gmail's `_header`/`_extract_bodies`/etc. would otherwise win the MRO).
9. **Native, not MCP** — same rationale as Gmail: a tight 16-tool catalog, multi-account by one parameter, real confirmation dialogs, and reusable MSAL/token plumbing for future Microsoft Graph services (Calendar, OneDrive).

**Local document reader** — `myagent/document_mixin.py` adds one tool, `read_document(path, max_chars?, pages?)`, extracting text from PDF (`pypdf`), DOCX (`python-docx`), HTML (via `extract_text_from_html` in `helpers.py`), and most plain-text/source formats. Architecture invariants:
1. **Provider-agnostic** — operates on local file paths, so it pairs with `gmail_get_attachment`/`proton_get_attachment`/`fetch_webpage` with no source-specific wiring. The local filesystem is the boundary between provider-specific download and format-specific extraction.
2. **Always-available** — in static `TOOLS` (no checkbox) and in `PARALLEL_SAFE_TOOLS` (read-only, stateless).
3. **Graceful degradation** via `_HAS_PYPDF`/`_HAS_DOCX` — a missing lib makes only that format return a `pip install` hint; others keep working. Plain text and HTML have no dependency.
4. **Per-format extras** — PDFs return `page_count`/`pages_extracted`/`metadata`; DOCX returns `paragraph_count`/`table_count`/core properties, with tables rendered as `|`-separated rows to preserve column structure.
5. **PDF page ranges** — optional `pages` accepts `"1-5"`/`"3"`/`"1,3,5-7"` (1-indexed); out-of-range values are dropped for a partial result rather than an error.
6. **Encrypted-PDF detection** — tries empty-password decryption (common for owner-password-only PDFs); on failure returns a clear message and suggests `qpdf --decrypt` via `run_command`.
7. **Per-page error isolation** — a malformed page gets a `[page N: extraction error]` placeholder and extraction continues.
8. **Unknown extensions** — tries UTF-8 decode (catches mislabelled text), else a 256-byte hex preview; suggests `file`/`unzip`/`pandoc`/`ffprobe` for the deliberately-unsupported long tail (XLSX, ZIP, RTF, EPUB, A/V).
9. **Paired with the on-demand skill "Email Attachment Processing"** (`skills.json`) documenting the `_read → _get_attachment → read_document → reason` pattern; on-demand so it costs zero base-prompt tokens.

**Click accuracy pipeline** — Desktop click invariants, refined for cross-provider accuracy:
- All providers receive **pixel coordinates** (no [0, 1000] normalization) — what the model reads in the image is what it passes to `mouse_click`. The old Gemini [0, 1000] convention caused ~1-pixel drift and broke entirely under multi-monitor mixed-DPI.
- `do_mouse_click`/`_scroll`/`_drag`/`_read_screen_text` use `round(float(x))` (not `int(x)`) to avoid truncation bias.
- A pre-screenshot guard refuses click/scroll/drag/OCR with "Take a screenshot first" when `_screenshot_dims == (0, 0)`.
- Tiered out-of-bounds policy: ≤2px overflow clamps silently; >2% of the dimension refuses with a "re-take a screenshot" message; in between clamps with a `⚠ clamped` warning.
- A 50ms `time.sleep` after `pyautogui.click` lets the UI settle before the next screenshot.
- The `_capture_single_display` region branch snapshots `entry_scale`/`entry_offset` at entry so chained region screenshots don't drift through stacked offsets.

**Per-display state tracking** — Multi-display coordinate state lives in two parallel dict pairs:
- `_display_states[N]`/`_display_images[N]` — the **most recent capture** (full or region) for display N. Used by `mouse_click`, `find_element`, and any `display=N` tool.
- `_display_full_states[N]`/`_display_full_images[N]` — the **most recent FULL capture** for display N, never overwritten by region captures. Region screenshots (`screenshot(display=1, x, y, width, height)`) interpret their coordinates in this full-image space, not relative to the last capture — without this two-slot split, chained region screenshots drift through stacked offsets.

`_resolve_coord_state(display)` is the shared lookup: returns `_display_states[display]` if a `display` param is given, else the current `_screenshot_scale/offset/dims`. `mouse_click`, `mouse_scroll`, `mouse_drag`, `read_screen_text`, and `find_element` all accept an optional `display` so the model can disambiguate screens without re-screenshotting.

**Image resolution caps per provider** — `_capture_single_display` resizes to each API's actual limit:
- **Anthropic**: `1568` long edge / `1.15 MP` — the API silently downscales to this anyway.
- **OpenAI**: `2048` long edge / `5 MP` — verified the API silently downscales above 2048 (gpt-5.2 reported `PIL.Image.size == (2048, 1152)`), so 2048 keeps `_screenshot_scale` matching what the model sees.
- **Gemini**: `2048` long edge / `4 MP` — higher than Anthropic's because Gemini's 768×768 tile system gives small UI elements more pixel density.

**find_element tool (Gemini-only)** — Uses Gemini's native spatial pointing API to locate UI elements by description. `gemini_mixin.py:do_gemini_find_element` uses Google's *exact* documented prompt (`"Point to the X. The answer should follow the json format: [{\"point\": <point>, \"label\": <label1>}, ...]. The points are in [y, x] format normalized to 0-1000."`) — the trained pointing capability only fires on this phrasing. Parses both the array shape and a single-object fallback. Takes an optional `display` so the cached-image lookup hits the right screen (`_display_images[display]`). Returns pixel coordinates (converted from [0, 1000]) and names the exact `mouse_click` to make. Stripped from `_get_tools()` for non-Gemini providers.

**Grid overlay** — `do_screenshot` accepts optional `grid=true`; `_capture_single_display` then calls `_draw_coord_grid(img)` after the API-limit resize (so labels match what the model sees), drawing 100px magenta gridlines with `(x,y)` labels at intersections (skipping (0,0)). Opt-in / default-off so it doesn't obscure small text; the tool description nudges its use for small/dense UI.

**Diag checkbox** — `Diag` (next to `Save Thinking`) gates `[DIAG capture]`/`[DIAG click]` activity lines showing the full coordinate-mapping trail (display rects, physical/logical/sent-to-model dims, scale, offset, raw input, computed screen pixels). Persisted as `diag_enabled`. Independent of `Debug` (which controls API JSON payload display). Defaults on.

**Code interpreter gating (OpenAI)** — `_stream_responses_call` and `_payload_for_display` skip `code_interpreter` when desktop tools are on (`self.desktop_enabled.get() and _HAS_DESKTOP`). With CI access, gpt-5.2 loads screenshot bytes via PIL, sees the API-resized dimensions, and pre-scales coordinates itself — colliding with our scaling and producing double-scaled clicks. Stripping CI forces direct visual perception. CI stays available for non-desktop OpenAI tasks (data analysis, file processing, etc.).

**OpenAI tool rejection cache** — Newer models can reject server-side tools with HTTP 400 (e.g. `gpt-5.2-pro` rejects `code_interpreter`). `_stream_responses_call`'s `BadRequestError` handler regex-extracts the tool name from the message, adds it to `self._openai_unsupported_tools[model_id]`, strips it, and retries once — caching so later calls in the session skip it upfront. Same pattern as the temperature retry.

**Weak desktop combo warning** — `_weak_desktop_combo_warning()` (streaming_mixin) returns a warning string for weak-click-precision provider/models: gpt-5 at reasoning none/minimal, gpt-5 `-chat` Instant variants, any `gemini-2.x`. `stream_worker` posts it as `⚠ ...` at agent start. Informational only — doesn't change behaviour or override the model. Anthropic, gpt-4, gpt-5 ≥ low, and gemini-3.x pass clean.

**Parallel tool execution** — When the model requests multiple tools in one turn, blocks are partitioned into parallel-safe (`web_search`, `fetch_webpage`, `csv_search`, `get_skill`) and sequential (everything else). Parallel-safe run concurrently via `concurrent.futures.ThreadPoolExecutor`; sequential run one at a time in order. Results go into a pre-allocated list indexed by original position, preserving API-expected ordering.

**Conversational mode** — Per-instruction `conversational` toggle (Convo checkbox) enforcing a chatbot loop: when the model ends a turn without calling `user_prompt` and the toggle is on, `stream_worker` invokes `do_user_prompt` directly, appends the reply as a regular user message, and continues. Empty/`quit`/`exit`/`stop` ends cleanly. Unlike the 2+-calls "established pattern" nudge (which coaxes the model back to self-driven `user_prompt`), this bypasses model compliance entirely — for smaller open-weights models (Qwen3, Llama, gpt-oss) that don't follow the meta-rule. Default off so one-shot tasks exit normally.

**Agent Instructions** — Stored in `agent_instructions.json` as `{name: {text, images: [{data, media_type, filename}], desktop, browser, meta, mcp, conversational, provider, model, temperature, thinking_enabled, thinking_effort, thinking_budget, thinking_mode, text_verbosity, skill_modes: {name: mode}, disabled_confirm_patterns: [str]}}`. Images are base64-embedded and re-attached on load. Tool toggles, model params, skill modes, and disabled confirm patterns are all saved per-instruction and restored on load. Restoring an instruction's skill modes is **session-only**: `_restore_skill_modes` updates the live `self.skills` (which drives `_build_system_prompt`) but does NOT write back to `skills.json`, so loading an instruction — or restoring the last applied state on launch — never overwrites the user's global skill modes. `skills.json` is the sticky source of truth, changed only by explicit Skills Manager / `manage_skills` edits. Skills absent from the snapshot default to disabled (for that session only); deleted skills are skipped. Old entries without `thinking_mode` infer it from `thinking_enabled`+`thinking_effort`; without `text_verbosity` default to `"medium"`.

**Editor draft/commit model** — The instruction editor works on temporary copies (`_editor_images`/`_editor_desktop`/`_editor_browser`); changes commit to live state only on SAVE (→ disk) or Apply (session-only). Closing with [X] discards them. Model params and skill modes are restored immediately on instruction selection (they're environment-level, not draft state). Model/provider widgets exist only while the editor is open; refs are set to `None` via `_nullify_editor_widgets()` on close/Apply so `_has_model_widgets()` guards skip stale updates. Current provider/model show in the title bar via `_update_title()`.

**Threading model** — Same as SelfBot: a background daemon thread for API calls, a `queue.Queue` for events, main thread polling every 50ms via `root.after()`.

**PowerShell Safety dialog** — The "PS Safety" button (in the editor, next to Skills) lists all `COMMAND_CONFIRM` patterns as checkboxes: checked = confirm required (default), unchecked = bypass + a `⚠ Confirm bypassed` warning. Disabled patterns persist per-instruction as `disabled_confirm_patterns`. The bypass warning uses the `"warning"` queue type (always shown, regardless of Activity). The button label shows a count when patterns are bypassed (e.g. `PS Safety (3 bypassed)`).

**Command-line launch** — `python MyAgent.py -l "Name"` auto-loads a saved instruction and starts the agent (`argparse` `-l`/`--load`). `_auto_launch()` is scheduled via `root.after(100)` (UI ready), then `_start_agent` via `root.after(200)` (one event-loop cycle between state setup and start). Unknown names show an error dialog listing the available ones. `-l` also auto-fills "Save Chat as" with `"{Name}_{timestamp}"` so output is captured.

**Headless mode** — `--headless` runs without a main window (`root.withdraw()`); dialogs skip `transient()`/`grab_set()` so they float standalone. The process auto-closes after the loop completes. For orchestrator patterns where a parent spawns child instances via `run_command`.

**Meta-agent tools** — Three tools in `META_TOOLS` (gated by the Meta checkbox). Two CRUD tools (`manage_instructions`, `manage_skills`) use one `action` param (`list`/`read`/`create`/`update`/`delete`) to keep the tool count low. `manage_instructions` create inherits the current provider/model/thinking settings; `read` returns all model params; `update` accepts them as optional fields alongside text/desktop/browser/meta/skill_modes. `manage_skills` updates the in-memory dict and refreshes the UI thread-safely via `_post_skill_ui_refresh()`. `run_instruction` launches a saved instruction as a separate fire-and-forget process (`subprocess.Popen` + `sys.executable`), headless by default (`headless=false` to show the GUI). None are `PARALLEL_SAFE` (they mutate shared state or spawn processes). Meta toggle saved per-instruction.

**State persistence** — `agent_state.json` stores provider, last instruction, model, temperature, thinking settings (incl. `thinking_mode`), `text_verbosity`, display checkbox states (debug, tool calls, activity, show/save thinking), and a `geometries` dict keyed by monitor configuration. Each monitor-config key (from `_get_monitor_config_key()` — Win32 `EnumDisplayMonitors` / macOS CoreGraphics `CGGetActiveDisplayList`) maps to a set of window/dialog geometries (main, editor, prompt, confirm, PS Safety, Skills Manager), so docked/undocked or different arrangements restore correctly. Periodic auto-save every 5s captures live geometry from open dialogs; geometries also flush immediately on dialog close. On restore, `_sanitize_geometry()` validates against the full virtual-desktop bounds (`_get_virtual_screen_bounds()`) and resets windows that are too small (<200×150) or fully off-screen. Old flat-geometry state files are migrated to the per-config format on first load. (Disabled confirm patterns live per-instruction in `agent_instructions.json`, not here. Skill modes are likewise NOT stored here: `skills.json` is their single sticky source of truth, loaded by `_load_skills()`; the `applied_instruction` snapshot deliberately omits `skill_modes` so a relaunch cannot overwrite the user's global modes.)

**Dialog geometry pattern** — All dialogs use a withdraw/deiconify sequence so `transient(parent)` can't override saved positions: `withdraw()` → build content → `update_idletasks()` → set geometry → `deiconify()`. PS Safety re-applies geometry via `after(100ms)` because its checkbutton widgets request a large natural size that can override saved dims on map. On macOS, `transient(parent)` is skipped entirely (its WM confines transients to the parent's screen, blocking secondary-monitor placement); on Windows it works cross-screen and is kept. Dialog refs (`_ps_safety_dialog`/`_confirm_dialog`/`_prompt_dialog`) live on `self` so the auto-save can read live geometry; closing the editor captures the PS Safety geometry before the destroy cascade.

**LaTeX to Unicode conversion** — Assistant text is converted to Unicode after each streaming segment via `_post_process_latex()`, which walks `tag_ranges("assistant")` and applies `_latex_to_unicode()` only to assistant-tagged text (so tool_info filenames/paths aren't mangled). The static converter handles all delimiters (`\( \)`, `$ $`, `\[ \]`, `$$ $$`), *braced* super/subscripts only (`^{...}`/`_{...}` — bare `^x`/`_x` left alone to avoid filename false positives), Greek letters, operators, `\frac{a}{b}`→`a/b`, functions, arrows, set notation, with unrecognised `\command` patterns falling back to backslash-strip. A `post_process_latex` queue message fires after each provider call returns text, and during `complete`.

**Server-side tools** — OpenAI and Anthropic use server-side web search and code execution instead of the local DuckDuckGo `web_search`/`fetch_webpage` tools. OpenAI appends `web_search_preview` + `code_interpreter` (`container: auto`, `include: ["code_interpreter_call.outputs"]`) — but CI is gated off when desktop is on (above). Anthropic appends `web_search_20250305` + `code_execution_20250825` via `client.beta.messages.stream()` with the matching betas + `files-api-2025-04-14`; code-execution file outputs are extracted from `final_message.content` post-stream (file IDs aren't available mid-stream) and downloaded via `client.beta.files.download()`. Gemini can't combine built-in tools (`google_search`, `code_execution`) with custom function declarations (API restriction), so it keeps local DuckDuckGo search. xAI CAN mix (verified live 2026-07-05) and appends server-side `web_search` + `x_search` (+ `code_interpreter`, desktop-gated) at $0.005 per invocation — see the xAI integration block. Code-execution file outputs from both are sniffed with PIL: images are shown inline (max 600px) and saved to `saved_chats/` as PNG; non-image files (exported reports, CSVs, ...) are saved to `saved_chats/` as `ci_output_{ts}_{filename}` with a `[File saved: …]` notice instead of a PIL "cannot identify image file" error — the original filename comes from the provider's file metadata (Anthropic `beta.files.retrieve_metadata`, OpenAI `files.retrieve`), falling back to a utf-8 sniff (`output.txt`/`output.bin`).

**Multi-display desktop tools** — On macOS `pyautogui.screenshot()` only grabs the primary display, so `_macos_display_screenshot()` uses Quartz `CGWindowListCreateImage` with a per-display `CGRect`; on Windows, `ImageGrab.grab(bbox=..., all_screens=True)` via `_get_windows_display_rects()` (EnumDisplayMonitors). Both index the primary (origin 0,0) as display 0. The `screenshot` tool's `display` param: omit it to capture ALL displays as separate images (the recommended first step, stated explicitly in the schema), or pass a number for one. For OpenAI/Gemini, screenshot images are delivered as separate user messages (not embedded in tool outputs) with coordinate-system hints. Region screenshots interpret (x, y, width, height) relative to display N's FULL image (`_display_full_states[N]`), capture, then store the result in `_display_states[N]` for subsequent clicks. The result text tells the model to "use pixel coordinates AS YOU READ THEM... Do NOT scale or convert" to stop it pre-converting after inspecting dimensions via code_interpreter (see CI gating).

**Chat saving is opt-in** — Chats save (on close or via the periodic auto-save) only if a name is typed in "Save Chat as"; blank → no file is created.

**Multi-instance support** — Multiple instances run at once; each claims the lowest free number via lock files (`agent_lock_N.lock` holding the PID). Instance 1 uses `agent_state.json`, 2+ use `agent_state_N.json` for independent persistence. Stale locks (crashed PIDs) are detected via `OpenProcess` + executable-name verification (`GetModuleBaseNameW` confirms `python.exe`/`pythonw.exe`, guarding against recycled PIDs) and reclaimed. The title bar shows `My Agent (N)` for 2+. Locks are cleaned up on graceful close.

**API retry logic** — Same as SelfBot: up to 10 retries, exponential backoff capped at 60s (429) / 90s (529). OpenAI also catches `APITimeoutError` (retry without backoff). A 180s first-content timeout cancels a stream that produces no visible output (thinking/text/tool calls); a background ticker posts elapsed time every 15s while waiting. OpenAI models that reject `temperature` retry without it; those that reject server-side tools are handled by the rejection cache (above). All providers break out of the loop immediately on success.

**STOP during streaming** — STOP sets `stop_requested`, checked inside each provider's stream event loop (not just between API calls), enabling mid-stream cancellation.

**API cost tracking** — `stream_worker()` tracks real-time cost across all three providers. Each streaming method returns a usage dict (6th tuple element): Anthropic from `final_message.usage` (incl. `cache_creation_input_tokens`/`cache_read_input_tokens`), OpenAI from `stream.get_final_response().usage`, Gemini from the last chunk's `usage_metadata`. Static `_get_pricing(provider, model)` does a longest-prefix match against the hardcoded tables in `constants.py` (`ANTHROPIC_PRICING`/`OPENAI_PRICING`/`GEMINI_PRICING`). Costs accumulate per run and emit as `cost_update` messages (blue monospace `cost_info` tag, gated by Activity); unmatched prefixes skip silently. `MyAgent_Pricing.txt` documents the entries. STOP/incomplete streams return `None` usage and skip cost for that call. When the agentic loop ends (GUI **and** headless, on success **and** on the exception path — which also schedules `_on_close` in headless so a failed unattended run exits instead of lingering as a zombie process), `_log_api_cost(total_cost)` appends one `{timestamp};{provider};{model};{cost}` line to `APICOST_LOG_FILE` (repo root via `_BASE_DIR`, gitignored) — semicolon-delimited so a comma in a model name can't split a field, plain 4-decimal cost for spreadsheet summing. It skips when `total_cost == 0` (no priced usage — Ollama, unmatched prefix, or STOP before the first result), mirroring the live display; best-effort, so a write failure warns via the queue but never interrupts the run. Before each append it runs the shared one-slot rotation `rotate_log_if_needed(APICOST_LOG_FILE, APICOST_LOG_MAX_BYTES)` (`myagent/helpers.py`; 100 KB cap in `constants.py`): over the cap the log is atomically renamed to `APICostLog.txt.old` (replacing the previous archive) and restarts with a timestamped marker line — semicolon-free, so the Cost Log viewers' field-count parsers (`NF>=4` / `$f.Count -lt 4`) skip it in their summaries. `Heartbeat.py` (`heartbeat.log`) and `UnreadSummary.py` (`unread_summary.log`) delegate their rotation to the same helper.

**State restore fallback** — `_restore_model_params()` checks the saved model exists in the saved provider's model list; on mismatch (e.g. an auto-save race pairing an Anthropic model with the OpenAI provider), it falls back to the first available model for that provider.
